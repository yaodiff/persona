# PersonaCore for iOS

The Apple binding of the shared Rust core (#6871, #6793). The iOS app and `PersonaTests` link it; watch,
widgets, Vision and Persona Link do not. It does not replace the production `ChatStore` in phase 1
and has no user-facing text or screen changes.

## Build and verify

```sh
native/app-core/scripts/build-apple.sh
xcrun swift test --package-path apple/Packages/PersonaCore -Xswiftc -warnings-as-errors
```

The builder uses the workspace's pinned Rust toolchain and creates `build/PersonaCoreC.xcframework` with iOS device,
the Mac's iOS-simulator architecture and the macOS host slice; `--simulator` (what `scripts/app/sim.sh` asks for) builds
the simulator slice only, which neither `swift test` on the Mac nor an Xcode build for a phone or "My Mac (Designed for
iPad)" can use: run the builder with no flag before those, or Xcode stops with "no library for this platform was found".
The package's `build/`, `.build/` and Cargo target are ignored: no XCFramework, static library or dynamic library
belongs in a commit. The input hash covers the source files' content and their paths in the checkout, the toolchain and
builder, the Mac's architecture, the Apple SDKs and the caller's `RUSTFLAGS` and deployment targets, never where the
checkout is: built frameworks are shared by every worktree through a cache under `~/Library/Caches/persona/app-core`
(#10713, `docs/operations/testing.md` "Development builds").
Run the builder before XcodeGen/Xcode package resolution on a clean checkout.

On Linux, with a Linux Apple toolchain (one that builds the iOS app without Xcode), the same
command builds the iOS device and arm64 simulator slices as static libraries, writes the XCFramework without
`xcodebuild`, and leaves out the macOS slice, so `swift test` still needs a Mac (#16944). Its cache is under
`${XDG_CACHE_HOME:-~/.cache}/persona/app-core`, and its key takes the SDK build versions from the toolchain's copy of the
Xcode SDKs (`APPLE_BUILD_SDK_ROOT`, else `sdk_root` in apple-build's `config.json`).

`Sources/PersonaCoreWire` and `Sources/Serde` are generated by `cargo run -p persona-core-typegen`; do not edit them
manually. `cargo run -p persona-core-typegen -- --check` regenerates both Swift and Kotlin in scratch directories and
byte-compares the committed trees. `PersonaCore` and its tests use Swift 6, nonisolated defaults, strict concurrency and
warnings as errors. The mutable serializer/deserializer classes are not marked Sendable.

The real-C replay is `PersonaCoreContinuityTests` on macOS and in the iOS `PersonaTests` target. It reads every JSON
case under `spec/fixtures/continuity`, dispatches encoded actions, drains patches, applies Insert/Update/Remove, and
compares complete items, ids, continuity fields and effects. `NativeChatStoreContinuityReplay` runs the same JSON
against the unmodified native iOS `ChatStore`. A separate AppModel test proves the native immediate-fill scheduling.
The fixture reader (`ContinuityCase`, `ContinuityJSON`) and the C replay (`ContinuityBindingReplay`) are the test-only
`PersonaCoreTestSupport` target in `Tests/PersonaCoreTestSupport`. Only `PersonaCoreTests` and `PersonaTests` link it,
so the `PersonaCore` library the app links reads no files.

Only `dispatch` is suitable for the UI thread. `drain`, `flush`, creation and `close` stay off the main actor and off
the launch path. Host callbacks run on the Rust worker thread and must not synchronously flush or free that same core;
the C header specifies the ownership and borrowed-buffer contract. The callback box is retained once and released once.
Errors from an effect callback are reported by the next test-only `flush` rather than silently discarded.

## Pure projection binding (#8952)

`PersonaCoreProjections` wraps the six existing pure C entry points: sort, answer, display_answer, stream_chunks,
turns and task_index. Each accepts and returns a UTF-8 JSON document, without a core handle or a worker. An empty C
result is an explicit error rather than an empty JSON value; the adapter copies the returned bytes and gives the
allocation back with `persona_core_bytes_free` on every path. `displayAnswer` takes a bare JSON string for the option
label. These synchronous calls run on their caller, so sizable projections stay off the main actor. No production
client calls them yet.

The test-only replay in `ProjectionBindingReplay` and `TranscriptProjectionReplay` reads the unchanged fixtures and
compares complete expected objects, including exact array order and integer-vs-boolean distinctions. It pins exact
case-name manifests, exercises malformed input in each domain, and catches deliberately wrong expected objects through
the same comparison. `PersonaCoreProjectionTests` runs this on macOS through the real C XCFramework:

- 33 `agents_list` sort cases, including the three iOS-derived held-row State, Space and quiet-fold cases (#9033).
  The separate `session_state` / `hub_state` projections have no C entry point and are
- Answer: 15 question and 8 recommendation cases, conditional expected fields, invalid page/option and U+200B.
- Stream chunks: all 21 complete `{done, tail}` objects.
- Turns: all 57 static cases with the checked-in current-iOS overlay applied by the caller; 54 cases hold 73 complete
  turn objects, while three compare empty arrays only.
- Task index: all five complete expected objects plus the background receipt boundary.

This is macOS-host SwiftPM binding evidence, not an iOS simulator or physical-device result. It does not cover
production adapters, rendered lines, incremental rebuilds, `StreamRepair`, transport, performance or the minimum
Xcode 26.0 compiler when tested with a later Xcode.

## Adapter and shadow contract

`PersonaCoreCallbacks.changedChat` carries the chat ID and the global patch version. `Effect.Fetch` already carries the
chat, so the adapter can route a wake and its transport request to the same owner without guessing from a global version.
Legacy `changed` remains the version-only compatibility path when no targeted callback is supplied. C/JNI/OHOS preserve
that fallback; an existing host does not need a new callback.

`CoreContinuityShadow` is a test-only adapter used by fixture comparisons. Native `ChatStore` remains the
iOS behavioral reference and the production default. The shadow harness applies the same action, drains one patch and
compares items, continuity fields and per-step effects; every event's wake is checked against its chat and whether the
patch changed. Diagnostics contain only a rule and an input shape, never message contents or expected/actual item JSON.
The shadow does not select Rust for production. Real `AppModel` tests with manually released `APIClient` responses
cover independent concurrent folds, coalescing two opens of one fold, overlapping reloads retaining newer pushes, and
per-owner subscriptions; fold/reload rules must remain covered before any later adapter integration.

### Production DEBUG shadow (#8970)

The iOS app's `ChatContinuityAdapting` boundary keeps native `ChatStore` authoritative. In DEBUG builds the
`ProductionContinuityShadow` mirrors the same immutable inputs into one lazily created real C core on a private serial
queue, applies every drained patch and compares complete decoded items and continuity state. A `ChatPatch` is a delta:
its continuity fields are those at the previous drain, so scheduling-only inputs cannot be treated as a full snapshot.
The adapter mirrors native reload retention and fold ownership explicitly; core effects are inspected only and never
reach native transport. Tests drain on that private queue, never the main thread.

Diagnostics contain `domain`, `rule` and an input shape made of kind, counts and set/unset flags, never message text,
item/fold/chat IDs, history, sequence values or payload JSON. Mismatches use the existing error-report queue and OSLog.
DEBUG enables the mirror by default; `-showContinuityShadow NO` turns it off and `YES` selects it explicitly for an
optimized A/B run. The implementation and its switch are excluded from Release, which retains the original native
calls. No Android, UI or production-default implementation changes are involved.

The package and fixture replay are not proof of physical-device performance, download-size, launch or memory budgets.
Those remain unmeasured until a named device/simulator, optimized build and workload are reported.
