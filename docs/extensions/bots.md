# Lark bot: chatting with Persona in Lark

When the user DMs the bot of a custom Lark app, they are talking to Persona: messages go into the main chat in the **Persona** tab (or, via commands, another chat or
Claude Code / Codex on one of the computers), and the turn's answer is sent back to Lark as the bot; whenever Persona or an Agent needs the user to answer or approve something, a card is sent in Lark,
and one tap answers it; pushes and answers from the main chat elsewhere can also be copied to Lark. Each item has its own switch, all off by default (requested 2026-11-02: "do P1/2/3, all optional", issue #322).

It is the channel `feishu` (`docs/extensions/channels.md`): tracking the turn goes through the shared pipeline (`assistant/channels_runs.go`, rules in `server/internal/channel`, the same as WeChat);
this page covers the Lark side (progress card, answer card, reactions, question cards, commands).

**Who owns what** (since 2026-11-04, `docs/extensions/channels.md` ("Responsibilities"); since 2026-11-05 the transport also lives in the manager, `server/internal/extmgr`, `docs/extensions/extensions.md` ("Who owns what"); the transport parts below that say "hub" are done by the manager): the transport is only the app credentials and feature switches (`bots.feishu`), the Open Platform long connection, pairing, accepting only the owner (in DMs, and in the topics of the group chats the owner opted in), sending / replying to / editing messages and cards,
reactions, reading messages and downloading resources; the owner's messages and card taps are handed to the assistant (`feishu.message` and `feishu.card_action` on the bus). Which chat a message goes to, commands, tracking the turn, progress and answer cards,
question cards and button answers, pushes and sync belong to the assistant (`personad assistant`), and so does the chat state `bots.feishu.state`; whatever it needs to send or edit, it asks the hub to do via `app.call feishu.*`.
Every card the assistant posts (`feishu.post`) that lands is logged in the assistant's log as `bots: card sent: kind=<kind> machine=<id> session=<id> message=<id>` (#8270): `agent_done` (an Agent's finished card), `push` (a `notify_user` copy), `sync` / `task` (the main chat's or a scheduled task's own answer), `answer` / `progress` (a run's answer and progress card), an Agent's `question` / `permission` / `plan` / `screen` card, and `other` for the rest (machine and session `-`); a failed one is logged by its sender as before.
When the assistant isn't connected, the owner's message first waits up to 60 seconds for it (the hub just started, the assistant is restarting); only if it doesn't come does the bot reply "Couldn't send it: Can’t reach the assistant right now. Try again later"; card taps get the toast "Can’t reach the assistant right now. Try again later";
pairing, binding and the settings page here keep working (see `docs/extensions/channels.md` ("When the assistant is away")). When a card tap answers a question / approval, the hub hands the assistant a one-time "owner action" that can only answer that one card;
the assistant can't approve anything on its own (`docs/extensions/channels.md` ("Responsibilities", "No answering approvals on the user's behalf")). After re-pairing (including while the assistant was away), the chat starts over: it goes back to the main chat, and thread bindings and pending answers are cleared.

Code: `server/internal/modules/lark/feishubot` (long connection, REST; the extension host reaches it through `server/internal/botport`), `server/internal/botcard` (the card and event model with no I/O: cards, events and message content, answer rendering, error codes; #13404), `server/internal/hub/bots*.go` (pairing, routing, transport: events on the long connection are handed to the assistant; `assistant_channels.go` is the `feishu.*` the hub gives the assistant),
`server/internal/assistant/feishu*.go` (targets, commands, sending into chats, cards, pushes, sync: Lark's side of the shared pipeline);
prompt `server/internal/prompts/bot/message.md`; the App page `apple/Persona/Views/Settings/FeishuBotView.swift` (**Settings › Connectors › Lark Bot**). On web Settings › Connectors, the lark-cli status appears in this Lark group.

## Recovering saved settings

The manager treats a missing `bots.feishu` record as a fresh, disabled bot with the existing feature defaults.
A failed storage read or JSON decode leaves the settings unknown: Settings GET/PUT and pairing requests fail,
channel binding does not start registration, and `feishu.status` returns an error rather than an empty owner.
The assistant therefore does not reconcile an unread pairing as an unpairing. Writes are blocked until a complete read succeeds.

Later status, settings and transport lookups retry the read, at most once every five seconds per manager while it fails.
Each storage read has a five-second deadline, shortened by the caller's earlier cancellation. Only one read runs at a time;
it releases the bot settings mutex during storage I/O, and concurrent lookups return temporarily unavailable instead of
waiting behind the read. A timeout starts the same cooldown, and the next eligible lookup can recover.
There is no additional polling loop. A successful read restores the saved credentials, owner, pending pairing and switches
and starts the enabled bot's connection under the manager's existing context; the owner does not pair again.
Successful reads, including a genuinely missing record, are cached as before. JSON `null` and `{}` retain the existing
defaulted-decode behavior; only an actual read/decode error leaves settings unknown. A disabled bot, a member hub or a manager
whose context has ended keeps the connection closed. Persistently invalid records remain protected and log one failure
per attempted read; correcting the stored record lets the next eligible lookup recover it. This does not add a reset or
migration of invalid data, change chat permissions, or change the card-nudge defaults or timing.

The lark-cli connector is registered before connector switches and options are restored, even while its profile is
unknown. Every CLI execution, including Inbox polling and login, is gated on a known identity. A manager.json profile
override is already authoritative during a storage outage; a genuinely empty saved configuration still selects the CLI
default after a successful read. A saved manual profile applies even when the bot itself is disabled.
On recovery the existing connector refresh path synchronizes the managed profile when needed and replaces the placeholder
outside the bot settings lock, after startup has restored connector settings. Replacement preserves the connector's own
enabled/feed switches and current options; retained old connectors refuse calls rather than reuse their Inbox caches
for a different profile. Publication stays quarantined until the new instance has its disabled mark; only then is the
identity gate released and an enabled connector started. Retired instances refuse process execution even when the selected
profile name is unchanged. Assistant configuration and extension host CLI requests also fail closed while identity is unread.

The connector's `connectors.settings` record is independent of `bots.feishu`: a failed read quarantines the placeholder
with its connector and Inbox feed off, and rejects preference writes until that record can be read completely. Recovery
reads its durable options, feed and enabled choices before starting the replacement; a missing record keeps the existing
defaults. A manager.json profile override still works when only bot settings are unavailable, with known connector choices.
An unavailable preferences record also gates that override until its enabled/feed policy is known.

A failed managed-profile synchronization remains pending after bot settings have loaded. Ordinary bot status/transport
lookups, connector listings and tool/CLI calls can request one recovery attempt after the shared five-second failure
cooldown. Concurrent requests coalesce into one worker; synchronization runs outside the bot lock under the manager's
lifetime. There is no recovery timer loop. A later successful synchronization releases the identity gate, restores the
connector preferences and resumes its normal lifecycle.

## How it differs from Lark `/agent`

| | Lark bot (this page) | Lark `/agent` (`docs/extensions/lark-agent.md`) |
| --- | --- | --- |
| Trigger | DM the bot | **You** send `/agent …` in any chat |
| Identity | The bot itself (never taken as you speaking) | Replies in your name (ends with "> 🤖 AI 代答，仅供参考" (AI reply, for reference only); the prompt forbids making promises for you) |
| Where it goes | The main chat (or the chat / Agent switched to), continuing the earlier conversation | A new headless chat per request / thread; the hub first collects that chat's context |
| Depends on | A custom app on the Lark Open Platform (may need admin review) | The Lark gateway (no approval needed) |
| Interaction | Card buttons answer questions and approvals directly | None |

The two complement each other and have separate switches.

## Why the Open Platform long connection

- The hub doesn't need a public address: `POST /callback/ws/endpoint` returns a WebSocket URL, the hub connects out, and both events and card callbacks come over that connection (Open Platform's "receive events over a long connection").
  It runs on intranet machines, NAS boxes and home machines alike.
- The official Go SDK (`oapi-sdk-go/v3`) is 4.8 MB in total and also pulls in gogo/protobuf and gorilla/websocket; the protocol itself is tiny (one protobuf `Frame`),
  so `feishubot/frame.go` hand-writes the encoding, checked against bytes the SDK generates in `TestFrameMatchesTheSDK`. The WebSocket is the repo's existing coder/websocket.
- Protocol essentials (following the SDK's behavior): the client sends ping control frames every `ClientConfig.PingInterval` (2 minutes by default), and the pong may carry new config; a data frame's
  header has `type` (event / card), `message_id`, `sum` / `seq` (fragments of large messages, reassembled before processing); every data frame must be answered with the same frame, its payload replaced with
  `{"code":200,"data":<base64 JSON>}`; for card callbacks the data is the toast / new card to show, and if Lark gets no answer **within 3 seconds** it retries. Receiving nothing for two ping intervals means the connection is dead, and it reconnects.
- The same event may be redelivered: messages are processed only once per message_id (`seen` in `bots.feishu.state`, keeping the latest 300).
  Card presses are not deduplicated on the hub side, which hands every delivery to the assistant: each press that does something once guards itself there —
  an answer goes through its one-use owner action (a second answer to the same card finds it answered, `interactions.resolve`), and a press that starts work
  takes a slot per pressed card and button (`pressOnce`, `modules/lark/card_actions.go`: the `/start` card's **Start** for a minute, the list card's **Start new agent**
  for ten seconds), so a double tap, Lark's redelivery and the hub's resend of a call it gave up on all act once. A press whose work failed frees its slot and
  says why, so pressing again retries it rather than being answered with the same "Starting…".

## Pairing and permissions

- App credentials: enter the App ID / App Secret in the App (it tries `GET /open-apis/bot/v3/info` once first and saves only if that works); the Secret is AES-GCM encrypted with the manager's own `secret.key` and stored in settings
  `bots.feishu` (the same master key as launcher keys), and no endpoint ever returns the plaintext. If you'd rather not go through the App, write `bots.feishu` in the manager's `manager.json` (0600, `docs/operations/config.md` ("manager.json")); what's saved from the App takes precedence.
- **Only the one paired person**: the main chat can use all the data (Lark, mail, every computer, the phone's calendar and location), and anyone in a group can @ it, so a group is only listened to where the owner said so ("Topic group chats" below). In the bot's DM, anyone else who writes to it gets a single reply "This bot only works for its owner." (at most once per person per 10 minutes). Card buttons also only accept the owner's open_id, in the DM and in a group alike, and only on a card in the DM or in an opted-in group: the chat comes from the callback, else from the card's message (what the hub remembers of it, else the Open Platform), and a press whose chat cannot be told is refused.
- Sending: the assistant's `feishu.post` / `feishu.text` go into the owner's DM unless the call names a `chat_id`; the hub accepts the owner's DM chat id and the ids of the group chats the owner opted in (anything else is refused with an error, nothing is sent). `in_thread: true` on a reply puts it in the parent's thread (`reply_in_thread`); if the parent was withdrawn, a plain reply's answer goes into the call's chat as a plain message, while a call with `no_detour: true` fails with the error instead (for what belongs under that parent or nowhere: a to-do's line into its topic, and a card for a topic's run, which then goes to the owner's DM as one that the chat refused does). A reply lands in the chat of the message it answers whatever `chat_id` says, so `reply_to` is checked too, for `feishu.post`, `feishu.text` and `feishu.cot_create` (the only calls that take one): the hub looks up which chat the parent is in and refuses a parent that is not in the owner's DM or an opted-in group, and one whose chat it cannot tell. The chat comes from what the hub remembers (the owner's own messages in the DM and in an opted-in group, and the messages the bot itself sent there, the last 500; a stranger's message is never kept, so strangers cannot push them out), else from the Open Platform (`GET /open-apis/im/v1/messages/:id`, whose answer must be about that very message; the client reads again when the network blips or Feishu is busy; an answer for a chat the bot may use is remembered). A lookup that keeps failing refuses the reply, so it happens only for a parent that is not remembered (after a hub restart). A parent that is withdrawn or deleted cannot be replied to and goes by the rule above. An agent message (`feishu.cot_create`) follows the same parent rule and accepts `chat_id` and `in_thread`: its destination is an allowed chat, with `origin_message_id` and `reply_in_thread` keeping it in the parent's origin topic. A thread reply and a plain reply to the same message with the same content have different idempotency keys, so one is not dropped as a repeat of the other. A call may also pass its own `uuid` (`feishu.post` and `feishu.text`; letters, digits, `:`, `_` and `-` only, anything else is ignored; cut to 50 characters for text, 46 for a card): the reply goes out under it in place of the parent-and-content key, so two lines with the same words are two messages. Without these fields nothing changes. The one exception is a text reply (`feishu.text`) under a message the owner's `@bot /ai …` was taken from in a group that is not opted in ("Asking from any group" below): that chat is not allowed, only the reply is.
- Reminder-only routing fence (#12609): a keyed private-chat reminder post may carry `todo_reminder_pairing` with the original status's `owner` and `paired_at`. The transport validates both against the same bot-settings snapshot used to choose its API client and destination, with pushes still enabled. A missing/changed pairing, an explicit chat/reply/thread or an invalid key is refused before transport. This constraint only narrows a reminder's existing route; calls without it keep their existing authorization. A request already admitted to the provider remains pinned to its snapshot's recipient and cannot be retracted by this check.
- **Creating the app in one authorization** (#4347, `extmgr/bots_register.go`, `feishubot/register.go`): binding the channel (Settings › Channels › Lark) with no app yet starts the accounts site's
  device-code app registration (`POST https://accounts.feishu.cn/oauth/v1/app/registration`, Lark's accounts site for Lark tenants) for a personal-agent app named Persona, asking for the bot's tenant scopes
  and the card callback (the page's `addons`) and for the confirming person's `open_id`. The step is a QR code of the authorization page with a link to open it directly (on the phone that has Lark);
  the client asks again every `interval` seconds. Once confirmed, the answer carries the new app's App ID and Secret: they are saved and checked like typed ones, `AutoConfigure` runs as below, the confirming
  person becomes the owner, and the bot greets them by `open_id`, which gives the private chat's `chat_id`; the assistant is told `feishu.owner {paired, greeted}` and starts the chat without a second greeting.
  The registration under way (its device code sealed with `secret.key`) is kept in `bots.feishu.registration`, so a restart between polls loses nothing; a confirmed one whose finishing failed is finished on the next poll, never registered again.
  Concurrent clients reuse the same effective registration; binding operations wait independently of the bot settings lock, so an older network response cannot replace or clear a newer session (#12620).
  A tenant on the other cloud (`tenant_brand`) is polled there. An expired or declined authorization keeps its error until the user cancels the step and starts binding again; background polling does not start another registration.
  When the accounts site cannot be reached, or the deployment is private, the step is the credentials form.
  Typing the App ID and App Secret of an existing app stays available on the Lark bot's settings page, folded under Advanced.
  Changing credentials through binding or the bot settings page retires the previous registration in the same settings commit, after validation succeeds; a failed validation or save keeps it. These updates share the binding lifecycle gate, while switch-only and feature-only settings remain independent and keep the registration.
  Polls from a retired registration do not re-enable a bot the user turned off; they stop at the credentials prompt until the user explicitly binds or enables it again.
  The web Lark bot page starts the same registration itself when there is no app (#5818): its first group is **Create the bot**, one
  **Scan to create with Lark** button that sends the channel's bind step (`POST /api/v1/channels/feishu/bind`) and draws the QR step
  Settings › Channels draws, so both places run one flow. The credentials form and the manual steps sit under a folded
  **Already have a Lark app?** (no app) or **Advanced: use another Lark app** (an app bound); with credentials from `manager.json` there is no
  create step. When the dialog also shows reading Lark as you (`larkcli`) and lark-cli follows the bot's app with none of its own,
  that section says to create the app above first instead of offering an authorization that cannot work; once the scan is
  confirmed, the authorization starts by itself and shows its own QR code, so setting up both is two scans on one page.
- Pairing (an app whose credentials were typed in): tap **Pair** in the App to get a 6-digit code (valid for 10 minutes) and send it to the bot in Lark; whoever sends it becomes the owner (its open_id and the DM's chat_id are recorded).
  When not paired, DMing it returns instructions on how to pair; 5 wrong guesses void the code, and you have to get a new one. Changing the App ID means pairing again (it's a different bot).
  The owner and consumed code must be saved before pairing is acknowledged or messages are authorized. If saving fails, the bot asks you to send the same code again before it expires; the previous code, expiry and attempt count stay unchanged. A later failure to save the optional contact name keeps the committed binding and its previous display name.
- Names: reading contacts needs `contact:user.base:readonly`; without that permission the owner is called by `assistant.owner` in the manager's `manager.json`, and others "someone".

## Reading as you: daily sync

The bot reads and writes as itself (a tenant token). Separately, the owner can let a bot's app read **as them** once, and
from then on a daily sync copies what changed in their Lark into the knowledge base: chats and their history (threads and
attachments included), Drive, Docs, Sheets, Base, Wiki and Minutes. It is the built-in Lark channel's own feature
(`server/internal/modules/lark/larkauth` and `server/internal/modules/lark/larksync`, wired to the manager through
`server/internal/extmgr/larksync_host.go`); it needs no extension and no lark-cli.

### Two steps on one page

1. **Create or extend the app.** The device-code registration of "Pairing and permissions" now also asks for user scopes
   (the page's `addons.scopes.user`), from one of two packs:
   - **Documents and minutes** (`docs_standard`): Drive, Docs, Sheets, Base, Wiki, Minutes and message search, plus
     `offline_access`, which is what gives a refresh token.
   - **Everything, chat history included** (`full_with_im`): adds the chats and their history as the owner
     (`im:message.group_msg:get_as_user`, `im:message.p2p_msg:get_as_user`) and file downloads.

   An existing app (the chat bot's, or one added earlier) gets the scopes added by a registration that names its App ID
   (`POST /api/v1/bots/feishu/sync/bots/{bot}/scopes`); a new sync-only app is one QR code
   (`POST /api/v1/bots/feishu/sync/bots`, then `POST /api/v1/bots/feishu/sync/bots/{bot}/register` until done).
2. **Authorize.** Right after, the page starts the user authorization (`POST /api/v1/bots/feishu/sync/bots/{bot}/authorize`):
   OAuth v3 with PKCE and `offline_access`. The redirect URL is the web app's `/lark-oauth` page; the manager first adds it to
   the app through `PATCH /open-apis/application/v7/applications/{app_id}/config` (`security.add.redirect_urls`, effective at
   once without review) together with the user scopes, and publishes a version. The page then opens Lark's authorization
   page; Lark returns to `/lark-oauth`, which hands `state` and `code` to `POST /api/v1/bots/feishu/sync/oauth`.

   Changing the app's configuration needs `application:application:patch`, which the platform does not grant by default.
   Without it there are two fallbacks, in order:
   - **Device flow**: the page shows a QR code that authorizes without any redirect URL (the endpoint lark-cli uses,
     `oauth/v1/device_authorization`; it is not in the public API catalogue, so it may change).
   - **Paste once**: if that fails too, the page shows the redirect URL with a copy button and a link straight to the app's
     security settings; after pasting it there, **Continue** opens the authorization page.

The iPhone and iPad app and the Android app have the same section on their Lark bot page (#15392), on the same routes.
For the browser way they show Lark's authorization page in an in-app web view with the hub's own address plus
`/lark-oauth` as the redirect URL, stop that view when it reaches the address (the web page never loads), and hand
`state` and `code` to `POST /api/v1/bots/feishu/sync/oauth` themselves. The device flow and the paste-once way work as
on the web. A hub without the sync (404, or `available: false`) hides the section.

So a new owner confirms twice on one page (scan to create, then agree); an app that already has the scopes needs only
the second. The tokens are sealed with `secret.key` (settings `bots.feishu.sync.bindings`, re-sealed by the key rotation),
never shown and never logged.

### Company tenants and approval

The app the registration creates is a **custom app of the tenant** of whoever scans (Lark has no separate "personal app"
type that skips the tenant's rules). In a company tenant:

- **User scopes need the admin's approval**, unless the admin made them review-free. Reading chat history as a user
  (`…:get_as_user`), Drive and Minutes are sensitive and usually reviewed. Until a version is approved the page shows that
  the app is waiting for the admin's approval (`awaiting_approval`); authorizing meanwhile only grants what is already approved.
- If the company does not let employees create apps, the scan is refused: ask IT to create the app (or allow it), enter its
  credentials under **Already have a Lark app?**, then add the scopes and authorize.
- Only people within the app's availability scope can authorize it (error `20010` otherwise).
- When the admin will not approve chat history, choose **Documents and minutes**: documents, wiki and minutes still sync,
  and company chats stay with what the Lark gateway already collects.
- A personal account without a team can create a free one-person team in the Lark app first; its owner is its admin and
  approves their own app.

### Several accounts and several bots

Bindings are (account × bot) pairs. The bot in `bots.feishu` stays the **primary** bot (`bot_id` `primary`): the only one
that chats, configured exactly as before, so older settings need no migration and keep working unchanged. Every other bot
is **sync-only** (`bots.feishu.sync.bots`) and holds no long connection. An account is whoever authorized
(`<brand>:<tenant_key>:<open_id>`); a work account and a personal account, each with its own tenant's app, are two
bindings. Each binding has its own token refresh (one at a time: the platform rotates the refresh token, so two
concurrent refreshes would lose it), cursors, rate limits and failure backoff: one binding being refused, rate-limited or
missing a scope marks only that binding, and the others and the chat bot carry on.

### The daily run

Each enabled binding runs once a day, at `schedule_hour` local time (default 3) plus a minute of its own, or at once with
**Sync now** (`POST /api/v1/bots/feishu/sync/bindings/{key}/run`). The first run reads the last 30 days; later runs read what
changed since the cursors, with a few minutes of overlap. A run has a 20-minute budget; what is left is read next time.
For bindings that include chat history (`full_with_im`), a lightweight incremental chat sync also runs every 15 minutes
(5-minute budget) after the first full run: it reads only new messages since each chat's cursor, discovers newly started
single chats (`chat_type: "p2p_chat"`), and follows any newly linked cloud documents and meeting minutes without walking
Drive or Wiki. It shares the binding's rate limiter and running lock with the daily full sync (never overlapping it) and
can be turned off in Settings (`PUT /api/v1/bots/feishu/sync` with `im_poll: false`), leaving the daily full run unchanged.

Synced messages are scanned for Feishu / Lark cloud document and wiki links (`/docx/`, `/docs/`, `/sheets/`, `/base/`,
`/bitable/`, `/file/`, `/wiki/`, `/minutes/`), including documents shared with the owner outside their My Space root.
Wiki links resolve via `GET /open-apis/wiki/v2/spaces/get_node`, metadata is batch-queried via
`POST /open-apis/drive/v1/metas/batch_query`, `docx` / `sheet` / `bitable` convert to Markdown with the existing readers,
readable text files (`.md`, `.txt`, `.csv`, `.json`, `.yaml`, etc.) download via
`GET /open-apis/drive/v1/files/{file_token}/download` using the user token, and non-text files keep metadata only. Every
linked document deduplicates by `obj_token` + revision and records `message_link` in `sources[]`; unfetched links when a
run hits its budget or rate limit are persisted per binding in `lark_sync_cursors` (`links_queue`, deduplicated by
`obj_token`) and drained on subsequent runs (including 15-minute `ModeIM` runs) with recent live links prioritized ahead
of historical backfill links. Unreadable documents (403, missing scope, export disabled, oversized file) record the
reason in `Note` at revision 0 without blocking the run, and 403 / `scope_missing` links remain queued for automatic
retry once permissions recover. The scope packs and all three manual setup guides include the API permissions below.

pack for compatibility. Full retains `drive:file:download`; the document tier's existing `drive:drive:readonly`
already covers the readable-file download endpoint. `wiki:node:retrieve` covers child listing, while
`wiki:wiki:readonly` covers resolving a wiki link; these are different API requirements.

`drive:drive:readonly` does **not** cover the batch metadata endpoint, which needs
`drive:drive.metadata:readonly` (or the broader write scope). `contact:user.base:readonly` grants the name field,
but querying another user's contact record also needs `contact:contact.base:readonly`. The p2p chat-name fallback
needs `im:chat:readonly`, even though `im:chat:read` is sufficient for listing chats.

A missing permission appears as **Reauthorize to add missing permissions**, with **Authorize Again** available
even when the grant is far from expiry. First publish/approve the app permissions, then authorize the expanded
user scope pack. Refreshing an old grant does not expand it. When the owner explicitly starts authorization for a
`scope_missing` binding, the manager attempts to configure the current scopes even if the redirect URL is unchanged;
without the patch permission it uses the existing device/manual fallbacks. See the official
[permission application guide](https://open.feishu.cn/document/faq/trouble-shooting/how-to-fix-the-99991672-error).

Sender lookup scope errors are reported separately from readable messages, so message content and cursors can
still commit. A failed sender-name repair remains pending (`backfill_version` does not advance), including when
some names were resolved. Reauthorization preserves cursors and the pending repair marker and makes the binding
due now; the next scheduler tick runs the sync and retries repair automatically. Disabled bindings remain disabled.
The repair marks its version complete only after it finishes, so later ticks are idempotent.

Senders that `contact/v3` cannot see (external members) are looked up in the chat's member list, read on demand: only
while a sender of that chat is still unnamed, resuming where it stopped, up to 500 pages of 100. A member who left the
group is in no list; the binding's name book (`sender_names` cursor, at most 5,000 names, the oldest learned dropped
first) keeps the names the sync learned from contacts, member lists and @mentions, and the sender-name backfill
(version 3) also reads the chat around such a sender's message for an @mention of them. Another app's bot is named only
when a message mentions it: the API that names an app by its id
([application/v6](https://open.feishu.cn/document/server-docs/application-v6/application/get)) takes a tenant token,
an admin scope and a custom app of the same enterprise, none of which a user's sync has. A system message without a
`sender_id` stays unnamed.

The sender-name backfill runs in rounds, one after each sync run until it is done. A round has its own budget
(`larkSyncNamesBudget`, 90 seconds, apart from the run's) and starts only after the run's messages are committed, so it
never holds up message sync. Every lookup is paced at five requests a second, so a backlog of external senders (one
`contact/v3` call each) and a few large groups (up to 500 member pages each) can need more than one round. When the
budget runs out, the round stops and saves how far it got in the `sender_names:progress` cursor: each large group's
next member page and which senders the pages already read were checked for, plus the lookups that found nothing. Those
are tried again after a week. The next round picks up from there, and `backfill_version` advances only once a round
finishes everything. A timeout, rate limit or passing failure in this step only degrades naming. The binding's health
stays `ok`, the run is not counted as failed, and the reason goes into `names_warning`, with `names_rounds` counting the
rounds. Only what the owner has to fix shows in health: a missing contact scope (`scope_missing`) or a refused grant
(`needs_reauth`). Coverage: `server/internal/modules/lark/larksync/names_progress_test.go`,
`server/internal/modules/lark/larksync/service_names_test.go`.

Regression coverage: `server/internal/larksyncwire/scopes_test.go` checks the audited permission alternatives;
`scripts/test/test_lark_sync_scope_guides.py` checks every locale of the three setup guides against both packs;
`server/internal/modules/lark/larksync/service_impoll_test.go` covers scope refusal followed by authorization and scheduler recovery;
client sync model/component tests cover the reauthorization prompt and action.


The sync's runs commit cursors, the dedup index and the outbox rows together in one transaction; once committed, any round that wrote new messages emits batched, paginated `lark.messages` metadata events (no message bodies) to enabled extensions subscribed to `lark.messages` and explicitly granted `lark.messages.read` (`docs/extensions/extensions.md` "Events").

Requests are rate-limited per binding and per API family, and a 429, `99991400`, `230020` or `1061045` waits as the platform
asks before trying again. **A read that fails leaves its cursor where it was**: the cursors, the dedup index and what the
knowledge base will collect are committed together after a run, so nothing is skipped and nothing half-read is kept. A failed
run tries again 15 minutes later; from the third failure in a row it backs off 1, 6 and then 24 hours. A run that ran out of
budget or into the rate limit goes on an hour later. An authorization lasts at most 365 days; 14, 7 and 1 day before the end
the owner gets a reminder to authorize again, and the page shows it.

### One copy of everything

Every piece of content has one canonical key: `feishu_msg:<message_id>`, `feishu_doc:<obj_token>` (a wiki node resolves to
its document), `feishu_minute:<token>`. The manager's index (Postgres `lark_sync_index`) records each key's revision, body
hash and every place it was read from (`sources`: binding, account, how it was found). Content read again by another bot,
another account, or through both Drive and Wiki is written once and only gains a source. A document whose revision grew is
updated in place; one that arrives late with an older revision never replaces the newer one. The knowledge base applies
the same rule to its items (`canonical_key`, `revision` and `sources` on `kbwire.Item`).

Alignment with what the Lark gateway already put in the knowledge base: documents and minutes match by the
token in their URL (a wiki link by its node token), so the existing item is updated in place and lists both sources.
Messages first use a known pairing of the two chats (the knowledge base's `chats/.crosswalk.json`), then a content
fingerprint: the same chat name, sender, two-second window and text means the same message, which is not written twice and
records the pairing for next time.

## How a message flows

1. `im.message.receive_v1` → de-dup → stop if it's not the owner / not a DM (a group's message goes by the gate in "Topic group chats"; a group message from someone who is not the owner is dropped unless "Group access for teammates" lets it through; up to here it's the hub; the owner's message is handed to the assistant, which de-dups again by message_id and stores it). Anything starting with `/` is first treated as a command (below); unknown commands are passed through as is (they may be the Agent's own, e.g. `/compact`); to a Persona conversation, a bare one that looks like a slipped bot command (a letter dropped or two adjacent letters swapped, e.g. `/stpo`, `/stp`) is not sent: the bot replies "Did you mean /stop?". With words after it (`/news 今天有什么新闻`), real words (`/news`, `/now`) and Claude Code / Codex commands (`/stats`) it goes on, and nothing to an Agent is held back. To send such a command itself, double the slash (`//stpo` sends `/stpo`); a doubled slash is only taken off before a bot command or a slip of one, outside an Agent, so other text starting with `//` (`// TODO`, `//example.com`) goes as written (#5005).
2. Target: if it's a reply to a message the bot sent (or in its thread), it goes to the chat / Agent bound to that message (`threads`, kept for 30 days, up to 500 entries, so replying to a card from several days ago still goes back to the original place, #4779); otherwise it goes to the current target (`current`: `main` / a Persona chat / an Agent).
3. Content: text (rich text converted to Markdown, @ mentions turned back into names); images (up to 4) as image attachments; files, voice, video and extra images are downloaded and stored via the node's
   `file.upload.*` in that computer's temp directory, with the path written into the message (a file over 50 MB is skipped: the rest of the message still goes, and a line says which file was too large, #4824); quoted messages and merged-forward chat histories (read out one per line) go into `<persona-context>`; images and files in quoted messages are handed over by the same rules (up to 4 together with the message's own images; if they can't be read, only the quoted text is included, without blocking the send, #4728). A private reply omits a parent marked deleted in the message readback, including its text and media, while the reply's own content and attachments continue normally;
   messages to Persona also get a note "the answer will be sent back to Lark; lead with the conclusion, don't use notify_user" (prompt `bot/message.md`).
4. Sending: Persona chats go through `session.send` (the main chat follows the launcher in **Settings › Assistant** just like the App; the assistant sends via the hub's `session.send_once`), with `client_msg_id` `feishu-<message_id>`,
   sharing the `sent_messages` de-dup with the App: redelivered events aren't sent twice. If there's no main chat yet, a new one is started and set as the main chat. The message gets an "OnIt" reaction.
5. Tracking the answer (the shared pipeline's run, stored in `channels.state`, so waiting resumes after the assistant or hub restarts; old versions' data in `bots.feishu.state` is moved over on first read): the assistant follows the chat the way the App does when it opens it (`session.follow`; the hub forwards new items and text being written).
   - Progress: about 1 second after the message is sent, a **progress card** is posted as a reply under the owner's message, without waiting to see the chat working: while the message hasn't shown up in the chat yet it says "Getting ready…"; while the chat is busy with another turn (this one queued behind it) it says "Queued…"; once the message is found it says "working", with the summary "Working · 3m 12s so far", and steps are counted only from this message on (the previous turn's steps aren't listed). The state is a coloured tag at the start of the card (working blue, queued or getting ready grey), followed by the label and the time taken. The card is a CardKit entity (`server/internal/modules/lark/stream.go`): made on the first tick with what the conversation is writing in an element of its own (up to 2,000 characters, its end), sent by its id (`feishu.card_create`, then `feishu.post` with `feishubot.CardEntityContent`), and written into from then on — the words streamed (`feishu.card_stream`), so they come in letter by letter, and the rest of the card (steps, counts, time, Stop) written whole when it changes (`feishu.card_update`), which CardKit takes as often as it comes while the card streams. CardKit turns streaming off ten minutes after it was turned on; it is turned on again for the next write (`feishu.card_settings`). CardKit goes on taking writes into a card whose message was withdrawn or deleted, so while the card is an entity its message is read back every 30 seconds (`feishu.messages`); one gone is forgotten with its entity, and the next tick posts a new card, as when a message update finds it gone. Any other failure sends the run back to updating the card as a message (`feishu.update_card`), which a card sent as an entity still takes; when CardKit will not make a card at all (the app lacks `cardkit:card:write`, an older hub) progress cards go as messages for ten minutes. The answer, a fold and a recall turn the streaming off first and write the card as a message, as before.
     The card shows, in order: "Now: Run `go test ./...` (40s so far)" (the latest tool call without a result yet and how long it has run; when several are running it adds "and N more"; once all have results this line is dropped);
     the last 5 steps (earlier ones as "…N earlier steps"); when subtasks (Task / Agent) were used, a "Subtasks" section, one line each with description, type and "running" / "done", up to 6, more as "and N more";
     small gray text "N tool calls · read X files · changed Y files" (counting distinct files, zeros omitted, "1000+" from 1000 up); and finally the text being written. These are recorded as new items arrive (`chanLive`), not rescanned, with a cap on entries; the turn after a background task reports back starts from zero.
     With new steps it's edited at most once every 3 seconds, and even without new steps it's edited every 3 seconds, so the elapsed time keeps moving and it never looks stuck. The answer is written into this card; when no native agent message carries the process, it goes into a collapsible panel "Called tools N times". Before a background task reports back (after one answer, while waiting on the background), no new card is sent; it's sent once that turn starts working.
     When editing, if the content is the same as last sent, nothing is sent; when Lark says edits are too frequent (230020, 99991400, HTTP 429), it pauses 5 seconds first, then 10 and 20 seconds on repeats, up to 30 seconds, and then sends the latest state; the answer isn't held back by that pause: its own last write into the card waits the card-update window out once when it is refused as too frequent (a finished run has no later update to write the card, so it would keep saying it is still working),
     if the card was recalled or deleted (230011, 230110), it forgets the card, the next refresh posts a new one, and the answer goes into the new card.
   - With `topic_cot` on, a topic run also gets an **agent message** (the Open Platform's `message_cot`) at its first thinking or tool event, including a quick turn that reaches its answer before the first progress refresh. It is created under the originating message with `origin_message_id` and `reply_in_thread`, in the same topic. Its collapsed process opens into thinking, one icon-and-subject row per tool (command, file path or query as available), and expandable output; a turn that finished closes it with `RUN_FINISHED` (other endings are below). A text-only turn creates none. The progress card keeps its own lifecycle beside it—elapsed time, current step, the answer and "Open web app"—and its updates do not wait for the native API.
     Topic native work is serialized outside the progress-card mutex, with one replaceable snapshot of the bounded item history. Ending the turn cancels in-flight progress and replaces pending work with a terminal snapshot; the answer uses the last confirmed native availability and never waits for native completion. Late results cannot update a removed run or a held run's next turn (#12574). A definite terminal refusal restores the folded process on the same delivered card; folding a live run leaves native completion to its worker alone. Native checkpoints keep the existing ordered channel-state storage path; its storage latency is separate from native network latency.
     Who gets an agent message: a topic when `topic_cot` is on, a private chat when `dm_cot` is on, and never a `/read` run or a proxy-reply handoff (those have no channel run). A text-only turn creates none in any mode and gets today's card. With the scope's switch off, a private run that already has an agent message from before keeps appending to it and finishes it, and the answer is sent as a separate card. A run stays on the path that opened its message: turning `dm_cot` off mid-turn does not hand a worker-owned message to the older cursor, which would append the same events twice. The hub's `feishu.cot_create` / `cot_append` / `cot_complete` call the API, and events are in AG-UI format (`feishubot/cot.go`).
     With `cot_answer` on as well, that turn sends no progress card and no answer card: the answer is written into the agent message (`TEXT_MESSAGE_*` before `RUN_FINISHED`) and the run is marked done. The card is held only while the agent message can still open (up to `cot_unified_grace`, 10 seconds, or until creation is refused); after that the turn is a card turn and stays one, so the answer is never sent twice. The answer goes into the message only when the turn finished normally, it is not quiet, it is not a `/read`, no progress card was posted, and the answer lays out as exactly one card. A longer answer, a table or a chart stays in cards. The message carries the card's text and the footer line, not the "Open web app" button. The answer waits up to `cot_answer_wait` (25 seconds) for that append to be confirmed. It counts as delivered only when every append through `RUN_FINISHED` returned without error; an append that got no reply is not counted, the agent message is closed with `cot_complete`, and the card goes out too, so the owner may see the answer twice and never loses it. The same card goes out when the wait runs out, and then the process panel is on the card. When the message is open but the answer was not confirmed, the card goes out without the process panel. Once the append is confirmed the run's Ext `cot_answer` is `1`, cleared with the other `cot_*` keys when a held run starts its next turn.
     If creation is refused (an older tenant or client without `message_cot`, or missing permission), the run is marked `cot_off` and today's card and collapsible process panel carry the turn, including the final answer. When an already-open agent message errors (#2807): rate limits, a busy service or no response from Lark (the hub records error code -1) only mean this attempt wasn't sent, and the next one continues; a batch that may already have arrived isn't resent; if the final append fails, the answer is still sent and the agent message is closed with `cot_complete` (its own 15-second deadline, up to 3 tries) rather than left spinning; tool calls already shown but without results are stored in the run's `cot_calls`, so they're still closed after the assistant restarts.
     How the agent message ends, for every worker-driven message (a topic and a private chat, unified or not): a turn that finished writes the pending events, settles open tool calls, sends `REASONING_END` and then `RUN_FINISHED`, and calls `cot_complete(done)` only when that append did not get through. A turn that was stopped, recalled or superseded by an unrelated message sends `REASONING_END` and then `cot_complete(done)`, not a `RUN_FINISHED` that would read as completed. A turn that failed, timed out, whose conversation is gone or whose computer went offline closes the same way with `cot_complete(error)`. The stop or error text is never put in the agent message; it goes out as today's end card. A private run still on the older path ends as before, with `RUN_FINISHED`.
   - When the turn ends (not working, no card waiting for you), it takes the answer **after this message** (every assistant text from the first on, in order, except a passing line of at most two sentences said right before a tool call: a report written before a tool call is part of it; `transcript.AnswerParts`) and writes it into the progress card
     (for an old private turn that still has an agent message: that gets closed, and the answer is sent as a separate card; a topic's answer stays in its progress card, unless `cot_answer` put it in the agent message), and the reaction changes to "DONE". The card has no buttons.
     If the turn stopped without saying anything (model service error, interrupted): the card says "This turn stopped without a text answer: <reason>"; the only reasons recognized are "API 错误：…" (API error) and "已中断" (interrupted) at the end of the turn (compaction notices after them are skipped; goals, background tasks, Codex events and command output don't count as reasons), squeezed into one line of at most 300 characters; for Codex it takes the session's `turn_error` (`channel.Stopped`, #3340); without a reason it's still "(No text answer this turn)".

Why: …" and logs it (#4588).

## Topic group chats

The bot's chat with the owner is the DM. A group chat is different: anyone in it can write to the bot, and the owner's Persona can reach all of the owner's data. So the bot listens to a group only where the owner has opted in, and then only to the owner, and only inside a topic (#5279: one topic per to-do, see `docs/assistant/todos.md` ("Replies in the thread")).

**Opting in.** The owner sends `/topics` (Chinese alias `/话题群`) in the group chat (only there: in the DM it is an ordinary message that goes to the assistant like any other); `/topics off` (or `/话题群 关`) takes the group out again. The hub checks the sender is the owner, and answers in the group with one line saying it is on / off / already on / was not on. From anyone else, or while the bot is not paired, the command is dropped without a word. It is the hub's own: it never goes to the assistant, and it takes effect before the next message is looked at (the message right after `/topics off` is not read, the one right after `/topics` is). The same list is the `topic_chats` setting: `PUT /api/v1/bots/feishu` takes `topic_chats: [{chat_id, name?, todo_mode?}]` (replaces the list; absent leaves it, `[]` empties it; a paired bot is needed; at most 50, ids not empty, no spaces, no repeats; the list is checked before anything of the request is applied, so a list sent together with a new App ID, which unpairs the owner, is a 400 and changes nothing: set the list in a request of its own) and `GET` returns it as `topic_chats: [{chat_id, name?, added_at, todo_mode}]`. It is kept in `bots.feishu` with the owner, so unpairing (or changing the App ID) empties it. Adding and removing a chat are audited (`bot_topic_chat_added`, `bot_topic_chat_removed`).

**Home topic group** (#6146). One of the groups on the list is the *home*: where a request from a group that is not on the list opens its topic ("Asking from any group" below; with no home group the request is taken in the DM instead). `/topics home` (Chinese alias `/话题群 主群`) in a group makes it the home, and turns it on if it was not (the owner said so in so many words); only one group is home at a time. With none marked, the first legacy enrollment is home. A strict enrollment is not an implicit home; with only strict groups and none explicitly marked, requests from elsewhere use the DM. Taking the home group out with `/topics off` takes the mark with it, and the first legacy enrollment left is home. `PUT /api/v1/bots/feishu` takes `home: true` on one entry of `topic_chats` (more than one is a 400; a list that says nothing about `home` leaves the mark where it is) and `GET` returns `home: true` on the group that is home now. `feishu.status` carries it as `home_chat`. Setting it is audited (`bot_topic_home`).

**Only respond when I mention the bot** (#10238). This per-group switch is off by default, visible under Settings › Connectors › Lark bot › Topic groups. Add a group there by its chat ID and optional name, select the policy before adding, or change the switch beside an enrolled group. The page shows the saved policy and effective home; **Home topic group** is a separate acknowledged save; **Use default home** clears the explicit choice and restores the legacy fallback (or the DM for isolated-only enrollments). Turning the switch off restores ordinary topic behavior without choosing a home. Strict enrollments retain an internal `explicit_home_only` marker, so later policy changes do not silently redirect requests from other groups. Tightening the policy of an existing legacy enrollment preserves its implicit home. Failed saves retain the previous policy and any enrollment input.

**To-dos in a topic group** (#11813). Set the mode for an enrolled group in Web Settings › Connectors › Lark bot › Topic groups.

| Setting | What happens in an unbound topic |
| --- | --- |
| **Answer only** (`answer_only`, default) | The main conversation answers the first message and later replies in that topic. |
| **Main conversation decides** (`main_decides`) | The main conversation answers in the topic and can link a to-do when the work needs an Agent or sustained follow-up. The bot confirms the creation in one line. |
| **Always open a to-do** (`always_todo`) | Starting a topic opens and links a to-do automatically. An unbound reply gets the opening hint. |

In all three modes, `/todo`, `/ai`, and explicit requests can open a to-do in an unbound topic. Existing bindings keep their reply routing. See `docs/assistant/todos.md` ("Opening a to-do from a topic") for the exact matching rule. The `todo_mode` field is saved with the group. An older client omitting it on an existing enrollment preserves its saved mode. Enrollments without a saved mode, including those made with `/topics`, use **Answer only**.

**Binding a topic group to a domain space** (#17117). An opted-in group in `topic_chats` can optionally carry `space`, the slug of an existing non-archived domain space with a directory (or `health`). Set or clear it through `PUT /api/v1/bots/feishu` (`topic_chats: [{chat_id, space?}]`; omitting `space` on an existing row preserves the saved binding, `""` clears it, and an unknown or archived space returns 400), or directly in the group with `/topics space <slug>` (Chinese alias `/话题群 空间 <slug>`) and `/topics space off` (`/话题群 空间 关`). `GET /api/v1/bots/feishu` returns `space` on bound rows, `feishu.status` carries the map as `topic_spaces`, and changes are audited as `bot_topic_space`.

When an unbound topic in a space-bound group receives a message (under `answer_only` or `main_decides`), Persona creates an isolated conversation in that space — inheriting its directory, `SPACE.md`, and space context — without creating a to-do or disturbing the main conversation. The `(chat_id, thread_id)` pair is persisted in `bots.feishu.state` (`topic_sessions`) so follow-up replies in the same topic route back to that conversation, while each new topic in the group gets its own space conversation. Explicit `/todo` or `/ai` commands still open a to-do on demand.

**Scheduled task thread delivery** (#17117). A scheduled task (`Task.delivery`) can specify `{channel: "feishu", chat_id, thread_id}` (see `docs/assistant/health.md` ("Tracks and kinds")). When a run completes, the bot posts the result directly into that opted-in group thread (`in_thread`, `no_detour`, without requiring private DM `pushes` to be enabled) and records the thread in `topic_sessions` for that execution conversation, so owner replies in the same Feishu thread continue the task's conversation directly.

`topic_chats` entries accept `require_owner_mention: true|false`; GET always returns its saved boolean. An older client omitting it on an existing row preserves the value. It is stored with the enrollment in `bots.feishu`. A failed durable list write rolls back the in-memory list and returns an error. The list still replaces enrollment as a whole, so clients should refresh before changing it.

For a strict group, before `/topics` commands, topic creation, assistant delivery, replies or reactions, require the paired owner's sender identity **and** a structured `mentions[].id.open_id` equal to the current bot's nonempty `botOpenID`. Display names, textual @s, @all, mentions of another user or bot, non-owner senders, and unknown bot identity do not qualify. This applies to roots and replies, including bound topics, rich text and attachment captions. Queued messages read the current policy when handled; redeliveries keep ordinary message-ID deduplication. Eligible input still needs the existing topic/thread conditions below. Card-button presses keep their existing owner checks; this switch governs inbound messages, not outgoing task updates.

Platform delivery and Persona triggering are separate. `im:message.group_at_msg:readonly` may limit what its scope delivers, but broader `im:message.group_msg` or `im:message.group_msg.include_bot:read` scopes can still deliver ordinary group messages through `im.message.receive_v1`. The subscription name alone is not a mention-only guarantee. The Persona gate applies even when broad delivery is enabled. Tests use synthetic events and a fake bot API; no live account or permission change is required.

**The gate.** A message from a group chat (`chat_type` other than `p2p`) is handed to the assistant only when all five hold, or when it is the owner's `@bot /ai …` from a group that is not on the list ("Asking from any group" below); otherwise it is dropped without a word: no reply, no "owner only" note, no reaction, nothing said in the group.

1. The bot is paired.
2. The sender is the owner.
3. The chat is on the owner's list.
4. The message is in a topic (it has a `thread_id`).
5. It is not the opt-in command above.

A group message never changes where the owner's pushes go: the DM's chat id (`owner.chat_id`) is only ever set by a message in the DM. The message is handed over without an owner action (it can answer no card). The assistant checks the sender again. A group `feishu.message` goes to `threadMessage`, which routes by topic and skips private-chat commands, card answers and the current target. The to-do bound to the message's topic takes it as a `source = "thread"` decision and its Agent (else the conversation that opened it, else the main chat) gets it; the answer, progress card and notes go back into the same topic with `chat_id` and `in_thread`, and so do the question, plan, permission and terminal-dialog cards of the run (a card whose run was asked in a topic is a reply to that message in the topic). A conversation that has both a private run and a topic's gets the card in the owner's DM, where only the owner sees it, and the topic gets one short line saying the card went there. A card the topic refuses outright (the hub's refusal, because the group was taken off the list; Feishu's "the bot is not in the chat" 230002 or "the chat was dissolved" 232009) goes to the DM as well; any other failure (a timeout, a gateway error) may have gone out, so it is only logged and the card is not sent again. Unbound topics go to the main conversation according to the mode above. A topic bound to a closed to-do gets a reminder to reopen it in the app. Details: `docs/assistant/todos.md` ("Replies in the thread").

### Asking from any group

(#6146) People who work with many groups do not want an AI conversation in each one. The owner writes `@bot /ai <what>` where the question comes up (optionally as a reply to someone's message, which is then the context); the work happens as a topic in the home topic group, and the outcome comes back as a reply to that message. Everything about the work stays in the topic; the original group sees an emoji on the message and, at the end, the outcome. It needs only `im:message.group_at_msg:readonly`. A topic group is not required: Lark is one channel of Persona, not its shape, so with no home topic group the work happens in the owner's private chat with the bot instead (see "No home topic group" below).

- **What the hub takes** from a group that is not on the list (`botAIElsewhere`, `extmgr/bots_topics.go`): the owner's message (a text or rich-text one, not a merged forward) that @-mentions the bot (told by its own open id) and whose words, the leading @ of the bot taken off, start with `/ai` as a word (`feishubot.AICommand`, also the full-width slash and any case; `/aim` is not it). Nothing else from such a group: someone else's `/ai`, the owner's ordinary message, an `/ai` without the @ all stay dropped without a word. What is taken is kept as a *source* (`ai_sources` in the bot's settings: chat and message id and how many replies it has had; the last 500, a source older than 90 days no longer counts, gone with the owner on unpairing), audited (`bot_ai_taken`, never the words), and handed over as `feishu.message` with `from: "elsewhere"` (no owner action), so the assistant can tell it from a topic's message. The group does not become one the bot reads, and a group message still never changes where the owner's pushes go.
- **What the bot may write there.** A reply from `feishu.text` must be under the original `/ai` message in its own chat (`aiSourceReply`). The short result has a 2000-character limit. An opt-in final answer is one literal rich-text reply, or one text attachment if it is too long for an inline post. The source allows two attempts, including failures. Both attempts keep the same delivery key. A withdrawn original prevents delivery. Other messages in the group and top-level sends remain outside this permission.
- **Opening** (assistant, `modules/lark/elsewhere.go`): `openFromElsewhere(src Source)` posts the topic's first message into the home group (a new message, so a new topic: "From another group chat: <what>", the replied-to text as a quoted line, clipped, only text, a merged forward not expanded, and a line saying `/noreply` stops the report back), reads its `thread_id` back, and from there does what a topic the owner started does (`docs/assistant/todos.md` ("Opening a to-do from a topic")): a to-do bound to the topic, handed to the main conversation, with the source recorded on it. The replied-to text is someone else's: it goes into the to-do's notes under a label that says so (and with nothing in it that closes a context block), and to the main conversation as a block of its own, escaped like any quoted text, titled as a message written by someone else, background only (`prompts/todo/thread_open.md`); the user's own words stay in the quotation above it. On success the original message gets an emoji (`OnIt`) and nothing is said in its group. Nothing is posted if there is no one to take the to-do (main conversation missing or off). A bare `/ai` gets a line asking for the words, under the message; any other failure is told under the message, with its reason.
- **No home topic group** (none on the list): the request is taken all the same, in the owner's private chat with the bot, the one place the bot always may write (`openInOwnerChat`). The first message is the same line, posted to the DM; the to-do is made as for a topic (supervised, handed to the main conversation, the run answering as a reply under that first message) but is bound to **no topic**, and its `source` carries that first message as its `anchor` (`docs/assistant/todos.md` ("Where it came from")). The original message gets the same emoji, and the group is told nothing. With a home group nothing differs from the above: it is never bypassed, and a home group that fails to give the message a topic is still a failure under the message, not a fall-back to the DM. The notice before the report goes into the DM as a reply under the first message, and `/noreply` is said by replying to that first message, to the notice, or to an answer under it (a `/noreply` that replies to none of them is an ordinary message to the conversation the chat is talking to). A to-do with no topic gets no lines in a topic, since it has none; its question and permission cards come as for any run in the DM.
- **Reporting back.** Web Settings › Connectors › Lark Bot previews a short result for ten minutes by default. **Reply timing for the original group** sets the preview window for new replies. Choose **Immediately** to send as soon as the result is ready or choose **10 min** to restore the default. **Reply with the complete final answer** lets the original group see the task's full answer, including its paragraphs and links. Anyone in that group can read it. Turn it off to return to short results and stop pending full answers from being sent while it is off. With a positive wait, the owner can cancel by sending `/noreply` in the preview's topic or replying to the preview in the private chat. Details: [Where it came from](../assistant/todos.md#where-it-came-from).
- **Later channels.** `openFromElsewhere` takes a `Source` (channel, chat and message of the request, the words, the quoted text) and does not care who received the request: the bot's gate is the first caller. A channel that sees the owner's own chats as the owner (an extension; the bot is usually not a member of those chats) can hand the same `Source` over the bus once a bus method for it exists, and tell the outcome back itself: a channel is added to `sourceChannels` and to `sendSourceReport` in `assistant/todo_source.go`, and until then a request from it is refused when it comes, so that no to-do is opened that cannot answer.

### Reading a group with /read

(#11803) Alert and problem groups are where questions come up, and the question is usually about what was said there: an alert's cards, someone's screenshot, a log file. `/read` brings that history in. With `read_group` on, the owner writes `@bot /read <task>` (Chinese alias `/读群`; a full-width slash and any case count) in any group the bot is in, opted in or not, in a topic or not. The main chat reads the group as the owner, downloads its images and files and does the task with them. The answer comes to the owner's DM first, and goes under that message (in its topic when it was asked in one) only when the owner presses **Post to group** (#14437, "The owner looks first" below); with `read_group_direct` on it goes there straight away. Unlike `/ai`, the work does not move to the home topic group: the point is to answer in the group, on the spot, once the owner is happy with it.

- **What the hub takes** (`botReadGroup`, `extmgr/bots_read.go`): with the switch on, the owner's message (text or rich text, not a merged forward) that @-mentions the bot (told by its own open id) and whose words, the bot's leading @ taken off, start with `/read` or `/读群` as a word (`feishubot.ReadCommand`; `/reader` is not it). It is checked after the group's own "Only respond when I mention the bot" policy and `/topics`, and before the topic rules. It is kept as a source of kind `read` (`ai_sources`, as for `/ai`), audited as `bot_read_taken` (the chat, never the words), and handed over as `feishu.message` with `from: "read"`. Anyone else's `/read`, one without the bot's @, and anything with the switch off stay where they were: dropped without a word in a group that is not opted in, an ordinary topic message in an opted-in one.
- **Reading as the owner, not as the bot.** The bot gets no way to read a group's history and needs no new permission (reading every message of a group is a sensitive scope that needs the admin's review). The hub hands over the chat id, the message id, the topic's thread id and the words; the assistant (`feishuRead`, `modules/lark/read.go`) sends the main chat a request (`prompts/bot/read_group.md`) to read the group with `lark-cli` as the owner on its own computer, who is in the group by definition. Reading marks nothing as read.
- **What is read, and the limits.** With no range in the task: the last **40** messages, other members' and bots' included (`im +chat-messages-list --page-size 40 --no-reactions`), and the topic's replies when it was asked in one (`im +threads-messages-list`). A range in the task ("the last two days", "read everything", "only what X said") is turned into the command's options by the model; no parser is involved. Any range stops at **500** messages, and the answer says how many were read and from when. The listing downloads nothing: `--download-resources` would fetch every image and file whatever its size. The list shows an image as `[Image: img_…]` and a file as `<file key="file_…" name="…"/>` (a bare `[Image]` has no key: Lark returns an empty one, and nobody can fetch it); the model then downloads only what it needs, one at a time, into a directory of its own on the main chat's computer, `~/.persona/lark-read/<message id>/lark-im-resources/` (`im +messages-resources-download --output lark-im-resources/<key>`). Neither the list nor the raw message API carries a file's size (checked against lark-cli 1.0.91), so the limits are applied after each download from its `data.size_bytes`: a file over **50 MB** (the bot's own limit for a file it passes on) is deleted unread, and the one that takes the total past **200 MB** is deleted and downloading stops. That bounds what is kept and read, not what one download may transfer. It looks at up to **20** images itself and reads files by type. Without lark-cli (not installed, not signed in, a scope missing) it reads at least the text with the `larkcli_messages` tool and says what it could not read.
- **The Lark gate.** Listing is a read. `lark-cli` rates `im +messages-resources-download` `Risk: write`: it changes nothing on Lark, but it writes a local file, overwrites one that is there and takes a dotfile name, and without `--output` the file is named by whoever sent it. The node's gate treats it as a read only when it can prove from the words that the file lands in `lark-im-resources/` (`larkCLILocalDownloads`, `larkCLISafeDownload`, `node/larkcligate.go`): every flag is one the command's `--help` lists (lark-cli 1.0.91), there is an `--output`, and every `--output`, not only the last one pflag keeps, names a plain file there. Anything else asks: no `--output`, a dotfile, another directory, `..`, a flag the list does not name (`-o` in any spelling, which the command does not have today but a later version might, a shorthand cluster, `--`, a stray argument) and a high-risk rating. So does a subshell (`( cd … && lark-cli … )`), which the gate cannot see into: the request uses `cd <dir> && lark-cli …`. Neither the default read nor the downloads it asks for raise a card.
- **Quiet in the group.** The message gets `OnIt` when it is taken and `DONE` at the end; no progress card, agent message or "working" line goes into the group. Once posted, the answer is cards under the message (`feishu.post` with the message as `reply_to`, at most 8 replies for one source, never a detour into the group if the message is gone; each card under a key of its own for the turn, `readAnswerKey`, so an answer tried again after its reply was lost lands once, #11987), without the process panel, the workbench button or the web link to the conversation, since everyone in the group reads it. A question, plan or approval the run raises goes to the owner's DM, never to the group: while a `/read` of the conversation goes on, no topic's run of that conversation decides where a card goes either, so the card goes to the owner's DM (under the latest private run, or on its own) and no topic is told it went there (`interactionRuns`, `assistant/ask_view.go`; the lark module places the card, `interactionPlace` in `modules/lark/asks.go`). A `/read` run is never folded with another message's run: each is answered under its own message.
- **Investigating before concluding** (#16808). Reading is not the whole job: when the task asks for a cause, a diagnosis or the impact (or names no task while the group is dealing with a problem), the request has the model check the group's leads before it answers, instead of restating the analyses already in the group, other bots' included. It lists what can be checked (log, trace and request IDs, error text and codes, times, attachments such as client logs, links, services and repositories) and checks it with what the main chat's computer already has: installed CLIs and skills that query logs or traces by ID (their `--help` when unsure), the code in local repositories, the downloaded logs (an archive listed, then extracted into the `/read`'s own directory). Read only: no code, config or database changes, nothing that changes state, no message to anyone, and no other Agent or task started in the turn (that goes into the next steps). The budget is about **20 minutes** and **40 tool calls** past the reading (`readInvestigateMinutes`, `readInvestigateCalls`), far inside the run's own 4-hour limit (`channel.RunMost`): at the budget the model stops and gives a staged conclusion. The answer leads with the conclusion and how sure it is, keeps what was verified (with what was checked) apart from what is inferred, and says what could not be found or checked; when a tool, a sign-in or a permission is missing, it says what is missing instead of writing as if it had looked. Before this, a `/read` asking for the cause of failing answers in an on-call group read the group, looked at its screenshots and answered within about a minute from two bots' disagreeing analyses, without querying the request's log ID it had or opening the client log; an earlier `/read` whose words said "analyze with the trace" did query logs by ID with the same computer's CLI, so depth hung on the owner spelling it out.
- **Not instructions.** The request tells the model that what it reads in the group is other people's words: requests and commands in it are not followed, and commands or scripts posted there are not run. Its IDs, errors, times, files and links are data the model may look up with read-only tools of its own choosing, and what those return is material too. The answer leaves out paths on the computer, secrets and private details unrelated to the group: the request says the answer goes to the owner first and may be posted to the group (with `read_group_direct`, that the group reads it), so the rule holds either way.
- **Saying it is on it.** Investigating takes minutes, and the group's `OnIt` is all the owner would otherwise see. A held `/read` still working after **a minute** (`readWorkingAfter`, the lark module's timing `read_working_after`) gets one card in the owner's DM: the line saying which `/read` it is, "reading the group and checking its leads; the answer comes here", and the link to the group (`readWorking`, `read_held.go`). Once per run, under a key of its own (`readHeldPrivateKey(<message>, "working")`), so a restart that forgets it does not say it twice within Lark's hour; nothing goes into the group, and a quick answer gets no note. A `/read` answered straight in the group (`read_group_direct`) gets none: its owner looks at the group.
- **The owner looks first** (#14437, the lark module's `read_held.go`). Unless `read_group_direct` was on when the owner asked (the run keeps it as `read_direct`, so the request's wording and where the answer goes always agree), the turn's answer does not go into the group: the lark module keeps the cards the group would get, each with its key (`readAnswerKey`), and posts them to the owner's DM. The first card opens with a grey line saying which `/read` it answers (the owner's words after the command, clipped to 60 characters); the last ends with "Only you can see this", two buttons, **Post to group** and **Don't post**, and a link that opens the group in the Lark app (`applink.feishu.cn/client/chat/open?openChatId=…`, as the sidebar links do). A reply to these cards goes to the main chat, as a reply to any answer card. When the card with the buttons cannot be posted, the buttons come on a card of their own. A run that ended with nothing to say gets its ending line in the DM, with no buttons. Nothing is said in the group meanwhile: what keeps a `/read` from starting (the main chat switched off, a send that failed) is said in the DM too.
  - **Post to group** (the card action `{"a":"rd","do":"post","id":…}`, the same `card.action.trigger` path as every card: only the owner's press in the owner's DM counts, checked by the hub) posts those same cards under the `/read` message, through the source rules below (its chat only, its 8 replies, `no_detour`), each under its group key. Each card that goes is recorded at once, so a press again, Lark's redelivery of a press, or a press after a restart posts nothing twice; a press meanwhile is told it is under way. An answer of several cards goes out on one press, in order. The card then says "Posted to the group". Lark waits 3 seconds for the press: a post that takes longer answers "Posting to the group…" and edits the card when it is done.
  - **Don't post** turns the card into "Not posted to the group"; it can no longer be posted. With no press nothing is ever posted: nothing goes on a timer.
  - **When it cannot go.** A post the hub refuses (the source expired or used up its replies: `chat_denied`) or one whose message was recalled or deleted (Lark's 230011 / 230110, `no_detour` keeps it out of the group) settles the card as "Not posted to the group: <why>" (or how many cards went, when some did), and nothing goes into the group as a message of its own. A post that did not reach Lark, or that Lark slowed down, leaves the buttons and says to press again: the try goes under the same keys, so a card Lark took but whose receipt was lost lands once (Lark keeps a key for an hour). With `read_group` switched off since, a press posts nothing and the buttons stay.
  - **How long.** The hub keeps a `/read` source 90 days (`botAISourcesKeepFor`), so a press days later still goes. The held answers are kept in their own setting, `bots.feishu.read_held`, apart from the chat's state (written on every message): at most 30, each for 14 days (about as long as Lark lets the bot edit the card), the cards only while the answer waits. A press on one past that says it is too old to post. An answer that cannot be kept (the store refused it) is not posted anywhere: the run keeps it and tries again, as an answer the hub could not take.
  - **The default changed.** `/read` shipped on 2026-11-20 answering straight in the group; since #14437 it answers in the DM first for everyone, settings saved before included. **Answer /read in the group directly** (`read_group_direct`) brings the old behaviour back.

**What the bot may write there.** Under the `/read` message, in its own chat, cards (`feishu.post`) and short lines (`feishu.text`, at most 2000 characters, no full answer), 8 in all; a send into the group, a reply under any other message, a reply naming another chat are refused (`readSourceReply`, `extmgr/bots_read.go`). An `/ai` source keeps its own rule (one text line, two tries).

**Turning it on.** Settings › Connectors › Lark bot › **Read the group with /read**; under it, **Answer /read in the group directly** skips the DM. The bot needs nothing beyond what `/ai` needs: `im:message.group_at_msg:readonly` (or `im:message.group_msg`) to receive the @ in a group, and the scopes it already has for answering and reacting in the DM; the reading needs `lark-cli` signed in as the owner on the main chat's computer with `im:message.group_msg:get_as_user` and `im:message:readonly` (`lark-cli auth status` lists them). Nothing on the Open Platform changes for the bot.

**Risk: a group on the list is a group the bot acts in.** Once a group is on the list, every topic the owner starts there opens a to-do and wakes the main chat, so a group used as a notebook gets a to-do per topic. And a group another bot already works in (an auto-starting bot, for instance) is answered twice, once by each bot. Put only groups meant for this bot on the list.

**What the bot says in a topic** (#5279, step 4). A to-do bound to a topic tells it about new decisions, its Agent finishing a turn or needing the user, and the to-do being accepted or closed: one short line with a link to the to-do, at most one a minute per to-do (several things of the same minute are one line; each line under a key of its own, so two that read the same both arrive). It goes out as `feishu.text` with `chat_id` and `in_thread: true`, a reply to the latest message the owner said in the topic, and only when the chat is one the bot may send into: `feishu.status` carries it as `chats` (the owner's DM and the opted-in groups, the same rule `feishu.post` / `feishu.text` are held to), so a `chat_id` an Agent put into a binding is never written to. The bot's own line is not a reply: it comes with a sender that is not a user and is dropped at the gate (condition 2 holds for users only). The DM's reports and pushes are not changed. Details: `docs/assistant/todos.md` ("Posting into the thread").

**Safety limits.**

- Only the owner counts. What anyone else writes in the group is never handed over, whatever it says; people in the group cannot drive the owner's Persona.
- Nothing others said is read in: a quoted message and a merged forward are not expanded for a topic message (the owner may quote someone else's text, which would carry it in).
- A card button pressed in a group counts only from the owner (the same check as in the DM) and only when the press names a chat that is the DM or on the list: a card left in a group that was switched off is dead (the toast says the chat is not turned on). The Stop button of a topic's progress card works the same way.
- A recall cancels an owner's message still queued at the hub before it reaches the assistant. After handoff begins, the recall is passed to the assistant. In an opted-in group, the hub requires a known owner message in that exact chat and bot identity, because the event does not say whose message it was; current topic receive policies still apply. Pending redeliveries keep their original cancellation even when recent-id history rolls over; completed messages use bounded recent history, with locally canceled sources kept distinct from handed messages so a wrong-chat recall cannot use the unknown-DM fallback. Events from a replaced connection, or with a conflicting envelope App ID, are ignored.
- The bot sends into the DM and the opted-in groups only (see "Sending" above), and, in a group that is not opted in, one text reply under a message the owner's `/ai` was taken from ("Asking from any group"), or the answer under a message the owner's `/read` was taken from ("Reading a group with /read").
- `/read` reads what others said in a group into the main chat, as the owner and only on the owner's own request; it is handed over as other people's words, not instructions.
- The group should still be one the owner trusts: anyone in it sees what the bot posts there (answers, progress, cards).

The progress card's **Stop** acts only while its actual message is the current watched Feishu run's progress card for that exact machine and conversation. An older card left behind by a refused final edit, or a card whose run is finishing, awaiting answer delivery, recalled or replaced, returns the existing expired-card notice without interrupting later work. Concurrent redeliveries of a successfully stopped current card send one interrupt; a failed interrupt can be retried. A restored current run regains this control after its watcher resumes. Typed `/stop` keeps its conversation-level behavior described below. These are assistant-side ownership checks; the node interrupt RPC still targets a conversation and does not atomically compare a turn generation.

**Open Platform permissions.** Receiving a group's messages needs one of two permissions; the code does not tell them apart:

- `im:message.group_at_msg:readonly`: only messages that @ the bot arrive, so every message to Persona in the topic has to @ it. No special review is usually needed.
- `im:message.group_msg`: every message in the group arrives, no @ needed. It is a sensitive permission and usually needs the enterprise admin's review.

Subscribe to **Receive message v2.0** (`im.message.receive_v1`) as for the DM; the bot has to be in the group. A leading @ of the bot is stripped when reading `/topics`.

## Proxy replies handed off from a group

An authorized extension, or the owner from their own app, can hand the bot a question a teammate asked in a group the bot is in. The bot answers in that group. The question never enters the owner's conversations: the assistant runs it as a guest conversation with a single tool, `bot_group_reply`, and that tool is also how the answer reaches the bot (`server/internal/modules/lark/handoff.go`). Nothing about the handoff makes the chat one the bot may send into (`botChatAllowed` is unchanged), so a card, a progress note, an agent message or a plain `feishu.text` into it is refused as ever.

**The two routes.** Both are the manager's, relayed by the hub like the other `/api/v1/bots/` routes, and each needs its own scope (`docs/extensions/extensions.md`).

- `GET /api/v1/bots/feishu/identity` (scope `bots.feishu.identity`) answers `{enabled, paired, ready, app_id?, bot_open_id?, bot_name?, domain?, capabilities}`. `ready` means the bot can send now. Unknown values are left out; `capabilities` is what this build supports (`["proxy_reply"]`), not the owner's policy. The body never carries a secret, a pairing or registration code, or the owner's identity.
- `POST /api/v1/bots/feishu/handoffs` (scope `bots.feishu.handoff`, or full credentials) takes `{chat_id, message_id?, in_thread?, ref?, chat_name?, sender_name?, question, context?}`. `chat_id` is required (1 to 100 characters, no whitespace). `message_id` is an optional anchor the bot can read, and the hub refuses it unless the message is in `chat_id`; absent, the bot posts one new message into the chat. `in_thread` needs an anchor. `ref` (optional, at most 120 characters of letters, digits and `:._-`, scoped to the caller) makes a repeat of the same payload return the first handoff with `replayed: true`, and a different payload under the same ref a 409 `handoff_conflict`. `chat_name` and `sender_name` are clipped to 80 characters, one line, with terminal escapes stripped. `question` is required and at most 2000 characters; `context` at most 6000. The body is at most 64 KiB. The call answers once the assistant has accepted: `{handoff: {id, state: "accepted", delivery, expires_at}, replayed}`. `delivery` is `confirm` or `direct`. There is no status route.

**Errors.** Every body is `{error, code}` with a message from the `hub-bots` catalog.

| Status | `code` | When |
| --- | --- | --- |
| 400 | `invalid_handoff` | Bad JSON, a field outside its rule, or an anchor that is not in `chat_id` |
| 403 | `handoff_off` | The owner switched proxy replies off |
| 403 | `chat_blocked` | `chat_id` is on the blocklist, which always wins |
| 403 | `permission_denied` | The scope was not granted, or the caller is an answer-only device |
| 409 | `bot_off` | The bot is off, unpaired, or not connected |
| 409 | `handoff_conflict` | `ref` reused with another payload |
| 429 | `handoff_rate_limited` | The per-chat or daily cap, or too many running; `Retry-After` is set |
| 503 | `assistant_unavailable` | The assistant is away, does not know `feishu.handoff`, or the settings could not be read |

A hub from before this change answers 404, which a caller treats as "not available". `chat_blocked`, `handoff_off`, `bot_off` and 429 are not retried; a 503 is retried once with the same `ref`.

**Policy.** Kept under `handoff` in `bots.feishu` and set with `PUT /api/v1/bots/feishu` (no client draws it). A chat on `blocked_chats`, or on `group_access.blocked_chats` ("Group access for teammates"), is refused (`chat_blocked`) and that always wins; `off: true` refuses every handoff (`handoff_off`); a chat on `direct_chats` is answered without asking; every other chat needs the owner's confirmation. The default, when `handoff` was never set, confirms every chat, so an install that never receives a handoff changes nothing. Unpairing or changing the App ID clears the policy. `launcher` names the launcher of the guest run (empty uses the assistant's default; guest runs are Claude Code only).

**Confirm and direct.** In direct mode the guest's one reply is posted at once. In confirm mode the draft is held and the owner is asked with the ordinary decision card (Needs you, a push, every client): one option posts exactly the stored draft, the other drops it. A typed answer or any other option drops it too, and it is never taken by default. The draft is at most 400 characters; a direct reply may be 2000.

**What is posted.** Plain text, in the owner's language: a header naming who asked and the question (clipped), the answer, and a footer saying it is an AI reply for reference. With an anchor it is a reply under that message (in its thread when `in_thread` was set) and is lost if the message is gone, never sent into the chat instead. Without an anchor it is one new message in the chat. At most one message lands: a repeat carries the same idempotency key.

**Limits and audit.** Six handoffs an hour per chat, sixty a day, three running at once; a handoff nobody finished is dropped after six hours. The audit records the policy change, a handoff taken, one refused, one posted and one ended, with the chat id and the handoff id only. The question, the context, the draft, the reply and the caller's names are never stored and never audited.

**Known limitations.** Without an anchor, a topic group gets the reply as a new topic. The chat and sender names in the confirmation come from the caller; only `chat_id` is checked against the owner's lists. The confirmation shows the draft on one line. A live process bubble in the group (a native agent message) is not part of this: the default is to ask the owner before anything is posted.


## Group access for teammates

A teammate in a group can ask the bot a question and get one answer, without ever reaching the owner's conversations. It is off until the owner turns it on (`server/internal/extmgr/bots_group_access.go`, `bots_guest.go`).

**What triggers it.** A message in a group, from a sender whose `sender_type` is `user` and who is not the owner, that carries a structured mention of the bot in `mentions[]`. Text that only looks like a mention does not count, and a message that starts with `/` is a command, which stays the owner's. The hub lets the next message through before it does anything with this one, so a stranger cannot slow the owner's messages down.

**Modes.** `owner_only` (the default, and what every existing install keeps: nothing changes), `allowlist` (only the listed people, and only in the listed chats) and `everyone_in_allowed_chats` (anyone in the listed chats). The first match wins:

| Check, in order | Result |
| --- | --- |
| The sender is on `blocked_users` | refused, `blocked_user` |
| The chat is on `blocked_chats` | refused, `blocked_chat`; this also silences the owner's own messages in that chat, and a proxy reply into it |
| The mode is `owner_only`, or there is no policy | refused, `owner_only` |
| The chat is not on `allowed_chats` | refused, `chat_not_allowed` |
| The mode is `allowlist` and the sender is not on `allowed_users` | refused, `user_not_allowed` |
| Otherwise | the guest answers |

**The guest.** The assistant runs the question as a guest conversation of its own (`bot_group`, `docs/assistant/assistant.md` "Guest conversations"), one per chat and thread, kept apart from the owner's chats. It lists only `bot_group_reply` and the connector tools the owner named in `guest_tools` (read-only connector tools, at most 8; a name that fails the guest check is dropped, never added). It gets no snapshot, no memory, no skills and none of the owner's files, and it never runs on a work machine. A follow-up in the same thread continues the same conversation; a thread nobody finished is dropped.

**What is posted.** One plain-text reply, anchored under the message that triggered it, in the owner's language, through `feishu.text` with the turn's id so a retry lands once. Paths and private hub links in the answer are replaced before it goes out. While the guest works, the group sees a guest chain of thought whose tool titles are sanitized the same way; the owner's own progress card is never used.

**Limits.** A question is at most 2000 characters. Each sender gets 10 questions an hour, each chat 20 an hour (the owner sets another number with `per_chat_hourly`), and the bot 200 a day, with at most 3 running at once. Past a limit the chat gets one short note, and at most one every ten minutes. The last 20 refused @-mentions are remembered, in memory only, so the settings page can offer to allow or block that person.

**Audit.** The audit records the policy change (`bot_group_policy`), a guest triggered, one refused, one posted and one ended, with the chat id and the guest id only. The question and the answer are never stored and never audited.

**What stays the owner's.** Cards, approvals, commands (`/topics`, `/ai`, `/read`, `/stop` and the rest), the private chat, pushes and the workbench are unchanged: a guest cannot reach any of them, and a teammate's tap on a card left in the group does nothing.

**Known limitations.** The reply is one text message; a topic group gets it as a reply in the triggering topic, and a thread the platform does not anchor falls back to the chat. A node too old for guest conversations refuses the start, and the turn ends quietly. A work machine never hosts the guest, so a hub whose only machine is a work machine answers no guest.

## Commands

`/help`, `/main`, `/new [first message]`, `/list`, `/agents [keyword]`, `/start [what it should do]` (a form to pick a machine and fill in a directory), `/stop` (Chinese aliases `/停止`, `/停`; interrupts the turn: sent in a message's thread / as a reply to it, it interrupts the chat or Agent bound to that message, otherwise the current target; a conversation whose last turn already ended gets "nothing is running" and no interrupt, while one this chat just sent a message into is stopped even when it does not read as working yet, #3793), `/status` (picks the target the same way from the reply / thread binding: who messages go to now, how many answers are pending), `/tasks` (aliases `/进展`, `/总览`; a snapshot of what waits for your decision and the open to-dos, or with `board` on, the standing board below). With `workbench` on: `/home` (aliases `/工作台`, `/主页`), `/today` (`/今日`, `/今天`) and `/inbox` (`/收件箱`); with it off they go on as text, as any command the bot does not know.

`/modellist` lists the models available from the main chat's current launcher; `/modelchange <model ID>` selects one of those IDs for the main chat. An unknown ID is refused. Wait for the confirmation before sending the next message. The selection is kept with the main conversation and applies to its next message; it does not change the Main chat default in Model Settings. These commands work when the bot is targeting the main chat; switch back with `/main` first if it is driving another Persona chat or an Agent. See `docs/assistant/model-config.md` ("A conversation's own model") for how the selection is stored and applied.

A newline, Tab or full-width space after the command name all count as separators, and a leading full-width slash `／` counts as `/`; content after `/new` is passed through as is, multiple lines included (#3897).

In the owner's private chat, `/new <first message>` explicitly starts a fresh Persona conversation even when replying to an older bot card or its thread. The first message does not answer that card's pending question, approval or verification; the original reply still supplies quoted context. Bare `/new` only confirms that the next unbound private message will start a conversation; ordinary replies still follow their existing card or thread binding.

## Cards

- **How they look** (`botcard/card_kit.go`). The header's colour is the card's state, changed in place as it changes: orange, the owner is to act (a question, an approval, a plan, a check, a decision); red, urgent or failed (an agent cut off, a stuck goal); blue, under way or only to know (progress, a push, a report); green, done; grey, over (an answered question, a sent draft, a passed check). The title says the matter in one line — for what an agent asks, the conversation's title, with the computer as the subtitle (then the CLI title, when the agent goes by its herdr tab name) and the kind (Question, Plan, Approval, Terminal, Authorize; Report, Conclusion, To check; Notice, To-do) as a tag on the right; no emoji in titles or buttons. The body opens with the point, then a line of small grey facts, the details folded (a finished agent's long result, the answer's process). Actions are one row: one primary (the option the asker recommends, Allow, Approve & run, AI draft, Take the recommendation), at most two more, and a **⋯ "more" menu** (`overflow`) for the rest — dismissing, the conversation's page, a decision's other options and fixed answers, muting a sender. A menu entry calls back with the menu's value and its own (sent as the option, `k=v&…`, and merged back when the press is read: `CardAction.UnmarshalJSON`), or opens its link (that press is `{"a": "nop"}`). What cannot be taken back asks first in Lark's own dialog (`confirm`): approving a plan to run on its own, allowing a call for the session, sending a draft as the owner. Lists are rows pressed whole (`interactive_container`: the agents, what waits on the home card) rather than a button per row, except the conversations list, whose rows keep their own web links. Once over, a card is grey and small: what it asked in a grey line, how it ended, the conversation's page as a link in its small print, no buttons.
- Cards use JSON 2.0 (`schema: "2.0"`): Markdown supports headings, tables and code blocks, so model answers display as written (1.0 doesn't support headings and tables). Needs Lark 7.20 or later; old clients show only the title and an upgrade notice.
  2.0 pitfalls: there's no `action` module, so lay buttons out horizontally with `column_set` (`flex_mode: flow` wraps automatically on narrow screens); `note` is gone, use `div` + `text_size: notation` + `text_color: grey`;
  button callbacks go in `behaviors: [{type: callback, value}]`; a submit button in a form needs `form_action_type: submit` and a `name` unique within the card; **one unknown extra field rejects the whole card**;
  a new card returned from a callback must also be 2.0.
- `<` in text outside code is turned into `&#60;` (cards swallow things like `<at>` and `<font>` as their own tags); data such as names and titles goes through `EscapeMarkdown`.
  The exception is autolinks the model writes, `<https://…>` and `<mailto:…>` (CommonMark): cards don't recognize them, and escaped they become unclickable text, so they're first rewritten as `[url](url)` (#4727). `(` `)` in the URL and `[` `]` after the hostname are percent-encoded, and `_` `*` `[` `]` in the link text become entities; other schemes (`javascript:` etc.), `\<` and anything in code stay as they are. Test: `go test ./internal/modules/lark/feishubot -run CardMarkdownAutolinks`.
- `persona-card` (chart cards, #886) in assistant answers can't be drawn by Lark, so they're written out as numbers before sending (`PersonaCards` in `botcard/personacard.go`; it's the first step of `CardMarkdown`, so all text sent through `CardMarkdown` gets this, not just the health space; text a client draws as Markdown is converted before it is clipped as well, since `clipMarkdown` flattens a chart to its title on its own (`PersonaCards` first in the briefing card and in the task report card, #3818 / #4093); the bot's answer is converted as a whole before being cut into cards (`answerCards` in `modules/lark/answer.go`), otherwise a chart longer than one card would be cut off and unreadable, leaving an empty card):
  `stat` becomes one line (`Steps today: **8,432 steps** · +12% vs yesterday`); `line` / `bar` become the title plus a ▁…█ sparkline, with the numbers on the next line one by one (at most the latest 31) and the unit written once; `stacked_bar` and `ring` become a small two-column table (a `ring` whose `total` is more than its parts ends with a "剩余" row) with the total in the header, and beyond 31 rows the rest are combined into one "Other" row.
  Numbers are formatted the same as on every client (`wire.Number`), and text the model wrote always goes through `EscapeMarkdown`; cards that no client can draw keep only the title; a `persona-view` card (the assistant's cards are always on, #5509) is written as its text `fallback`, never its JSON or HTML; other code blocks and example cards inside code blocks are left alone. In chat list summaries, cards show only their title. Tests: `go test ./internal/botcard -run PersonaCards`, `go test ./internal/assistant -run TestAnswerCardsWriteChartsAsNumbersBeforeCutting`.
- Link buttons only use http(s) (the docs only mention http(s) and AppLink; `persona://` may get the whole card rejected); "Open on web" opens the matching session page in the web version the hub hosts. A card's links are one row at its end (`Card.Link`, `AppendToLinks`): three as buttons, past that two and a "more" menu with the rest, each address once; the answer's links, its open button and a push's to-do button share it. A button says what it opens, never the address: a link the answer wrote with words keeps them; a bare address is named by `linkNamer` — a page of the hub's web app by the page ("Open the conversation", "Open the to-do", "Open the Inbox", "Open the knowledge base", "Open in the web app"), a Feishu document as one, any other site as "Open <site>". The web app's own pages open in Lark's half-width sidebar on the desktop (`PageBtn`, an applink `https://applink.feishu.cn/client/web_url/open?mode=sidebar-semi&url=…`, Lark 3.41 and later) and as any link on the phone.
- The options on interactive cards match the App's cards:
  - Questions: a single question with at most 4 options and single choice is a row of buttons + a "Write your own answer" input; anything else is a form (one dropdown per question, a multi-select dropdown for multiple choice, plus an input), submitted at once.
  - Plans: the full text (up to 5000 characters), "Approve & run" (bypassPermissions) / "Auto-accept edits" (acceptEdits) / write feedback and "Send back".
  - Permissions: tool, reason, command or arguments; "Allow" / "Deny", plus "Always allow" for this session on Claude's card when there is a session. Another agent's card only gets the button that agent names itself (`always_label`, e.g. 本会话不再问这个命令): as in the App, a runtime can't keep Claude's session rule, so the button would only allow once. **Anything that must be filled in on the phone (passwords, authorization codes, `fields`) can't be approved in Lark**; only "Open on web" is offered.
  - An MCP server needs your authorization or a form (`elicitation`): the card says what it wants to do (`message`); link authorization gets an "Authorize" button (only http(s) links without username / password, opened as is; the card has a separate line "Opens: <site>", and after authorizing you go back to the App and confirm); forms only list the names of the fields to fill, which you fill in the App (values may be passwords, which Lark doesn't take), #4234.
  - Terminal dialogs: when the options can be read, one button per option; when not, Enter / Esc / 1 / 2 and an input; ones that need a password (`secret`) can't be typed in Lark. A supervised terminal question goes to the task's supervisor first. If the supervisor escalates, the Lark card names the direction, task, agent and computer, with the question and its choices. An ordinary agent's dialog still goes directly to its existing destination.
- Wherever it's answered (Lark, the App, the watch, a notification button, the computer), the Lark card changes to "✓ Answered: …"; recalled / expired ones change to "Ended". Cards posted before an assistant restart are closed the same way (which message each card is in is kept in the chat state). Pressing a card that was already handled replies "Already handled"; the card changes to "Ended" only when the record says it ended for good (resolved / dismissed / expired / cancelled), and one not restored yet or not found stays as it is. The catch-up after the assistant reconnects does not close a card just because it is missing from the current list either: it asks for each card's outcome, and looks again after 90 seconds at the ones it is unsure about. Pressing a terminal or Codex card has to wait for the computer; after 2 seconds it first replies "Working on it…", then edits the card when done. A press whose answer comes back after that wait still says what became of it: one that failed posts a note under the card, which waits again for another press, and one that lost to another surface answering first closes the card as handled, as ever (#4123).

## Nudging a card nobody answered

A card the bot sent (a question, a plan, a permission, a terminal dialog or an MCP authorization) that has waited a while without an answer can get a short reply under it in Lark, where the user answers (#6084): "Still waiting for you: <what it asks>". Users who run many Agents get many cards; one answered within minutes needs nothing, the expensive ones slip past while the user is busy elsewhere. The phone's reminder 30 minutes after a seen-but-unanswered question (`docs/protocol/agent-states.md`, #5096) is a push, does not follow the card into Lark, and skips a card never opened, which is the slipped case.

- **When.** The assistant looks at the bot's open cards once a minute (`nudgeLoop` in `modules/lark/nudge.go`, next to the reply reminder's loop; rules only, no model, no tokens). A card is nudged once it has waited `nudge_after` since it was posted: 60 minutes unless set, **`0` turns both kinds of nudges off**. The setting is the bot's, kept with its other settings in `bots.feishu` (the web app's and the iOS / Mac Lark bot pages have a picker for it, under "What it can do"; the Android page does not yet, so there it is set in the web app or through the API): `PUT /api/v1/bots/feishu` takes `nudge_after` (whole minutes, 0 to 8640, six days: the chat keeps a card's record seven days; a fraction, a string or a number out of range is a 400; absent leaves it), `GET` returns the value in force, and `feishu.status` carries it to the assistant. A card still not nudged a day after it was due (`nudge_after` plus 24 hours since it was posted) is let go. With no card kept, the sweep does nothing, not even asking the hub for the bot's status. Turning nudges on after they were off (`nudge_after` from 0 back to a number, seen by the sweep) does not catch up: the cards already due at that moment are let go, not nudged, so a backlog never arrives all at once; the moment nudges were first seen off is kept in the chat state, so a restart while they are off changes nothing. Shortening the wait (60 to 15) does nudge, at once, the cards that have waited between the two.
- **Before a decision deadline.** A card with an `expires_at` also has one deadline nudge, independent of the ordinary `nudge_after` nudge. Its due time is `max(posted + 2 minutes, min(expires - 5 minutes, posted + (expires - posted) / 2))`; if that is not strictly before the deadline, there is no deadline nudge. Thus a 15-minute approval is nudged after 7 minutes 30 seconds rather than waiting for the ordinary default of 60 minutes. A positive `nudge_after` does not delay this nudge, and `nudge_after: 0` disables it together with the ordinary kind. This never changes the card's lifetime. Cards without a deadline have no deadline nudge. While a question on an approval is being answered, no deadline nudge is sent; after the answer, completed pause time moves the effective deadline and the due time is recalculated from it. A live extension of the approval window is likewise used instead of the originally posted deadline.
- **Once per kind.** The ordinary and deadline nudges each have their own sent, skipped and retry state, and different idempotency keys, so neither consumes the other. When the ordinary card nudge was sent is kept in the card's record in the chat state (`bots.feishu.state`, `nudged_at`), next to where the card is; the deadline and its independent progress are kept as `expires_at` and `deadline_nudge`, so a restart before a due send retains its schedule and a restart after a completed send does not repeat it. Each record is written before its nudge is sent, so a restart in between can lose a nudge but never doubles one. A send that fails for a reason that may pass is tried again in the next sweep under the same key (`uuid`, so one that did go out lands once), at most three sends in all and only within an hour of the first, because Feishu drops a repeated key only for about an hour; a refusal (the card or its chat is gone) is not tried again. A nudge given up, let go or refused is recorded apart from one sent (`nudge_skipped_at` for the ordinary kind): the board shows only a nudge that went out.
- **Saving the wait.** If saving `nudge_after` fails, the settings request returns an error and keeps the previous live and saved value. No successful nudge-setting change is recorded; retry the same change after storage recovers. This applies to the nudge write itself: other settings in the same request are separate saves.
- **Not nudged.** A card that was answered anywhere (Lark, the App, the watch, the computer), dismissed, replaced, expired or withdrawn: its record is gone. A private interaction is never nudged into Lark, even if an anomalous stored card record exists. A deadline nudge is also held while its approval is paused for a question, and is never sent after the effective deadline. One whose interaction the hub's queue no longer has pending, whose Agent is no longer in its computer's list, or that the queue cannot be asked about now (not restored after a restart yet) waits for a later sweep. The main conversation's `ask_user` card waits 2 hours (`askUserWait`), so the default 60 minutes reaches it; a Claude Code hook card still expires at 30 minutes, before the default ordinary nudge, and is asked again on the terminal.
- **Where.** A plain reply to the card in the owner's DM, which notifies by itself. In a topic group (`Topic group chats` above) the card's record keeps its group (`chat_id`; a card posted before this feature has none, so it is treated as a private chat card: a plain reply, no @), and the nudge goes in the topic (`chat_id`, `in_thread`) and @-mentions the owner at its start (`<at user_id="…"></at>` in the text message, Feishu's own syntax) so it reaches them. It is sent with `no_detour`: if the card was withdrawn, nothing is sent rather than a stray message.
- **What it says.** One line from the language files (`assistant-feishu_cards.nudge`, `nudge_permission`, `nudge_bare`; en, zh-Hans, ja): the first line of the question or the plan, cut to 100 characters. A permission card names the tool only, never the command, path or reason.
- **Quiet hours.** The hub's quiet hours (#5806, `hub/quiethours.go`) are set per device, so there is no one window. The assistant asks the hub (`notify.quiet`, `AppNotify`): quiet means **any device with quiet hours on is inside its window now**. The price: a device the user forgot, with a window on, holds nudges back during that window too. A nudge due then is not sent; the sweep of every minute sends it in the first minute after, once, if the card still waits (a card answered meanwhile is gone); a deadline nudge additionally requires that its effective deadline has not passed. If the hub cannot be asked, the nudge waits as well.
- **On the board.** With the waiting-for-you board on ("The waiting-for-you board" below), the row of a nudged card says "nudged" next to how long it has waited, and sending a nudge brings the board up to date like any other change.
- **Not built.** Urgent buzzing (Lark's urgent API) and the morning summary of deferred questions.

## Configuration and endpoints

```json
"bots": { "feishu": { "app_id": "cli_…", "app_secret": "…", "domain": "feishu" } }
```

The Lark app is one app used in two ways. The built-in bot uses its sealed App ID and secret for the long connection and bot messages. When `lark.cli` is configured without an explicit profile, the manager binds lark-cli's managed `persona` profile to that same App ID and keeps it synchronized when bot credentials change; lark-cli then provides the “read as me” user identity. An explicit `lark.cli.profile` remains an advanced compatibility override. The bot secret is passed to `lark-cli config init` on stdin and is never exposed in arguments, logs or status.

`domain`: `feishu` (default), `lark`, or the Open Platform address of a private deployment. Switches, features and pairing are configured in the App and stored in settings `bots.feishu` (read / written by the hub); chat state (current target, thread bindings, processed messages, and which message each still-open question / approval card is in: only ids and the conversation it belongs to, never the card's content, at most 100 cards for 7 days, #4358) is stored in `bots.feishu.state` (read / written by the assistant), and pending answers in `channels.state`.

These routes belong to the hub; `target` and `agents` in the response are queried from the assistant on demand (`feishu.view`). When the assistant isn't connected, these two fields are absent; everything else works as usual. `agents` is one row per Agent the owner has talked to in the chat — the threads bound to it folded together, the newest naming the row, newest first — not one row per thread: every card the bot posts about a conversation is bound to it so a reply finds it again, and the settings page shows the Agents, not the cards.

## What to do on the Open Platform

Nothing, when the app is created in one authorization ("Pairing and permissions"). For an app you create yourself:

1. Create an enterprise custom app and enable its **Bot** capability, and open the **Modify app info** permission (`application:application:patch`) once: with that, the rest below is done for you. When the App ID / App Secret are entered in the App, the manager configures the app through the Open Platform's server API (`feishubot/configure.go`): it opens the scopes and subscribes the events with the **long-connection** mode (`PATCH /application/v7/applications/:app_id/config`), then submits the publish, which creates the version when none is pending (`POST /application/v7/applications/:app_id/publish`). Best-effort and never blocks binding: a private deployment skips it, and a failure names the one switch left (the bot capability, the patch permission) with a link to the app's console page. The credentials step links out to the developer console; a rejected App ID / Secret is one sentence, not a code. The pairing hint retains the sanitized configuration outcome and console link through polling, code renewal and hub restarts. Polling only reads that outcome; it does not retry configuration or publish. An explicit credentials submission retries configuration, replacing the outcome; changing the App ID, secret or domain clears the previous app's guidance, and successful pairing clears it. Automatic configuration uses the receipt captured inside that credentials commit, so a newer save (even of identical credentials) cannot lend its generation to an older request. A completed unpair retires pending outcomes from the previous pairing lifecycle. Rejected credential, outcome or pairing-code writes return a localized failure and restore the previous in-memory state; a rejected unpair keeps the owner and sends no success notification.
2. By hand (the app was not auto-configured, or a step is checked): permissions `im:message` (read / write direct messages), `im:message:send_as_bot`, `im:message.p2p_msg:readonly` (messages sent to the bot in a DM), `im:resource` (download images and files in messages); for `workbench`, `im:message.pins:write_only` and `im:message.pins:read` (pinning the home card; without them it stays unpinned and works otherwise); `cardkit:card:write` (the streaming progress card; without it progress cards are updated as messages, as before); optional `contact:user.base:readonly` (names); for topic group chats one of `im:message.group_at_msg:readonly` (messages that @ the bot) and `im:message.group_msg` (all messages in the group, a sensitive permission, usually reviewed by the enterprise admin), "Topic group chats". The auto-configure opens `im:message:send_as_bot` and `contact:user.base:readonly` only: the rest are read scopes the platform lists for review, and group messaging stays the user's decision.
3. Events and callbacks: select **Receive events through a long connection** as the subscription method; subscribe to **Receive message v2.0** (`im.message.receive_v1`), optionally **User enters a chat with the bot** (`im.chat.access_event.bot_p2p_chat_entered_v1`, client v7.18 or newer) and **Message recalled** (`im.message.recalled_v1`: if the owner recalls a message before it is sent into the chat, it isn't sent, #4880; if already accepted and being answered, a turn answering only that message stops like /stop, changes its progress card to ‘Recalled, this turn stopped’, and sends no answer; if merged with other messages, only the recalled message is removed; already completed answers remain unchanged, #5248); subscribe to **Card interaction callback** (`card.action.trigger`). The auto-configure sets the mode and subscribes the listed events and callback, retaining the legacy first-chat subscription (`p2p_chat_create`) as well. The schema-2.0 entered-chat event triggers the pairing hint while the bot is unpaired; the legacy event is a separate schema-1.0 notification, not an alias for it.
4. Publish a version (enterprises usually require admin review; a version already under review counts as done), then enter the App ID / App Secret in the App, enable it and pair.

## Not implemented yet / limitations

- Recall: a message recalled while queued at the hub or before it enters its conversation is not sent. After acceptance, a turn answering only that message stops; a merged turn removes only the recalled message, and completed answers remain unchanged. The bot can't obtain the new content of an edited message (the Open Platform provides no edit event to bots).
- Agent messages show tool-call titles and outputs, not arguments (tested), so describe the action in the title; progress cards show only steps and text being written.
- Each step is one line, "verb + object" (`stepOf` in `feishu_steps.go`): commands use their description when available ("Run · Run server tests"), background commands say "Run in background"; file reads include the line range, while edits / creates / writes are separate; searches include their scope ("in src (*.go)"); subtasks include their type; to-dos show the item currently being worked on; Codex calls are already mapped to the same tools in the transcript (command → Bash, file change → Edit, create / delete separate), so they use the same wording; Persona's own MCP tools (calendar, contacts, reminders, mail, knowledge base) have their own verbs, while other tools show the tool name and the first useful argument.
- Agents (Claude Code / Codex in herdr) have no "text being written", so progress cards show only steps.
- Card callback tokens (two further updates allowed within 30 minutes) aren't used: after an answer, cards are edited through the update-message endpoint.
- One hub connects one Lark bot and one owner.
- A proxy reply has no live process bubble in the group; the answer is one text message, after the owner confirms it unless the chat is listed for direct replies ("Proxy replies handed off from a group").
- Group access ("Group access for teammates") answers a teammate with one text message and a sanitized chain of thought; it never posts a card, runs a command or starts an Agent, and a chat on its blocklist is silent for everyone.

## Task progress and review requests (#2768)

The owner only watches Lark, so the bot proactively sends updates on tasks (to-dos) dispatched from the main chat to the DM, without lark-cli or individual approvals on the phone (requested and authorized 2026-11-05). Sends only when something changes; no change, no message. Code: `server/internal/assistant/reports.go`, `acceptance.go`.

- **Goal level by default** (#3218, the owner, 2026-11-10: "I care whether the direction and the goal are met, not the execution"): with `report_steps` off (the default) a finished turn, an interruption, a closing by the judge and the stage moving on are execution steps and are not pushed; the stage is still kept for the apps. What goes out is a change of the goal: reached (the conclusion card below, or "Please verify" once deployed), waiting on the owner (the decision's own answerable card, with no report line around it) and stuck: the task did not start, or its turns were cut off 3 times in a row with no finished one between (told once; a finished turn starts the count again). A stuck task's card (🎯, red) has three lines per task: **🎯 Goal** (the title), **Now** ("stuck: did not start" / "stuck: cut off 3 times in a row"), **Evidence** (the error in a line and a link to the Agent's chat, else the task page); no stage bar, no Agent's words; up to 10 tasks, then a line counting the rest. The rest of this section is the card with `report_steps` on.
- **Card titles** (#11195): task reports, stuck notices, review requests, conclusions and waiting cards name the direction and the task. The main conversation's work is shown under Persona. A report covering several tasks names them in order in the title up to the header limit, with its full list in the card.
- **Coalescing**: changes within a minute (a turn finished, waiting for you, interrupted, failed to start, automatically marked done) are combined into one card; only the latest state of each task is kept. Check again before sending: don't report questions already answered or to-dos deleted; if a question card is already in the chat (`cards` / `all_cards`), don't repeat "waiting for you"; quiet tasks aren't reported when `sync` is on (the main chat's answer has already been synced), except "automatically marked done", which is still reported (the main chat doesn't mention that).
- **Card**: decisions needed go first (each followed by the usual question card so options can be tapped directly; cards already sent aren't duplicated), then a section per task: status, title, computer, stage bar
  Plan → Development → Review → Merged → Deployed → Verified (✅ completed, 🔵 current, ⚪ upcoming; none for general work, and work closed with nothing left to deploy ends ✅ Done after its steps, #11590), the Agent's last words (first 300 characters), and buttons **Task page**, **PR**, **Agent chat** (web links; omitted if hub.json has no `public_url`). No bare IDs.
- **Stages** (`Todo.stage`, `Todo.pr_url`, stored in settings `assistant.todo_stages`, only advance): starting work is **Development**; a PR link in the reply means **Review**, also mentioning a merge means **Merged**; saying deployed / live means **Deployed** (doesn't count when preceded in the same clause by "还没" (not yet), "未" (not), "别" (don't), "无需" (no need), "等你确认后再" (after you confirm), "not yet", "will be", etc., or followed by "吗" (a Chinese question particle) or "yet"); saying tested successfully after deployment means **Verified**; tapping **Pass** on a review request also means **Verified**. The App's to-do detail draws the same stage bar from these two fields (#2776).
- **Deployed needs evidence** (#3205): a task reaches **Deployed** only when the running hub's commit contains its PR's merge commit; merged but not in the running hub, it stays **Merged** ("已合未上线", gate "等部署…"), with no review request, and moves on by itself once the deploy lands (`docs/assistant/todo-status-sop.md` "Deployed needs evidence").
- **Who verifies** (#3205): a deployed task is accepted by the supervising assistant by default (`by_assistant` on the ask, stage Verified, no card); only a big feature (a to-do with priority `high`) gets the review request below.
- **Review request**: as soon as a big feature reaches **Deployed**, send a three-line card: what changed (one sentence), where to look (a link straight to the page, only one present in a reply, the task page or Agent chat; never one invented by the model), how to check (what to tap, what to expect). A small model (purpose `inbox.judge`, prompts `prompts/assistant/acceptance*.md`) reads the task and replies to write these three lines; if the model isn't available, use the task title, task page and a generic check instruction.
  - Tap **Pass** or reply to the card with "通过" (pass; "没问题" (no problem), "OK", "LGTM" also count): mark the to-do **Verified**, and change the card to **Accepted**. When the hub cannot read the stored asks or save the acceptance, nothing is accepted and the stage does not move: the card button's toast and the web button (`POST /api/v1/todos/{id}/accept` answers 503) say the service is unavailable, never "already handled", and the same tap works once the store answers. A text reply says so only when the asks were read and the save failed: while the asks cannot be read the hub cannot tell the reply is about the card, so it is handled like any other message in the chat. A reply to a card of a round that is no longer the one waiting (an earlier round, or one handled meanwhile on another surface or by the card's own button) is answered "already handled", as that button is, and does not reach the Agent (#3836).
  - Any other reply: record it in the to-do's decision section (**Review feedback**) and send it to the original Agent to fix; deploying again after the fix triggers another review request.
  - Only the words of a reply go on (#5107). A reply that carries pictures or files is told they did not go to the Agent and to say in words what is wrong, or send the picture from the app: a picture alone gets just that line and the card still waits; a picture with words sends the words as above and adds the line to the receipt.
  - Each task gets one ask per round (stored in settings `assistant.acceptance`), kept whenever the work is deployed; the card is how it is shown in Lark, not what makes it. With the bot on and `reports` on, the ask has its card. With no card due (the bot off or not paired, or `reports` off) the ask is kept all the same, with `no_card: true` and no message id: the briefing's "To accept" section, the board and the snapshot list it, and the Accept button of the web `brief` item (`POST /api/v1/todos/{id}/accept`) verifies it like a tap on the card (stage Verified, the line in the to-do's topic, the report back to where the request came from). A card that failed to go out while the bot is on (the send failed or timed out, or the bot's status could not be read) is a different case: that is a card for later, not a card never due. The ask is kept without a message id and without `no_card`, listed meanwhile as a card-less one is, and every 10 minutes the sweep that sends the reminders tries its card again, under a key of that round's own (`uuid`), so a send that did land though its answer was lost is not posted twice. Feishu drops a repeated key only for about an hour, so the card is tried only within 45 minutes of the ask; after that, or when the sweep finds the bot off or `reports` off, the ask is marked `no_card` and stays card-less. An ask passed meanwhile by the task's supervisor (`by_supervisor`, see "Conclusions") still gets its card this way, saying the supervisor checked it: the pass settles the work, but the card is how the owner hears of it (#9253). One the owner passed themselves gets none. The sweep follows the round rules below: it never posts an ask from before the to-do's latest reopen, one whose to-do ended, or one its supervisor passed whose review no longer stands (cancelled or reopened since), and drops it instead. A card-less ask gets no morning reminder card and is not posted after the bot is set up later; the next briefing lists it. Round rules are the same with or without a card: an ask made before the to-do's latest reopen is dead, and a to-do the owner closed or a review closed drops its ask. If not accepted the next day, mention it again in the morning brief ("waiting for user acceptance" in the snapshot, item 4 of the morning prompt), and send a **Not yet accepted** card at the morning-brief time (the time of scheduled task `morning` when enabled, 9:00 if disabled or deleted, in the user's time zone), once a day. With the morning briefing's `facts` on, the briefing card carries these instead and the reminders wait an hour; see "Morning and evening briefings" below.
- The switch is `reports`; when the bot is disabled or unpaired, nothing is sent and changes during that time are discarded (later cards describe the state at that later time). The "Please verify" ask is not one of those changes: it is kept without a card (see above).
- **The verdict on top**: the "Please verify" card's first line is its verdict, "✅ Done: deployed, check it below", the same line the briefing and the web `brief` item show for it (see "Conclusions").

## Conclusions (#1226)

The owner hands out many tasks and wants one thing of each: its conclusion. Code: `server/internal/assistant/conclusion.go`.

- **When**: the main conversation's review of a supervised task gives a result. `task_review accepted` sends a card that says **✅ Done** (`outcome: done`, the default) or **⛔ Cannot be done** (`outcome: cannot`: the work found the thing cannot be done; that is a result too). `task_review needs_user` sends **🤔 Needs your decision**, and so does a third rework, which goes to the owner (its reason then is "sent back 2 times and still not done; how should it go on?", not the rework meant for the Agent). Rework and cancel send nothing.
- **The card** (goal → now → evidence, #3218): **🎯 Goal** (the task's title), **Now**: the verdict and one sentence of why, and for a done or cannot-be-done one how far the work went out (from the done judge's delivery, else the stage: "live and checked", "live, not checked yet", "not live: stopped at a PR", "not live: merged, not deployed", "deployed, off by default", "nothing to ship"; nothing when not known), then **Evidence**: one link. In detail: the verdict and one sentence of why (`reason`; the first line of the review's note when it gave none) on one line, one link, a button. The link is the one the review gave (`link`, a web address); else the task's PR; else the first web address in the review's note and evidence; else the Agent's chat; else the task's page. "Needs your decision" adds the option the supervisor recommends (`recommend`).
- **Against what was asked** (#3822, #10380): the card does not list the task's criteria; it leads with the verdict and the result, and on a done or cannot-be-done conclusion adds one line, **Not met**, naming the criteria the work did not meet (the first three, then how many more), only when there are any. Each criterion with how it ended (met, not met, not checked, dropped with the scope change), and what was done beyond the brief, stay on the task's page (`docs/assistant/unified-entry.md`, "Briefs"). Nothing of it on a decision.
- **Answering**: **Got it**, or a reply "OK" (the same words as **Pass**), marks it seen; unlike **Pass** on deployed work it does not move the stage to Verified (the review closed the task already). On a decision, **Take the recommendation** or "OK" records the recommendation in the to-do's decisions and sends it to the task's Agent; any other reply is the owner's choice, recorded and sent the same way. Either way the task no longer waits for the owner (`needs_user` is cleared), so the Agent's next stop comes back to the supervisor as any stop does. When the task has no Agent that can receive the choice, the hub still records it, ends the round, returns 200 with `delivered:"none"`, and tells the supervisor to pass it on without an automatic resend. Another delivery failure is not taken and not recorded: a reply is told that nothing was changed, and why, the Lark button shows an error toast, and the web button answers 502 with code `accept_not_taken`. When the send's answer never came, or the node is not sure it typed it, the recommendation may be with the Agent already: the reply and the toast say so and to look at the to-do before answering again (never that nothing was changed), the web button answers 502 `send_in_doubt` (`docs/assistant/todos.md`), and no default at the decision's deadline sends it a second time; a refusal the node coded, such as `dialog_open` for a dialog open in the Agent's terminal, answers 423 with that code, #7343, and the web says to close the dialog in the terminal first; the button works again. Any other reply to a done or cannot-be-done card reopens the to-do and goes to its Agent, as feedback on "Please verify" does. A decision with nothing recommended has no button, and "OK" to it goes on as an answer.
- **One push**: the task's closing is not also a line of the task report. Deployed work keeps its "Please verify" card (with the verdict on top) and gets no second card when the review accepts it. A decision is its own card even then. A later conclusion of the same task replaces the one before, whose cards then answer "already handled"; rework or cancel ends a decision still waiting.
- **The supervisor's acceptance is the check** (#3240): the owner only decides, and looks at what truly needs their own eyes. A supervisor's (the main conversation's or a leader's) `task_review accepted`, made after checking the evidence, passes a "Please verify" still waiting (one from before deployed work was accepted by the assistant, #3205) for the owner: the to-do is **Verified** as if they had pressed **Pass**, the card's buttons give way to "the supervisor checked the evidence: marked verified" (`by_supervisor` on the ask). A done or cannot-be-done conclusion it sends is likewise already checked: it tells, it has no **Got it**, and the briefing does not list it. Its card is still due: one whose send failed is tried again like any card for later (see "Task progress and review requests"). When the hub starts and every 10 minutes a sweep passes the asks left waiting on tasks their supervisor accepted. The owner is still asked when the review sets `user_check` (a UI change someone has to see: a "Please verify" card is posted and waits for **Pass**, also when the deployed work was accepted by the assistant before), for a big feature (to-do priority `high`, #3205), or when the task has no supervisor. A task the done judge closed after its spot check (`by: judge`, #3356) counts as checked the same way: its conclusion is told, not left for **Got it**, unless it is a big feature.
- **Restart during the first post** (#10393): before looking up bot status or posting an immediate conclusion, the manager saves its complete ask, including `asked_at` (the idempotency key), outcome and supervisor acceptance. An exit inside that provider call leaves the same round for the normal retry sweep after restart. While the original call is in flight, its in-memory claim still excludes duplicate initial posts and sweeps; other book saves preserve the prepared conclusion. A failed preparation sends nothing, and its in-memory retry must save successfully before posting. Retry windows, current-round guards, reports-off and quiet-mode rules still apply. This is not an atomic transaction with task closure: a crash before conclusion preparation, or a database outage followed by an exit before any successful save, is outside this guarantee.
- **Kept like "Please verify"**: the conclusion is the to-do's ask in `assistant.acceptance` (`conclusion`, `outcome`, `reason`, `recommend`), with a card or without (`no_card`), retried the same way. The briefing's "To verify" section, its Lark card, the web `brief` item, the board and the snapshot list it with the same verdict line. It is not posted again the next morning, and it does not expire: the briefing lists a done or cannot-be-done conclusion the owner is to acknowledge (a big feature's) until they press **Got it** (or reply "OK"). A decision stops being listed once the to-do is closed or no longer waits for the owner.
- **A decision that can wait** (#4930): a `needs_user` review marked `can_wait` gets no card and no push when it is raised; the next briefing lists it, and its card goes out later only if it had to be pushed because no briefing reached the owner with it (`docs/assistant/todos.md`, "Decisions that can wait").
- **Not covered**: tasks nobody supervises (closed by the hub's judge) end with the task report's closed line only with `report_steps` on; by default their closing is not pushed (it is no goal-level result: nobody checked it); Android draws no `brief` item yet.

## The waiting-for-you board (#6052)

With `board` on, `/tasks` (and `/进展`, `/总览`) keeps one standing card in the owner's private chat that lists everything waiting for them, and edits that card in place instead of sending a snapshot each time. Code: `server/internal/modules/lark/board.go` (when and how it is edited) and `server/internal/assistant/board_rows.go` (what it lists). With `board` off nothing changes: `/tasks` sends its snapshot every time and the board is never made or edited.

- **One card, edited.** The first `/tasks` sends the board as a message of its own and remembers its message id and the time it was sent (`board` in the chat's state, `bots.feishu.state`). Every later `/tasks` edits that message and replies with one short line, "Updated, it is the card above", as a reply to the board (Feishu shows the quoted board in the reply, and tapping it jumps there; Feishu has no link to a message). A new board is sent only when the old one can no longer be edited: it is older than 14 days (Feishu's edit period, counted from when it was sent; no edit is tried), or an edit fails with an answer that will not change: deleted or withdrawn (230110 / 230011), past the edit period (230031, "Update sent message card" in Feishu's docs), not a card (a card Feishu refused went out as rich text, and its id is a text message's), or any other Feishu refusal. Only a passing failure keeps the board as it is: no answer at all (the network, a timeout, the connection to the hub), a rate limit (230020), a server error (5xx) or a token that had to be renewed; then `/tasks` answers with the snapshot as it does with the switch off. The new board goes out under a key made of the old one, so a send that timed out and is tried again is still one message, and it is remembered and is the board from then on. Writes are one at a time, so two `/tasks`, or `/tasks` and the timer, make one board. A new pairing starts the chat's state afresh, and the board with it.
- **Kept current.** Once there is a board, it is edited about 3 seconds after any of these (changes that come within those seconds are one edit; nothing is scheduled while the chat has no board): a card opens or ends (`interaction.announced` / `interaction.ended`: answered anywhere, dismissed, expired, its Agent gone), a to-do enters or leaves "Please verify" (its card goes out, it is passed, it is closed, reopened or deleted), and once when the assistant has connected to the hub and read the cards that are pending (a restart of either); before that read, nothing is written, because the list is empty only for being unread. With the switch turned off, or the bot unpaired, nothing is edited, and the to-dos changing do not ask for the bot's status more than once a minute. A bot paired again is a new chat: the old owner's board is forgotten, not edited.
- **The rows.** Each row is a short number, one sentence, how long it has waited ("2 min", "1 h 20 min", "3 d"), who asked (Persona, or the Agent by its title), and a link to the conversation or the to-do on the web app (left out when hub.json has no `public_url`). The sentence is the card's question, clipped (a plan: "Approve the plan"; a to-do waiting to be verified: "Please verify: <title>"). A permission card says only "Needs your approval", never the command, the path or the tool, and a terminal dialog only "Needs you": the board sits in a chat that may be seen in a screenshot. Order: the cards that hold up an Agent first, the longest waiting first, then the to-dos waiting for you to verify them, the longest waiting first. A card that has ended is not listed even while its entry is still being taken away.
- **Waiting times do not tick.** How long a row has waited is written when the board is, so it does not move between two updates: go by the "Updated" note at the bottom. The board goes only to the private chat; a card raised in a topic of a group shows on it as a row with a link to the web app, and the topic keeps the card itself.
- **Nothing waiting.** The board says "Nothing is waiting for you right now" and stays; a note under the rows says when it was last written.
- **One card.** At most 30 rows, and as many as fit the card's size limit; the rest, the last in the order above, are counted ("and N more, see the web app").
- **Switch.** `board` in the bot's features, next to `cards`, `reports` and `pushes`. The web settings page and the channel page (Android, and the channel list in the Apple apps) draw it from the lists they have: the channel page's list is the manager's (`GET /api/v1/channels`), the web page's is its own. The iOS / Mac Lark bot page lists its switches itself and shows it under "What it can do" when the hub's answer has it (a hub from before leaves it out, and the page shows no switch); it sends it with the other switches, and when the hub did not send it, it sends nothing of it.

## The workbench (#1961)

For people whose front end is Lark rather than the app. With the `workbench` switch on, the standing board below is drawn as a home page and kept where the owner finds it. Code: `server/internal/modules/lark/workbench.go` (the cards, the commands, the Inbox actions), `workbench_pin.go` (pinning, the button on every card), `companions.go` (companion bots and their four routes, `hub_routes` of the lark module: 404 with the module off).

- **The home card.** Where messages go now as its subtitle, and as tags how many things wait for the owner and how many agents are busy; what waits for the owner, as the board lists it (the first three, each a row pressed whole: one holding an Agent up withdraws its card and posts it again at the bottom of the chat, a to-do to verify opens its page); the agents at work (the first three, each a row with its state as a tag, pressed to make it where messages go); the Inbox (what needs the owner, what is only to know, the first two items); the next meeting; how many computers are online; and one row of buttons: the Inbox (filled when something there needs the owner; an `inbox` companion's link in its place), Tasks, and a "more" menu with Today, `/agents`, `/start`, the main chat, a new chat, Refresh and the other companion bots. The `main` and `agents` switches still decide which of those entries are there.
- **One, pinned.** `/home`, the **Workbench** button of any card, or `POST /api/v1/assistant/feishu/workbench` posts a fresh home card at the bottom of the chat, pins it (`feishu.pin` with `exclusive`: the bot's other pins in the chat come off, the owner's own stay) and withdraws the one before (`feishu.recall`); one too old for Lark to withdraw is redrawn as a line that says the workbench moved. The card is the board from then on (`botState.Board`), so it is edited in place as the board is, and a home card that can no longer be edited is replaced by a new one, pinned in its place.
- **Kept current.** Besides the board's own triggers (a card opening or ending, a to-do entering or leaving "Please verify"), the pinned card is looked at every minute while the switch is on, and edited only when what it shows changed (the "updated at" note does not count). With `board` off as well, `/tasks` stays the snapshot it always was; with both on, `/tasks` edits the home card and points to it.
- **A way back from every card.** Every card the bot posts or redraws gets a small **Workbench** text button (not one that has workbench buttons already, and not one near the card size limit). The button follows the switch as last read (each feature read updates it), so it stops with the switch. When the last row already contains only `open_url` navigation (a mirrored answer's **Open on web**), Workbench joins that `flow` row instead of making a second navigation row; approval, form and other callback action rows stay independent. Narrow clients wrap the same row without changing either action (#5317).
- **`/today`.** The main conversation's Today (the one the app shows: waiting, meetings, done overnight, what did not go through, Lark chats that @ the owner), the questions and approvals waiting, the Inbox items that need the owner, and a "right now" line.
- **`/inbox`.** The open Inbox without its noise, what needs the owner first (at most six, the rest counted), each starting with its state as a tag (needs you, urgent, FYI) and with one row: **AI draft** (when a reply can be sent to its source, primary), **Done**, and **Mute sender** in its "more" menu (when it has someone to mute). Done and Mute redraw the card in place. AI draft posts a draft card under it (the model takes longer than Lark's 3-second callback): the draft to edit, a line of what to change, **Send as me** and **Redraft**. Sending is the app's reply (`replyInboxFrom`, the draft card's message as the send's id, so a double press sends once and a press after the item was filed changes nothing); **Send as me** asks first in Lark's dialog; the draft card turns grey with what was sent, and the Inbox card is redrawn.
- **`/start`.** A permission field before "what to do", offering `proto.PermissionModes`; none keeps the launcher's own mode (the agent's `session.start` gets no `permission_mode`).
- **Switched off.** None of it: the commands go on as text, no card gets the button, `/start` has no permission field, nothing is pinned, the companions are not linked and the notices go to the chat. The home card already in the chat stays as it was.

### Companion bots

An extension can run other Lark bots for the owner (an Inbox bot, a notifications bot) next to this one. The hub knows nothing of them: the extension registers them with the assistant, which links them from the home card and, while one polls, hands it the notices. All four routes are for full credentials only (an extension with `hub_api`); none has an extension scope yet.

- **Registering.** `PUT /api/v1/assistant/feishu/companions {bots: [{kind, name, icon, app_id}]}` replaces the list (at most six; `kind` is `inbox`, `notify` or `other`; `name` at most 20 characters; `app_id` a `cli_` app id); `{bots: []}` removes them. They are kept in the chat's state, so a new pairing starts without them: an extension registers again when it starts and from time to time. Each is a link button on the home card (`https://applink.feishu.cn/client/bot/open?appId=…`, which opens the chat in the Lark apps; the web client may not follow it). An `inbox` companion's button, with the count of what needs the owner, replaces the home card's `/inbox` button.
- **Notices.** While the workbench is on, a `notify` companion is registered and it polled in the last 90 seconds, these go to it instead of the chat: `notify_user` pushes (`push`), a scheduled task's own conversation's answers (`task`) and the task progress cards (`report`). The main conversation's turns, the agents' finished cards, questions, approvals, plans, a decision's own answerable card, "Please verify" and conclusions stay in the chat: they answer for the owner or are answered by a reply there. The companion long-polls `GET /api/v1/assistant/feishu/notices?boot=&after=&wait=` (`wait` at most 50 seconds) → `{boot, notices: [{seq, kind, card, text, at}]}`, `card` the bot's Card 2.0 JSON and `text` its fallback; `boot` changes when the assistant restarts (a poll with another one starts from the beginning). Notices are kept in memory, the last 200. A companion that stops polling gives them back to the chat after 90 seconds.
- **Presses.** A notice's button pressed in the companion's chat (the companion checks it is the owner's) is relayed to `POST /api/v1/assistant/feishu/notices/action` with the card callback's event; only what needs no owner's action is taken (`accept`, a workbench button), and anything else answers with a toast to answer it in the bot's chat, where the cards carry the owner's action.

## Morning and evening briefings (`facts`)

With a scheduled task's `facts` setting on, its run has a part Persona fixes and computes, and the model only writes a sentence or two on top. It is on for the default morning and evening routines of a new hub; on a hub set up before it is turned on only for a routine that still holds an earlier default prompt, which is replaced by the current one (`upgradeDefaultRoutines`). A routine whose prompt was edited keeps `facts` off and behaves as before. The setting is the task's `facts` field (`PUT /api/v1/assistant/tasks/{id}` sets it only when the body has it, so an app that does not know it leaves it as it is). Code: `server/internal/assistant/briefing.go`, `server/internal/modules/briefing/card.go`.

- **Computed once, when the run starts.** The card, the push and the facts the model is given (they head the message that starts the run) all come from that one computation, so their numbers agree. Right after a restart the cards waiting for an answer are not read yet: the run waits up to 20 seconds for them, and if they still are not there the briefing says so instead of saying nothing waits. The routine's own earlier failed attempt (this run is its retry) is not listed. The card is made only for the turn the run started and only when it ended normally; a message the owner sends into the routine's conversation later, or a turn that stopped on an error, is mirrored as any other answer.
- **Waiting for you.** The standing board's rows that hold an Agent up, as `boardRows` gives them: how long, who asked, a link, and "nudged" for a card the bot nudged under.
- **Last 12 hours.** What did not go through is listed before what finished, so a long list of finished to-dos does not push it out. To-dos closed in the 12 hours before the run (those still waiting to be verified are listed only as such), and what did not go through: to-dos whose Agent did not start, and scheduled runs that failed or were skipped (`todayFailures`, the same data as the Today card).
- **To verify.** The board's "Please verify" rows and conclusions waiting for the owner, each with its verdict line (word for word as its own card), what changed (deployed work) or the recommended option (a decision), and a button: **Accept** for deployed work, **Got it** for a conclusion, **Take the recommendation** for a decision (none when nothing is recommended). A decision its supervisor marked `can_wait` got no push and no card when it was raised and is first put to the owner here; a card that has no room for its row leaves it held (`docs/assistant/todos.md`, "Decisions that can wait").
- **Can wait.** The questions Agents left for a briefing (see "Questions that can wait" below), the oldest first, at most 10 and the rest counted, each with what was asked, who asked, how long ago, a link to the Agent's chat and a **Handled** button. After "To verify" and before "In progress"; left out when the queue is empty.
- **In progress.** The open to-dos whose Agents are working, the longest open first, each with its stage bar (plan → develop → review → merge → deploy → verify) and a link; at most 8, the rest counted. It comes last and is left out when nothing is running.
- **Inbox follow-ups, for the model only.** Up to five matters waiting on the other side (state key `waiting`) for more than 24 hours (`handling.since`), and up to five coming due today: `follow.check_at` in the owner's today, or the state key `follow_up_ask` / `check_due` whatever the date; each with its title, who or what it waits on and next step. The model includes them even when a card carries the other facts. These rows are not added to the card, the apps' `brief` item or the push counts. Computing them never advances a check, rewrites a follow or changes an item's state.
- **Recommended setup.** The first briefing of a week that reaches the owner (its run ends normally) carries one more section when the numbers name something: which mechanism that is off (the assistant answering agents' questions, standing authorizations, starting directly, the triage's actions, leader conversations, spot-check reviews, independent review) would have removed how many of the last 7 days' asks or background rounds, its cost in one sentence, and where it is turned on; and, when the background supervisor's reviews held on a provider that has a lower tier, one line saying so (#5805). It is computed like the rest and drawn on the Lark card and on the web app's briefing card, each mechanism is named at most once in 30 days, and nothing is turned on (`docs/assistant/assistant.md` ("Recommended setup")). There is no weekly routine; this is where the weekly block goes.
- **In the apps.** Whether or not the Lark bot is on, a `brief` item with the same rows is written into the routine's own conversation when a run is sent (`docs/protocol/protocol.md` ("Tasks and the chat feed")). The web app and the iPhone and iPad app (#2320, `docs/apple/ios.md` ("Briefing card")) draw it with an **Accept** button per task to verify (`POST /api/v1/todos/{id}/accept`, which holds to the same round check as the Lark button) and a **Handled** button per question that can wait (`POST /api/v1/later/{id}/handled`); Android does not know the kind yet and skips it. A waiting card's row and a question's row name the chat they came from (`machine_id` / `session_id`), which the apps open (the web where How Agents open says, #12055). The tasks to verify come from the "Please verify" asks, which are kept whether or not a Lark card went out, so the section is the same without the bot. When the Lark card is not going out (bot off, or `pushes` off) the model is told so and lists the rows itself, in the same order, from the same numbers, which keeps Android whole until it draws the item.
- **Accept on the card.** The button carries the time the "Please verify" ask of that round was made (`asked_at`; the ask of a to-do without a card has one too). It verifies the to-do only while that is still the round waiting, so the button of an earlier card does not verify a later round (#4853); it answers "already handled" instead.
- **No second reminder that day.** Once the briefing card is out, the to-dos it listed with an Accept button are not asked again by the morning reminder (`RemindedAt` is set). When the morning routine has `facts` on, is due that day and its card can go out (the Lark bot is on with `pushes`), that reminder waits until an hour after the routine's time (never past midnight); if the briefing has not gone out by then, the reminders go one by one as before. To-dos the card did not fit ("and N more") are reminded as before.
- **The push** says the counts instead of the first words of the model's answer: "waiting for you 3 · not through 1 · done 2 · to verify 2 · can wait 2". Only the turn a scheduled run started says them; a turn that failed, was cut off or asks a question, and a health conversation, are pushed as before.

- **Delivery retries and retained claims** (#10290). During an existing mirror retry, a temporary failure to read
  Lark status uses an existing retry slot, as a temporary post failure does. A post resumes only after its channel is confirmed enabled and its turn
  is still current, using the original card and UUID; the three-retry limit and 30-second interval are unchanged.
  While the run's turn claim remains cached, another completion for that turn cannot fall through to a generic
  reply, during its post or after its facts have aged out. Later turns and later routine runs keep their own sends.
  This is an in-memory guarantee; cache eviction, replacement by a later run and service restart are outside it.

## Questions that can wait (`urgent: false`)

An Agent working on a supervised to-do can say a question does not hold it up: `report_to_supervisor` with `kind: "question"` and `urgent: false` (#6287). Its other ways to ask stop it until the owner answers (its own question tool, a permission, a plan) or start a turn of the main conversation (`report_to_supervisor`, urgent). This one waits for the next morning or evening briefing. Code: `server/internal/assistant/later.go`, `agent_control.go`.

- **What happens.** No supervision signal (so no extra turn of the main conversation), no card and no push. The question is written into the supervisor's conversation as a `report` item marked `later` (the web app draws it quietly, with the mark), and an entry goes into the queue kept in settings `assistant.later`: id, to-do, machine and session, the text (clipped to 2000 characters as any report), `asked_at`. The queue survives a hub restart. At most 100 entries; beyond that, and whenever the queue can't be read or written, the question is sent as an urgent one. The same question of the same Agent that is in the queue already is not put in again (the answer says so). The report rate limit (10 in 10 minutes per session) counts these too.
- **Only when a briefing will list it.** If no daily routine with `facts` on is enabled (the default morning one, or the evening one), `urgent: false` is ignored and the report is sent as an urgent question; the tool's answer says which happened. `urgent` on any other kind has no effect and the answer says so. Missing or `true` changes nothing.
- **Leaving the queue.** Only three ways: the owner marks it handled (the **Handled** button of the `brief` item in the web app or on iPhone and iPad, Lark **Handled** button on the briefing card), its to-do ends (closed or deleted), or 7 days pass. Handled on an Agent's question only takes it out of the queue: its supervised to-do stays open and its Agent is not told. Persona does not guess from the chat that a question was answered. A question that left without an answer is not asked again. Entries that are over are dropped when the queue is next looked at (a briefing, a press of Handled, a new question); a Handled press on one that is over answers "already handled".
- **Not on the board, no nudge.** The standing board (#6052) does not list these, and the card nudge (#6084) does not apply: nothing is held up by them. They are in no push either, except as a count in the briefing's push text.
- **What a row says.** The question (the first 160 characters), who asked (the Agent by its title; one that is gone, or has none, by its to-do), how long ago, and a link to the Agent's chat. The evidence the Agent sent is only in the `report` line in the supervisor's conversation.
- **The assistant's own questions too.** An `ask_user` of the assistant's that expires unanswered becomes a to-do (`docs/assistant/todos.md`, "Questions nobody answered", #1617) and goes into the same queue, the asking conversation as who asked; it leaves the queue the same ways (its to-do is closed once the owner decides). Handled on its row ends the question too (#1854): the to-do is closed first, as closing it in the to-do list does, so the asking conversation is told once that it was dropped; if the to-do can't be closed, the press fails and the row stays.
- **Supervisors' decisions wait the same way, in their own place.** A `needs_user` decision a supervisor marked `can_wait` is not in this queue: it stays the to-do's ask and the briefing lists it under "To verify", where it is answered. It counts on the same routines and, unlike a question here, is held only when one of them is due in time, and is pushed after all when no briefing reached the owner with it (`docs/assistant/todos.md`, "Decisions that can wait").
- **In the briefing.** Every briefing run with `facts` on lists the whole queue, so a question stays in the next briefings until it is handled, ends or expires. The model is told how many there are and not to list them again. Without the Lark bot the section is only in the `brief` item, which the web app and the iPhone and iPad app draw.
