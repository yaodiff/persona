# Lessons: extension settings lifecycle

- Installed extension ids can collide with connector or channel ids under one assistant (#17762). Use the live
  host registration when it exists and an unambiguous contribution of the matching resource type next. Check both
  before using an older producer's equal id, so a built-in connector or a second claimant keeps its own settings.

- A computer's extension sync must not prune other computers using an old configuration snapshot (#15433). A snapshot can pass the registry-current check, then be overtaken by a configuration change while another computer completes its sync. Read the current selected-computers list under the node-state lock before pruning: this preserves newly selected computers' `running` or `outdated` rows and still cleans unselected rows for computers removed from the fleet. A deterministic old-snapshot regression checks both contracts without sleeps; multi-CPU repeats exercise the original fan-out race.

- A partial Lark feature save through Settings PUT or `feishu.configure` must retain its supplied keys until the final locked commit (#12646). Expanding them into a full snapshot before credential validation lets a delayed save overwrite another client's successful switch change. Merge into current features after validation, and snapshot rollback state at that commit so a failed write preserves intervening saves. Test the real settings route with a paused fake BotInfo response and let a second single-switch request finish before releasing it.

- Device-code pairing belongs to one effective session across clients (#12620). Serialize binding separately from the settings mutex, including the finish that saves credentials and ownership; a canceled waiter must leave the active operation alone. Every settings entry point that changes credentials shares that lifecycle and retires the old registration in the same successful commit, while unrelated switches stay independent; failed validation or persistence keeps the previous session. Keep terminal errors until an explicit bind action rather than creating registrations from background polls. Pause fake Begin, Poll and credential-validation responses to verify concurrent clients, cancellation and late results without calling a real accounts service.

- Node package transfers share a framed RPC stream with heartbeats (#8609). A 1 MiB chunk becomes about 1.4 MiB after JSON/base64 encoding and blocks that stream for about 20 seconds at 70 KiB/s. Use 32 KiB chunks for plugin packages, including on existing nodes: their chunk handler checks offsets, not a fixed chunk size. Keep failed package attempts across connection replacements and delay them for ten minutes; the lease loop retries due packages on its next tick, so a stable reconnect does not leave them missing forever. Always check `plugin.node.have` first and clear the failure when it succeeds. The old wire protocol cannot query a partial upload's acknowledged offset; cooldown is not resumable transfer. A throttled RPC-pipe test proves heartbeat queuing and byte integrity, not WebSocket/control-frame behavior, which still needs a live check.

- Bundled-logo tests must include the production facade and connection, not only a stub that overrides the optional methods (#5461). A process-owned Android facade otherwise inherits the unsupported default even though direct HTTP and UI tests pass. Check download limits before a general-purpose client buffers the response; streaming bodies belong on `Dispatchers.IO`. Both clients' private image caches need the actual default-manager identity, not an empty selector or an unchanged singleton API.
- SDK manifest projection is also embedded in the trusted Deno adapter. After changing the TypeScript projection, regenerate `scripts/gen/deno_adapter.sh` with the CI-pinned Bun version, not only the schema/wire bundle; `TestTrustedAdapterMatchesOfficialSDK` compares the installed adapter's actual bytes. Until #6001 any `sdk/ts/src` edit counted, even type-only changes to `wire.ts`: when the bundle's symbols changed, Bun's identifier minifier handed out different short names, and the adapter's bytes changed with no change in behavior (#5862 after #5834, #5971 after #5934). The adapter is no longer identifier-minified, and `pre-push` refuses an `sdk/ts/src` change whose adapter is stale, or that it cannot check without Bun (`docs/operations/testing.md`, "Trusted Deno adapter"). Without Bun this test fails on every tree, so "fails the same on main" says nothing about your change: install the pinned Bun (`docs/lessons/testing.md`) and run it. Authenticated logo fetches must reuse the regular API's client and selected-manager headers as well as authorization.
- Bundled artwork (#5461) is signed source/catalog metadata, not a new required runtime field: package and runtime manifest responses strip `icon`, and the package keeps `assets/icon.png`. A client must authenticate only the manager-built relative icon path; an external HTTPS logo must never inherit that authorization. Check catalog trust and package identity before and after reading the shared image cache, and do not hold the market lock or install an extension to draw its preview.
- Test catalog artwork with real transparent PNGs in both appearances (#4780), not only colored mock tiles: a black GitHub mark can decode successfully and still disappear on a dark role fill. Loaded logos need a neutral light backing; a missing or failed logo keeps the earlier role-tinted glyph. PNG publication also avoids assuming every native image loader can decode SVG.
- Catalog display metadata belongs beside the signed entry, not inside its runtime manifest (#4780): an old strict manifest decoder can reject a whole package for an unfamiliar icon field. Keep signed payload bytes intact and sort the API projection, never the verified entries. `MarketView` also has a legacy mirror converted by a Go struct cast; additive fields must be added at the same position there or the old endpoint stops compiling. Preserve absent download counts separately from explicit zero.
- GitHub markets already support repository-relative installable archives through the contents API with the existing market credential (#3363). A branch-following catalog and its packages are separate reads, so publishers must retain immutable version paths; SHA256 detects changed bytes but cannot recover a deleted old archive. Direct private raw-host URLs do not receive the API-bound token. Nonofficial plain catalogs remain unsigned; repository publication does not relax official signature or owner-pin checks.
- A destructive endpoint is not a preflight. `DELETE .../{id}/-/` can return dependency blockers, but when nothing blocks it the extension is removed. Never call it to populate a confirmation dialog. If a client needs a dependency/removal-set preview and the manager does not expose one, keep the standard action visible and disabled with that specific reason; the API change is a separate task.
- `ExtensionView.kind` is a contribution category from `Manifest.Kind()`, not the installed execution runtime. Do not display UI/connectors/voice as a runtime simply because another client does. If the installed declaration's runtime is not in the response, show Not provided and document the missing read-only field.
- Attached extensions can carry installed-looking metadata. Decode the existing `attached` record before deriving market capabilities; source text or an origin alone must not turn an externally running process into a host-managed package. Keep sandbox failures and externally reported runtime versions separate from the saved Enabled preference.
- The paused automatic-upgrade switch still represents the saved preference. Do not render it off because the extension is disabled, and do not submit a dirty configuration draft when changing lifecycle preferences. Manager-bound market checks and permission previews must use the same manager as the settings page, including global automatic-upgrade reads.
- Mirror saves replace both fields, so retire the whole form on credential-generation or manager changes and bind each request to that captured context. A read waiting behind a dispatched write must check its own context again before sending; the original write may still commit. Name the selected manager in both header and query because the hub gives the header precedence over the query. Exercise shared synthetic server state through the real REST client, including late authentication and proxy responses.
- Extension-summary UI tests must count only the current assistant's share of the merged mock list (#9759). `MOCK_EXTENSIONS=1` stamps built-ins once per installed manager; the default Settings page owns `manager == "assistant"` and unstamped legacy items. The loaded usage card can also push later extension rows below the viewport: scroll until the lazy rows exist, then scroll back before opening Example Notes; waiting alone cannot create an off-screen row.
- A new `NavIcon` is a hub feature first, not just an extension change. The hub checks a manifest's `ui.icon` against the icon list compiled into it (`wire.NavIcons`, generated from `schema/extension/view.schema.json`), so an extension that names an icon the deployed hub does not know fails to load whole. Put the icon in the schema and in every client, ship a hub build that carries it, and only then release the extension that names it; until then the package keeps the old icon.
- A node-only extension's top-level `status` is not the hub process's. An on-call `runtime` parks as `stopped` when idle and a manifest with only a `node` section gets a declaration-only `running`, while the program that does the work runs on computers (#7457). In `extmgr.view`, aggregate from `nodes` (`nodeStatus`, `node_status` counts) whenever the hub runs no live process of its own, and keep `disabled` / `needs_setup` / `incompatible` as the hub says them. Clients read the one aggregate line with localized plural wording and must not re-derive the rule from per-machine rows.
- A polled bind response replaces the client's entire prompt (#12688). Keep actionable setup diagnostics in the manager's credential-bound state rather than a request-local string. Persist only the safe outcome needed for localization; regenerate the hint and console URL for every pair poll without retrying remote configuration. Clear the outcome on pairing or credential replacement, and discard results from older credentials saves, including a save of the same app and secret. Carry the actual commit receipt out of the locked save instead of looking up the current sealed value afterward: another save can finish during post-save hooks. Check the pairing lifecycle too, since owner can change from empty to paired and back while configuration is pending. Roll back rejected writes before acknowledging them; when clearing setup guidance as part of an owner commit, restore it if that write fails so the redemption transaction can restore its owner and code.

- Cua Driver (0.38) keeps one current snapshot per window, shared by every session (#7560). A `get_window_state` of a window, from any session label, replaces that window's snapshot, so element tokens another session read from it go stale. Never re-read a window an Agent or the assistant is acting in just to check something; `protectedapps` traces a token by reading only System Settings' windows. Older snapshot ids still answer `since`, from any session: a read of window W with `since: <id>` says `other_window` when the id is another window's, which is how a token is traced to its window without the call's pid (a token carries its own; Cua Driver ignores a `pid` given beside it).
- The hub's session list is a bounded view of a computer, not its inventory (#10941). A node lists a quiet Claude Code chat only for a week, among its 80 newest and once its transcript holds 2 KB, so a rule that lets an extension act only on listed rows takes away chats it legitimately owns, on a busy computer within two days; a stopped Agent takes no message, so for a resume nothing else brings it back. Decide such a rule where the evidence is: the hub refuses what its list says (a row in the health space) and hands an unlisted id, marked, to a node that announces the check, which knows the transcript, record and directories. Make the node's refusal byte-identical to the hub's own 404 so the extension cannot tell a health chat from no chat, set the mark after every fill so the caller cannot drop it, and keep the hub's refusal for nodes that do not announce the check: an older node starts a new conversation under any id it is given. The node's own evidence is bounded too: an engine runtime (Paseo) runs an Agent under the id Persona named it by, with no transcript under that id and nothing in the node's files once the engine stops listing it, so keep the node's record of every start the check must later recognize, and answer what does not depend on the id (the engine is away) before refusing the id. Trust only evidence no later write moves: a resume writes a terminal record anew with the folder it names, so a record says where a chat started only when nothing but the start writes it (an engine runtime's), and that mark must reach the hub's copy or a node restart loses it. Decide the id-dependent answer after every check that holds for any id, or a request those checks refuse tells the ids apart.

- A display profile can outlive its connection and inherit the built-in Assistant's defaults (#17699). Bind an
  extension's read authorization to the connection that validated its route and token. Legacy owner trust comes
  from that connection's own snapshot. A partial snapshot without a profile or a reconnect requires fresh evidence.

## Settings recovery and connector identity

- A failed initial settings read is unknown state, not a fresh install (#12676). Decode into a temporary defaulted value, publish only on success, and gate both mutations and status reports until then; reporting an empty owner can make a downstream manager clear valid pairing state. A later successful lookup must also restart the saved enabled transport, with one shared retry cooldown across readers and writers.

- Recovering the settings value is only half of identity recovery (#12676): a connector may have cached its runner and account-specific Inbox state during startup. Keep the connector registered so its disabled/feed/options settings restore before it can run, gate process execution while identity is unknown or stale, then synchronize and replace it outside the settings lock. Bound the storage read itself, release the settings mutex during I/O, and coalesce concurrent lookups instead of making them wait for that read.

- Dependency recovery must include every independently stored policy (#12676). A readable account record does not make unread connector switches safe: quarantine the connector, then read and apply its durable enabled/feed/options choices before starting it. Keep failed profile synchronization pending for coalesced, cooled-down retries from normal entry points, even after the account record is cached; a temporary runtime quarantine must never become the preference copied into the replacement.

- Registry publication and activation are separate boundaries (#12676). Keep a replacement quarantined until its instance disabled mark is applied, then release the gate and enable only when allowed. Fence every CLI invocation to the currently registered instance too: removing an old instance clears its disabled mark, and an unchanged profile name does not make that retired instance current.

## Manual bot pairing

- Manual Lark pairing has two settings writes: committing the owner/code, then enriching the contact name (#12703). Publish success audits, greetings and assistant notifications only after the owner/code write succeeds; on failure restore the pending code and allow a fresh message with the same text immediately. If only the name write fails, restore that name while retaining the durable owner. Use the real bot event path with independently failing writes to test both contracts.

## Message intake and recalls

- Register pending owner messages before waiting on their inbound predecessor (#12644). A handed-message history cannot recognize a recall of a message still waiting in that queue. Bind both pending cancellation and handed recall evidence to the bot identity, owner, chat and message; serialize the cancellation-to-handoff transition under the same lock, and keep pending records until their handlers finish rather than evicting them with bounded history. Deduplicate pending references and reserve their queue position in one short lock even after the recent-id ring evicts them; release only the reservation owned by that handler and refresh the existing bounded recent history on completion. Bind the production connection callback to its source generation, and check that source and any supplied envelope App ID under the admission/recall lock; same-app credential refreshes retain stable pending references. After local cancellation, retain its exact source in bounded recent history with a canceled state, distinct from a handoff: the assistant recall wire carries only an id, so losing that source makes a wrong DM look unknown. Ownership evidence does not grant receive permission: reapply the current topic and mention policy after the wait. Reproduce the window with real inbound events and a fake assistant blocked inside the first handoff, then use a normal next message as the completion barrier.

## Message readback

- A successful Lark message readback can mark an item `deleted` (#12690). Check that flag before parsing a private reply's parent, resolving its sender, or collecting its media: success alone does not make the quote usable. Exercise the real reply handoff with synthetic old content and resource keys, and assert that the new message's own attachments still arrive.
- A sandboxed Node extension that reports its service "unreachable" with zero egress decisions never reached the proxy (#15707). Node's native `fetch` / `WebSocket` ignore `HTTP(S)_PROXY` unless `NODE_USE_ENV_PROXY=1` is set, so inside the Linux network namespace they fail with `ENETUNREACH`; the hub now sets it with the proxy variables. A process that stays `running` is not a healthy connector: compare `sandbox.egress` counts with the connector's error before blaming the service. A destination kept in an extension's own sign-in record cannot become a grant automatically; the owner allows that one host in the admin UI (`docs/extensions/extensions.md`, "Extension egress rules in short").

## Lark sender-name backfill

- A one-time repair that makes paced API calls needs a resumable position, not just a bigger budget. Backfill v3 read up to 500 member pages per large group within a 2-minute budget at 5 requests a second (about 600 calls). Two large groups whose unnamed senders had left could never fit, and with no position saved every run started again at page 0. The `context.DeadlineExceeded` it returned was classified `other`, so the binding's health showed `failing` and the deploy was rolled back. Make a budget-limited step stop partial and save its cursor. Let only owner-fixable errors (scope, auth) change health. Reproduce with the real family rate on the fake clock (`TestResolveNamesCompletesTwoLargeGroupsOfLeftSenders`), not with the test syncer's unlimited rate.

## Guest traffic

- Guest traffic gets its own bounded list; never share a ring with the owner's entries (#16848). A teammate's question, its refusal and its rate-limit note live in the guest's own book and its own short memory, counted and capped on their own, so a busy group cannot push the owner's dedup, thread bindings or pending cards out of their ring. The guest's reply and its chain of thought are posted through their own calls, never through the owner's progress card.
- Call `pass()` before anything a stranger can slow down (#16848). The owner's messages and a guest's message share one intake, so the guest path releases the next message before it reads settings, parses content, checks the mention or starts a conversation. Anything that waits on the network or the store happens after that, or one slow stranger stalls the owner's chat.
