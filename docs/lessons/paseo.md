# Lessons: Paseo engine (`integrations/paseo`)

Read before changing the bridge (`integrations/paseo`), its node runner (`node/paseobridge.go`), or testing real Paseo. Design: docs/integrations/paseo.md.

- **Expand home paths at the Paseo boundary** (#16985). The start, worktree creation, takeover, and launcher check
  all need the expanded directory for both local validation and Paseo's request. Reuse the worktrees-root helper,
  which follows the Go node's `proto.ExpandHome` rules for the current user's home and native separators.
- **Connect only to the address in home's `paseo.pid`, never default-port fallback** (2026-11-04). Paseo writes PID file immediately with listen:null; fills address after listening. Earlier fallback `PASEO_LISTEN` / `127.0.0.1:6767` connected a temporary-daemon prototype to the live local Paseo and sent agent.create. Missing provider made it fail, leaving only failed `creations/` record.
  - Bridge / node detection now trust PID-file address only, like Paseo CLI.
  - Before temporary-daemon requests, verify `daemonTarget(home)` port equals assigned port.
- **Claude Code `ExitPlanMode` permission passed to Paseo lacks plan body** (tested 2.1.294). Input {}, no metadata.planText. Plan in corresponding timeline tool call `detail.type: "plan"` and transcript tool_use.input.plan. Bridge finds via metadata.toolUseId.
- **Pending requests in Agent snapshots are trimmed**: `sanitizePendingPermissions` drops empty input. `agent_permission_request` event more complete, but either arrives first; never assume input present.
- **Read-only Bash does not request Claude permission**, e.g. echo / ls. E2E approval card needs writing command, e.g. touch.
- **New Paseo 0.14 Claude Agent `runtimeInfo.sessionId` null**, Claude ID appears only after first turn starts. Persona-created sessions use `paseo-<agent id>` stored `persona.session` label; waiting for Claude ID would change identity mid-run.
- **Provider models await warmup**: `get_providers_snapshot` immediately loading; `providers_snapshot_update` after ~1 second. First hello launchers may lack models; bridge rechecks while providers loading.
- **Send reply waits until turn actually starts**, Paseo max 60 seconds, node runtime timeout 30. Loading closed Agent may take longer; bridge waits max 25 then treats as handed to Paseo. Creation same.
- **Subscription event can arrive in same read as reply**: `fetch_agents` reply immediately followed by directory update. Register synchronously while handling reply, not after await, or lose events. Reply also `subscriptionId`, so route `requestId` replies before `subscriptionId` events.
  - The page is then taken after those events (#8129): the code after the await runs once the read is handled. Paseo 0.15 holds a new subscription's updates while it builds the first page and sends them right after the reply, and later pages are built while live updates go out, so a page can be older than an update already applied. Time cannot tell them apart: the end of a turn and Paseo's attention mark move no `updatedAt`. Taken as it came, the page left a finished agent Working, listed an agent archived meanwhile again and dropped one made meanwhile (not on the page, so "gone while away"). Take no page's copy of an id the subscription told of while the pages were read, and count it as seen; the same for workspaces. At connect only the subscription's own updates count: a card's event can come before the subscription exists, and then no update with the card follows.
- **Reading the timeline of an Agent Paseo let go loads it** (#8132, Paseo 0.14 and 0.15.4). `fetch_agent_timeline_request`, `agent.timeline.search` / `list_prompts` and `agent.fork_context` all start with `ensureAgentLoaded`, which relaunches the provider's process (an archived Agent too, "as history"): no read of a stored timeline leaves the Agent stored. Paseo 0.15 lets an Agent go after an hour idle (`closed`), so this hits every quiet Agent.
  - The background readers were not the obvious ones. The iOS app's background sync (`AgentSync`) warms the disk cache of up to 40 recent chats, offline ones included, three at a time, whenever a session's `rev` moves; on Paseo 0.14 a load also moved `updatedAt`, so the `rev`, which kept the cycle going (22 relaunches of 9 Agents in two days on one machine). The manager's triage lines right after each load were a consequence: a load shows as offline → working (`initializing`) → done, which the manager takes for a turn end.
  - A read's shape cannot tell an App opening the chat from a prefetch (both page from the end). The watch is the one signal, and the web and Android read their first page before they watch. So the bridge reads such an Agent only for a watch, a send, a rewind or a mode change, answers other reads from its last read while that is all of the conversation, refuses the rest with `not_loaded`, and reads nothing for a watched Agent Paseo let go (the closed update would otherwise reload it every hour a chat is left open).
  - Test it against the fake daemon's `loads` (it loads an Agent on a timeline read, as Paseo does) and, for real, in the Codex e2e, which counts `codex app-server` launches: a background read of the archived Agent must start none.
  - A client that reads before it watches gets that refusal on every open (#8321). The web and Android showed it ("Couldn't sync messages" on Android) for the second or three the watch took to load the Agent, then the history. A refusal that the watch the client is about to send resolves is loading: keep the chat's loading state until the watch's first items, and say the refusal only after a read's time (Android also on the hub's `error` for the session, when its backlog read failed too; the web's first screen has no room for that listener). Hold back the client's own stale-page or catch-up reads meanwhile too: they are refused alike, and their failures would show the error the wait hides.
- **Paseo's `config.mcpServers` entries need `type: "stdio"`** (0.13.2 schema), which Claude-style `mcp.json` entries omit. The bridge adds it and sets each server's `PERSONA_SESSION_ID` to the Agent's `persona.session` label (#3655); the provider's own session id would break the task link.
- **A provider that takes no MCP servers fails `agent.create` when `config.mcpServers` is set** (0.13.2 `requireExternalMcpSupport`: `Provider '<name>' does not support MCP servers`, an `error` on the response, before any Agent is registered). Paseo keeps a record of each creation request under `creations/`, and the failed one stays; the bridge's one retry without `mcpServers` simply uses a new Paseo agent ID, and only for that message. The Persona session ID must not change with it: the start may already have returned its row (a refusal later than the 25 s wait), so label and `PERSONA_SESSION_ID` stay the first request's. The fake daemon (`test/fake-paseo.js`) refuses MCP servers for `noMcpProviders` (slowly with `refuseDelay`) and checks the stdio shape Paseo's schema needs.
- **A Paseo workspace is not a tab** (#4493). A slot is one tab, and the apps draw the sessions that share a `slot_id` as that tab's panes: one row for all of them, a pane strip in the chat, a stopped one shown as replaced by another. A workspace's agents are separate conversations, any number of them: on one real machine a workspace had 78, of which 72 were created by other agents, and all 78 were one row. Send the workspace's title as `slot_name` and no `slot_id`.
- **An agent another agent created is quiet in Paseo and loud as a plain session** (#4494, Paseo 0.14). Paseo labels it `paseo.parent-agent-id`, shows it under its creator in the same workspace, archives it with its creator, and notifies nobody when it stops (`broadcastAgentAttention` returns early for it). It still sets `requiresAttention` on it, which only opening the agent in Paseo clears. Listed as an ordinary session, each one was a "done" push and a lasting Unread.
  - The workspace status follows `resolveWorkspaceRootAgent`, not the label alone: one created from another workspace is that workspace's own agent and its attention counts; one whose creator is gone, and a ring of creators, show nowhere.
  - A list that keeps only the agents whose direct creator is one of the user's own drops an agent two levels down, even while it waits for a permission. The node refuses a card for a session it was not told of, so that request never reached the phone. Follow the whole line of creators, and test with a fake node that refuses cards for unlisted sessions (`startFakeNode(t, { strict: true })`).
  - A creator Paseo closed (`closed`: it let the process go) while its agents run is not "offline" for a list of what runs: their reports wake it.
- **Paseo 0.14 runs Claude Code's command line itself** (#4521). Every transcript of its agents says `entrypoint: sdk-cli` from the first line to the last, as a script's `claude -p` run does, not `sdk-ts` as a host on the Agent SDK writes. Nothing in the transcript tells the two apart; only Paseo's agent records do. A filter written from what one host writes (#3931: "interactive hosts run through the Agent SDKs") hid the conversations of every archived Paseo agent. When a rule keys on what a program writes into a transcript, check what the other hosts write.
- **Paseo's removal of an agent from its list does not say why.** `agent_update {kind: "remove"}` is the same for an archive, a delete and an agent that only stopped matching the list (its provider switched off). `fetch_agent_request` tells them apart: an archived agent's record comes back with `archivedAt`, a deleted one is `agent: null`. Ask only about an agent that was listed: a removal also comes for every change of an agent the list never had (Paseo's internal agents, which name the others: a dozen removals for each agent started with a prompt), and an archive is told twice. Archiving an agent archives the agents it created in its workspace too (`cascadeArchiveChildren`); a delete does not cascade.
- **Paseo tells a delete only to the client that asked for it** (#4629, Paseo 0.14). `handleDeleteAgentRequest` sends `agent_deleted` and the list's `remove` to its own session. Every other client sees one last upsert with `status: "closed"` when the agent was loaded (the delete closes it first, and removes its record a moment later), and nothing at all when it was not. A list kept from updates alone keeps a deleted agent until it reconnects: ask for the agent after one closes, and compare with the directory now and then. A fake daemon that announces a delete to every list hides this; the end-to-end check deletes through a second client.
  - Paseo 0.15 tells every client (#8129): a delete goes through agent-manager `notifyAgentRemoved` to each session's list as a removal, archived agents' too. A bridge that asked only about removals of agents it listed kept a deleted archived row for up to 2 minutes: ask about one it keeps archived as well (a removal of an archived agent also comes when its record changes, so asking, not taking it as gone).
- **`fetch_agents_request` with `filter.includeArchived` lists archived agents among the live ones**, in the order asked for; an archive sets `updatedAt` to `archivedAt`. So "archived lately" is read newest first until a page ends before the window, not by a fixed number of pages.
- **An id the transcript does not carry is lost when the session is listed as its transcript** (#4771). A session Persona starts in Paseo is `paseo-<agent id>`, chosen before Claude Code has a session id. Named to the node as an archived agent's transcript (#4521), it came back under the Claude session id: a second id for one conversation, and the to-do link, pin, archive mark and read state kept under the first one were left behind. The node lists a named transcript under the transcript's id, and nothing in the transcript says otherwise. A session with an id of its own stays the runtime's row (`offline`, with `transcript`) while it is archived.
- **What Paseo 0.14 does with an archived agent.** `send_agent_message_request` takes it back from the archive first, then loads and runs it (`sendPromptToAgent`, `unarchive` on by default), its labels untouched. `import_agent_request` for a Claude session an archived agent has restores that agent rather than making another, found by `persistence.provider` and session, and writes the request's labels over its own: a takeover that sends the transcript's id as `persona.session` renames the session. `set_agent_mode_request` and `set_agent_thinking_request` refuse it (`ensureUnarchivedAgentLoaded`); `fetch_agent_timeline_request` loads it without restoring it; `update_agent_request` renames its stored record and tells no list (the directory lists only agents Paseo has).
- **Paseo tells the list of an archive before it answers the archive request** (`archiveAgentForClose` emits the stored record, then `agent_archived`). By the time the bridge has the answer, the list's `remove` has taken the agent's copy away: anything wanted from it (its placement) is read before the request is sent.
- **Retaining an archived Codex row also needs the archive ledger** (#5129). Extending `archivedUnderOwnId` alone leaves `noteArchived` dropping agents without a Claude transcript. Keep Persona-labelled Codex agents with a known thread, deduplicate their threads separately from Claude transcripts, and never put their IDs in `unlisted_transcripts`. Otherwise two archived Codex agents collapse into one because both have an absent transcript. Exercise archive, reconnect and restore through the bridge, with an unlabelled Paseo-originated agent as the negative control.
- **Paseo's workspaces are followed like its agents, and its answer to a creation is thinner than its update** (#6295, Paseo 0.14). `fetch_workspaces_request {subscribe: {}, page}` lists them and sends `workspace_update` (`upsert` / `remove`); a workspace's status moves with every turn of its agents, so tell the node only when the rows it lists change. `workspace.create.request` answers with a descriptor that has no `project` yet (no placement until Paseo's next update of it): keep the subscription's richer upsert when it came first, and find a just-made worktree by its `workspaceKind` and folder, not by its placement.
- **Create a worktree workspace without an agent** (#6295). With `agent` in the same request Paseo renames a new branch after the first prompt, asynchronously, so the branch the node checked and reported is not the one that stays. And `action: "checkout"` with a branch another worktree has checked out does not fail: Paseo makes another branch of it, so refuse such a branch before asking (`git worktree list --porcelain`), as for Orca.
- **A stale workspace id must be refused, not dropped** (#6295). Paseo files a worktree folder handed to it alone under a project record of its own: a start that drops a workspace id Paseo no longer has puts the agent in a new workspace somewhere else. A workspace Paseo still has, agents in it or not, is a valid target.
- **A Paseo workspace id where a terminal host's used to be** (#6295). Session rows now carry Paseo's `workspace_id` (`wks_…`), and "Open terminal here" and the preview's Start sent it to herdr. The node maps a runtime's workspace to the terminal engine's space that holds the folder, else a new one there (`newShell`, `preview.start`; the first space by id was an unrelated one), and the web and iOS offer Start only for sessions with a terminal.
- **Paseo renames the folder it is asked for, and steps around anything there** (#6295 review, Paseo 0.14 `createWorktree`, `slugify`). The
  requested name is slugified (lowercase, `[^a-z0-9]+` to `-`, at most 50 characters, cut at the last hyphen past the 25th), and when anything
  exists at `<root>/<slug>`, an empty folder too, it makes `<slug>-1`, `-2`… instead. A node check on the typed name or on "empty is fine" passes
  and the worktree lands elsewhere: check the slug's folder (`runtimeFolderName`, its test cases are Paseo's own answers) and refuse anything
  there. Long agent names lose their `-10` to the 50-character cut and land on the base folder: shorten the name, not the number.
- **One deadline for a create that asks twice** (#6295 review). prepare (30 s) and create (up to 140 s) each inside the hub's 150 s still add up
  past it, and the user then sees the hub's timeout while Paseo goes on. Bound the whole operation once (145 s) and say when it ran out.
- **Paseo's archive removes the folder whatever runs in it** (#6297 review; Paseo 0.14 `archiveByScope`). It archives the
  workspace's agents, running ones too, kills its terminals and force-removes the worktree, with a herdr Agent `cd`'d into it as
  well; when the disk removal fails it only logs it (`removedDirectory: false`) and still succeeds. So the node checks, at the
  preview and again at the confirmation, that no session of the workspace is at work and no Agent of any engine runs in the
  folder, and judges the outcome by the list and the disk, never the answer.
- **Where Paseo puts a repository's worktrees** (#6295, Paseo 0.14 `deriveWorktreeProjectHash`): `<worktrees root>/<hash>/<slug>`, the hash the first 8 base-36 characters of a SHA-256 of the repository's real path, the root `worktrees.root` in its `config.json` or `<home>/worktrees`. Prefer the folder of a worktree Paseo already made of the repository; the derived one is only what the dialog shows first, and the answer names where the worktree really is.
- **Archiving a worktree workspace in Paseo deletes its folder, forced** (#6297, Paseo 0.14 `archiveByScope`, `deletePaseoWorktree`). `archive_workspace_request` archives the workspace's agents and record, then, for a worktree Paseo made and no other workspace uses, removes it with `git worktree remove --force` and a recursive delete: uncommitted work goes, the branch stays. A main checkout, a folder or a worktree made elsewhere is only archived, its folder left. So the node shows the changes and has the user confirm them before it asks, and refuses anything Paseo did not make. Paseo answers `archivedAt` even when the disk removal failed (it only logs it): check the folder before calling it deleted.
- **A project rename reaches the workspaces, not the agents** (#6297). `project.rename.request` sets the project's `customName` and sends its workspaces' descriptors again, with the new `projectName`; agents keep the placement of their last update. The bridge names a space by vote over agents' and workspaces' placements, so the old name would win until each agent changes: update the placements the bridge keeps when Paseo accepts. `workspace.title.set.request` is the same for a workspace's `workspaceName`. An empty name clears the custom one (Paseo's derived name comes back), so never send one.
- **Android names a space by its session's workspace** (#6297). Its Rename space sends `workspace_id`, which for a Paseo session is now the workspace's (`wks_…`), not the project's: the node takes a runtime workspace id to the space it is in, and the hub finds the old name (for pins, mutes and to-do links) from the runtime session in that workspace.
- **Paseo forks an agent's Claude session when it goes on after an API error** (#6709, Paseo 0.14, Claude Code 2.1.294). A turn the model never answered (a gateway's 499, for instance) is dropped before the next message: Paseo rewinds it with the Agent SDK's `forkSession`, at the last answered turn, into a new transcript beside the old one. The agent's `persistence.sessionId` moves to the fork, and every record the fork copied ends with `forkedFrom: {sessionId, messageUuid}` (the last key of the line, after the message, so a prefix of the line does not show it). On one machine, an agent that hit the error four times left five transcripts in one project folder.
  - An id keyed on the current Claude session moves with each retry. The open chat answered 409 ("no such session"). Each failed turn's "needs you" card stayed under an id nothing listed: "Fixed, go on" could not reach it and put it up again under a new id, and only the card's 24 hours ended it. Paseo's own rewind is no different from Persona's, which #6293 already guarded with the label. The bridge now keeps the id on any move it sees, and follows `forkedFrom` for moves it missed.
  - A fork's records keep their original timestamps, so the first record of every transcript in the line is when the conversation began. That is how the bridge tells an agent's own line (begun after the agent was created) from a conversation handed over from another agent: Paseo plugins that move a conversation to another provider fork the previous agent's session into a new agent. Never follow such a line into another agent's session.
  - The manager now withdraws a card whose session stays missing from its online computer's list, and one whose answer the computer refuses as `not_found`. A card can only end that way while the session is gone for good. An engine that is merely away (its bridge leaves the node after 30 seconds) also takes its sessions off the list, which is why the manager waits 10 minutes first.
- **ACP providers approve through a switch, and Grok names its tools in its input** (#7758, Paseo 0.14, Grok CLI 1.0). A provider Paseo runs over ACP (`extends: "acp"`, such as Grok's `grok agent stdio`, and Copilot or Cursor) lists no permission modes, or only its own; what decides whether it asks is Paseo's Auto Accept feature (`features[].id === "auto_accept"`, set at creation with `config.featureValues` and later with `set_agent_feature_request`). OpenCode has the same switch. A mode sent to such an agent does nothing, so Allow all has to go through the switch, and the switch being off proves nothing: Grok's own always-approve setting answers its prompts before they reach Paseo. A closed agent's snapshot lists no features at all; Paseo loads the agent before it sets one.
  - Grok's ACP raw input carries its own tool's name as `variant` (`ListDir`, `Monitor`, `TaskOutput`, `KillTask`, `UseTool` for an MCP call). Paseo passes such a call on as an `unknown` detail named `other` or after the ACP title (``List `/w` ``), its output Grok's own object (`{type, Content: {content}}`, `{type, Result: {...}}`, `{type: "MCP", output: {OkayOutput}}`). Read the name from `variant`, never from the item's name. Grok's tool search arrives as `plain_text` titled `Search tools: "<query>"`, with no input at all.
- **Every Paseo provider that is neither Claude Code nor Codex is `agent: "paseo"`** (#8144). The bridge reports Grok, Kimi, Cursor or TRAE CLI with the engine's id, and the node labels a row or card that has no label of its own with the engine's name ("Paseo"). A client keyed on `agent` alone treated them all as one agent. On iOS, New Agent offered Claude Code's five modes, so a Plan Only remembered from a Claude Code start made the next Grok start fail (`readonly_unsupported`). The share card drew Claude's mark for Grok, child cards said "paseo", and cards said "Tell Paseo what to do instead". Key a start's modes on the launcher (`source` `paseo` with its own `agent`), and names and marks on the row's `agent_label`, else its `launcher` (Paseo's provider id).
- **Paseo unloads idle agents and then describes them from their stored record** (#8133, Paseo 0.15.4). An agent idle for an hour (`idle-runtime-cleanup`), or every agent after Paseo restarts, is `closed`, and what Paseo sends of it later (its directory, an update after `workspace.clear_attention` or a rename) is `buildStoredAgentPayload`: `requiresAttention` kept, `updatedAt` unchanged by the unload, but no `features`, default `capabilities` (no rewind) and no `availableModes`. Mapping `closed` to Not running before reading the mark dropped an unviewed finished agent's Unread until something loaded it again, which then brought it back with a new time; reading Auto Accept off that payload dropped Allow all. A stored payload's missing lists say nothing about what is on: keep the mark's meaning across the unload and the features last seen.
- **An archived agent's record still says what its provider can do** (#8133). The copy the bridge keeps when an agent is archived is its live snapshot (rewind supported, modes listed), but Paseo refuses every change to an archived agent (`ensureUnarchivedAgentLoaded`). A row built from that copy offered Rewind, the mode and effort chips and the model picker, all of which failed: an archived row takes them away in its own `capabilities`, which node now narrows by for `modes` and `model` as it did for `rewind`.
- **Paseo records no provenance for an agent's title** (#8133, Paseo 0.15.4). A rename (`update_agent_request` name, its App's, another agent's), `create_agent`'s `title`, an import's and the title derived from the first prompt all land in one `title`. The derived one is exactly `deriveInitialAgentTitle(prompt)`: the first line with words, white space collapsed, at most 60 UTF-16 units, so a cut may split a surrogate pair (U+FFFD once it reaches Go). Paseo's own workspace naming tells them apart the same way (`applyGeneratedWorkspaceTitle` replaces a title only while it equals the prompt's). Compare with the prompt as it was sent, blocks in: one that opens with one of Persona's `<persona-context kind=…>` blocks is titled after the block's first line (the node's first prompt keeps such blocks). An agent another agent created has its prompt wrapped in a `<paseo-system …>` envelope before Claude Code sees it, so its transcript's first line is the envelope and its title, derived from the bare prompt, never matches: it stays a title nobody replaces.
- **A process's name is not its program, and `paseo.pid` outlives its process** (#8134, Paseo 0.15). Paseo's processes set `process.title` ("Paseo Supervisor", "Paseo Daemon"), and on macOS that is what `ps -o comm=` shows, so the node never found the Paseo App's Node.js there: read the executable from the kernel (`KERN_PROCARGS2`'s executable path, which the title does not overwrite; `/proc/<pid>/exe`). And a `paseo.pid` left by a Paseo that crashed, or from before a reboot, names whatever has that pid now; Paseo itself counts a lock from another boot as abandoned (`isPidLockOwnerRunning`). The node ran that program with `-e …` and `ELECTRON_RUN_AS_NODE=1` to ask its version: take the pid's executable only while the daemon answers at the file's address, and only a Node.js or an Electron app.
- **A dismissal from the phone is not a person's "Return to computer"** (#8128). `rt.ask` answers `{dismiss: true}` for a hand-back, an expiry, no hub and the hub's own answer for a card it ended (cancelled after a link drop, 3 minutes after the node left; expired), and the node used to answer it too when its hub link dropped under a card with no `tool_use_id` (every Codex, ACP, OpenCode and pi card), before it told the runtime the hub was gone (`detach` runs after `Serve` returns). Taken as a hand-back, such a card never went up again while the session kept saying it needed the user. The node now marks a card with the runtime's own id resumable, so a drop answers `node_gone`; the SDK waited for the next node 2 minutes from when the card went up, not from the drop, so a card up any longer was dismissed at once all the same. The bridge keeps a hand-back only when it came while the card was up and the hub there, and puts any other card up again (a new id once the hub may have ended the old one: it keeps how a card ended, an answer included, under its id).
  - Paseo tells a permission's resolution to the subscriptions under the permission's own id, which the bridge answers it under: `route` settled the answer with that event and the subscription never heard it. The fake daemon now sends them in Paseo 0.15's order (the agent's update, the subscription's event, then the reply).
  - An answer removed from the bridge's pending cards before it was sent was lost when Paseo's socket was down (only logged), and an update of the agent in between put its card up again. The card now stays pending until Paseo confirms the answer, and one sent while Paseo is away waits for it.
- **A start answered before Paseo is done must stay listed, and say so when it fails** (#8130, Paseo 0.15). The node waits 30 s for a start; Paseo may take longer (a provider slow to start, a restart, a long import). The row handed to the node vanished at the bridge's next list, and a refusal after the wait went nowhere, not even the log: the wait (`within`) logged only a rejected promise, never an answer of `accepted: false` or `agent: null`. List such a start as `starting` until Paseo answers, turn it `offline` with `start_error` when Paseo refuses, and log a message refused late. A takeover's first message comes in a send of its own right after the takeover: with a hard limit on the import the takeover failed while Paseo went on importing, and the message, sent nowhere, was lost. Let it wait for the import. And a listed row makes the node route every later call about that session to the runtime (`known`, kept after the row leaves): a takeover that failed late must not stay the runtime's there, or its conversation can no longer be read or continued. The node remembers only rows that are neither starting nor failed, and the next message to a failed takeover tries it again.
- **Paseo 0.15's creation service dedupes by idempotency key, and only by it** (#8130, Paseo 0.15 `CreationService`). `agent.create.request` goes through `CreationService.create` with `key: idempotencyKey ?? requestId`: without a key every request is a new creation, so a request asked again after a dropped connection makes a second agent. With a key, the same request (every field but `requestId`, `type`, `subscribe` and the key: the agent id, config, labels, prompt and workspace) gets the agent made for it, or waits for the one being made; another request under that key is refused (`agent_request_key_conflict`), and one cut off by a daemon restart answers `agent_request_outcome_unknown`. Give each attempt a key of its own, send the very same request again, and after a reconnect look in the directory first.
- **Every provider but Claude Code and Codex reports Paseo's own id as its agent** (#8142, Paseo 0.15). Rows and launchers of Grok, Kimi, Cursor, TRAE, pi and OpenCode all say `agent: "paseo"`, so anything keyed or named by `agent` lumps them together and shows the engine's id: the node labelled their cards "Paseo" (it took the row's label only when the row's agent differed from the runtime's), and the web's pill, model panel, Agents filter and work-session Harness said "paseo" and put every provider under the first row's label. The provider is in `launcher` (rows) or `name` (launchers), its label in the row's `agent_label`: key by the provider, name by the label (web `providerAgent`). Paseo gives a provider without a configured label its id as the label, so a label still says which mark it is.
- **An engine's "default provider" is another agent and another account** (#8140, Paseo 0.15). A start with a launcher Paseo did not have went to it as `shell_launcher`, and the bridge ran Paseo's default provider: a Codex launcher started Claude Code, a gateway's launcher ran on another account, a provider added in Persona never applied its gateway or key, and the model and effort the start chose were dropped unsaid (#6192 had made that drop deliberate). Where every start goes to an engine that runs only its own providers, list only those, let one of the same kind stand in and say so, and refuse otherwise (`docs/integrations/paseo.md` "A launcher Paseo does not have"). Two more traps on the way:
  - A name both the login shell and Paseo have was resolved two ways: the form, the models, Test and the start options asked the shell (`runtimeOf` lets the shell win), the start went to Paseo. Every check that describes a start must resolve the name as that start will (`runtimeOfIn`, by the start's host).
  - The main chat runs the computer's own launchers on its command line whatever the engine, so its menu and readiness must keep reading the machine's own list: only a new Agent's start asks for the host's (`launchers.list {host}`).
- **What the node remembers of a runtime outlives what the runtime says** (#8131). The node keeps every id a runtime ever listed (DSH lists its latest 80 of thousands, and an older session is still its own), and sends every call about one to that runtime. An agent Paseo lists under its Claude session id and then archives is named back as an unlisted transcript, which the bridge no longer has an agent for: every read and message was refused ("no such session") until the node restarted and forgot the id. An id the runtime names in `unlisted_transcripts` and no longer lists is the node's, whatever it listed before.
- **Import an archived agent's session with that agent's own provider** (#8131, Paseo 0.15 `importProviderSessionNow`). Paseo finds the record to restore with `listByProviderSession(provider, sessionId)`; asked with another provider (the machine's most recent one) it imports a second agent beside the archived one, on the same Claude session and the other provider. The same goes for Paseo's own provider switches: two agents with one `persistence.sessionId`. Indexed by session id alone, they were two rows (the older one labelled, the newer one under its Claude session) or the message went to the older agent's provider; the newer one takes the older one's id now, and a message goes to it unless the older one is still at work.
- **A runtime that leaves takes its rows with it, and Paseo's transcripts do not come back on their own** (#8131). Paseo stopped for half a minute, the computer switched to another engine: the bridge leaves the node, and its rows go. The transcripts behind its Claude rows say `sdk-cli` throughout, so the offline list took them for one-shot runs and left them out too, and the node refused to read them because their runtime was away; the doc said they fell back to Not running. Keep a runtime's rows whose conversation is a transcript here when it leaves, under their own ids (a transcript's id would be a second id for a Persona-started session, #4771).
- **Each provider asks for an MCP tool in its own words, and a tool policy is not a free preapproval** (#8141, Paseo 0.15.4, Codex 0.167). A check that keys on Claude Code's `mcp__<server>__<tool>` name answers only Claude Code: its permission request names the tool so, but an ACP agent's request is named after the ACP kind (`other`, with the tool in its input: Grok's `UseTool`), OpenCode's after its permission key `<server>_<tool>`, and Codex asks through an MCP elicitation whose params Paseo trims to the server (`metadata.serverName`) and Codex's message, `Allow the <server> MCP server to run tool "<tool>"?` (`CodexMcpElicitation`). Recognize the tool in each shape, and leave anything that names it no known way to the card.
  - Paseo's `toolPolicy` does more than preapprove: on Codex it sets `enabled_tools`, so that server offers the listed tools only; on OpenCode a policy turns Auto Accept off for that agent (`!config.toolPolicy && auto_accept`: Paseo's newer OpenCode session never auto-accepts with one, the older one not until the switch is set again), so an Allow all start would ask for every tool again. Pass the policy to Claude Code only, and answer the other providers' asks for those tools in the bridge.
- **What else a reconnect left behind** (#8129, Paseo 0.15.4).
  - **A read that failed is no answer.** The archive was marked as read even when reading it failed, so the node was told there were no archived sessions (`unlisted_transcripts: []`) and dropped the ones an earlier bridge had named; the sweep read the archive again only when it already knew archived agents, so nothing healed until the next reconnect. Name nothing until a read succeeds, and try again.
  - **Live text belongs to its connection.** Paseo replays none of it to a new connection, nor the end of a turn that ended meanwhile: end it when the socket drops, or later chunks are added to the old text and a finished turn's text stays up.
  - **A keepalive timer does not run while the machine sleeps; the wall clock does.** Silence measured as `Date.now()` minus the last frame closed a healthy connection at the first tick after a wake, without a ping. Measure from the wake (a tick long after the last one) and judge by the answer to a ping, as Paseo's own client does. Say who closed the connection: closes the bridge makes itself (keepalive, hello timeout, failed setup) were logged as "Paseo closed the connection", and a dropped socket (`1006`) the same way.
  - **Paseo reads the hello's `appVersion` as a version of its own app** (session.ts `isAppVersionAtLeast`), and decides what a client gets by it. The bridge's own string parsed as NaN; only the `all_providers` capability kept every provider visible. Send none.
- **What another Agent sends an Agent reads as the user's words unless it is parsed** (#8220, Paseo 0.14). Paseo wraps another Agent's message, a child's notice and a schedule's run in `<paseo-system>` and gives it to the provider as the user's input, so the Claude transcript and the Codex rollout hold it as a user line: the apps showed the raw envelope in the user's bubble, and everything that tells the user's words from others (injected-message detection, task briefs, chat search, the send echo match) took it for the user's.
  - The versioned envelope is XML-escaped (attributes and body), so its first closing tag ends it; a batch is several envelopes separated by blank lines, in one string or one text block. Give the later ones item numbers no block has.
  - The bare form has no escaping and no batching: schedule runs still use it, and older Paseo sent child notices that way (`Agent <id> (<title>) finished.`), which transcripts keep.
  - Paseo's timeline already projects envelopes into `agent_message` / `heartbeat` tool calls, so the bridge maps those, not text; it cannot tell input that started a run, so it marks no wake.
  - Accept exactly what Paseo's own `parseAgentMessages` accepts: the whole input, line breaks between envelopes, version 1, a message id, valid escapes, a known kind and event, no empty title or server. Anything else stays user text, so a quoted envelope in the user's own message is never eaten. A trimmed match took `…</paseo-system>\n`, which Paseo passes on unquoted, for its own.
  - A bare envelope is always Paseo's (Paseo 0.11+ quotes one a person sends as a `user-message`), so one of a kind not known here is a notice of its first line, not the user's words.
- **Where a session's items come from can change under a send** (#8358, Paseo 0.15.4). A runtime's session reads the runtime's own items until its row names a Claude transcript the node has, then the transcript, with other line ids and seqs: a new session before its first turn, a takeover whose answer named no transcript (as before #8225), a list that left it out. The node tied a message's `client_msg_id` to the runtime's line while that was the content and kept that line, so the transcript's copy never carried it; a send recorded meanwhile was looked for past the runtime's seq, which the transcript may never reach. An echo record now says where its seq and line count (`in`), and is looked for again where the items come from now, by its words and time. A line found in the transcript stays, so a runtime batch matched later does not take it back. A record from an older node has no `in` and is tagged wherever its line is, as before. Anything else keyed by item ids or seqs of a runtime's session has the same trap.
- **An end-to-end check reads the state it asserts, not the last push** (#8358). The node pushes its session list a moment after what changed it: `node.info` stops naming the bridge before the list without the bridge's rows arrives, and a row names its forks (`aliases`) once the node has found their transcripts, which can be a list after the row is back. Checks that read `node.sessions()` once right after such an event failed about every other run. Wait for the asserted rows with `until` and a limit, and keep the check's own condition for the verdict.

## A catalog scope includes aliases, checks and shared mutations (#8942)

A shell launcher and a Paseo provider can share a name while running different accounts. Assistant model discovery
must follow the process that runs the conversation, and every cached projection of that answer must carry the same
scope: IDs, aliases and the default. Scoping the ID set alone made a later alias lookup read the Agent cache or no
cache at all. The main conversation's readiness check also needs the assistant purpose, independently of a generic
Settings Test. Test both cold and Agent-primed caches and the actual readiness call.

Custom model IDs are shared between these catalogs. Forget removes the row in both, and marks reads that overlap the
operation so a late response cannot restore a successfully deleted row. Failure restores only that ID while preserving
newer catalog data; a fresh read after success may show an ID the user has typed again.

The assistant-purpose query does not select a manager: the `/machines` routes are not automatically scoped by the
assistant switcher. Capture the manager when reading its catalog, send its header explicitly, and include it in cache
and in-flight request keys. Keep generic Agent reads on their existing default-manager route. Changing the selected
manager must refresh the pill even when the machine and launcher names stay the same.

## Native background work is independent of the foreground turn (#9320)

Paseo 0.16 adds `backgroundWork.count` to agent snapshots and a separate full inventory through
`agent.background_work.list.request` and `agent.background_work.update`. An idle foreground agent can still own live
shell commands or monitors. Follow the advertised `agentBackgroundWork` capability, subscribe before reading, and treat
an unavailable inventory differently from an empty one. A positive summary must not look finished while the details
are pending or a read fails. In-flight replies belong to their connection and inventory revision; a later completion
or archive must not be undone by an older response. Reconnects must fetch task identities even when the count is unchanged.

Reuse the native task ID when merging with Claude's local transcript; otherwise one process counts twice. Keep the
transcript's output path and command when both sources report the same task. Include native work when deciding whether
a delegated agent has finished, pinning active rows, and protecting worktree deletion. Those checks cannot rely only on
foreground `status`. The real Codex regression uses a file-watching process and a fixture-controlled exit, proving that
the task remains listed after the answer and disappears after exit without opening the chat or using a real model.

## Creation needs project identity, not only a path (#9726, #14844)

Git resolves a symlink spelling to its physical checkout. Paseo 0.16's project registry matches root paths by spelling,
so handing it only that checkout can allocate a second project. An explicit workspace supplies the project without folder
resolution; folder-only creation requires a fresh project list. A main-checkout project takes priority over legacy records
rooted at a linked worktree or its subdirectories. At the selected physical root, duplicate records prefer the one registered
at the physical path, then more workspaces, then the lowest project ID, never registry order. With no match, creation passes
Paseo the physical path so a symlink spelling cannot seed another duplicate. Different matching non-main roots remain ambiguous for new creation. An unavailable list is not
an empty list. Use checkout roots rather than remotes so independent clones remain independent. Read symlinks afresh for writes,
outside the display cache. Main-project preference must not make an existing worktree workspace depend on that fresh read: on
failure or ambiguity, an implicit start falls back to the old owner-less lookup and rethrows only when no workspace matches.

The direct Agent route reaches `findOrCreateProjectForDirectory` too. Its request has no project ID field: resolve ownership
before choosing an implicit worktree workspace, reuse an exact directory workspace owned by that project, or create a keyed
directory workspace first and pass its workspace ID to Agent creation. Keep the new step inside the existing pending-start
flow so a slow creation remains visible. A later Agent failure leaves that workspace available; never remove a project or
move existing sessions as part of alias repair.

The real Codex E2E registers the alias project without a workspace, then calls the real node with the alias. This forces
Git's physical-root handoff; an existing source workspace can hide the original defect in Paseo's own fallback. It explicitly
creates duplicate records at one physical root to prove stable path-only and direct-Agent ownership, while selected workspace
ownership still wins. The bridge tests use a real linked worktree for main-project priority and keep different non-main roots
as a refusing control. All of these resources belong to isolated fixtures.
