# Android interface styles and design system

Since 2026-10-31, the Android App's visuals and interaction have been redone wholesale. As the user asked, all three directions became themes, switched in **Settings › Interface style**; the default is **Glass**.
The old design (the parts of `docs/archive/redesign/` about appearance, layout and interaction, and the HTML prototypes removed in #9030) is superseded by this document.

## 1. Three styles

Pages are written once. Each style provides its own design tokens (palette, typography, shapes, motion), component skins, and the App shell and navigation. Interaction differences live in components rendered per style; page code does not branch.

### Compact iPhone reference

The maintainer requested visual alignment in #2589, not only removal of the four-destination navigation. The reference is the current compact iPhone default: Liquid Glass, Match Interface Style, Standard text size. `HomeTokens`, `HomeChrome`, `JShellDrawer`, `JSettingsSheet` and the default Glass tokens hold the application-owned geometry and surfaces. The drawer pushes an unchanged-size page to the right; Settings has an independent secondary stack inside its sheet, with root Close distinct from child Back. Default home chrome uses a neutral tint, the sidebar's New chat button fits its content, and count badges keep readable text. The main composer is opaque, not refractive: idle is attach / Ask Persona / microphone; editing exposes the secondary tools below the text. `AssistantAnswerFrame` boxes final home replies in the iPhone's pale gray, while intermediate work narration stays inside its existing collapsed summary. Default home user messages use the new layout's pale blue; custom bubble colors and alternative styles are retained. Repository Agents have wrapping filters and a folded search, with computer selection retained in the list menu.

This is a reference contract, not a claim of identical platform rasterization. Android keeps its lawful system font, icon assets, IME and touch targets. Glass draws the iPhone's colors as they are and holds iOS's floors (white on the accent 3.5:1, links 3:1, words on the bubble 4.5:1; decision 2 of #4194), so its secondary text is iOS's gray, about 3.3:1 on light pages. Screenshot acceptance must compare the actual final APK with the native reference in both themes.

The Glass home switcher's outer capsule uses a lightly tinted Haze surface with a shallow blur and refraction concentrated at the curved edge. The capsule glints from the upper leading edge and brightens and grows slightly while pressed. The selected segment remains one neutral pill. Frosted and Solid use a thin gradient edge, and Reduce Motion keeps the static glass. On these paths the pressed label changes tone, preserving a single selection and the usual focus and hover states. The unplaced width probes do not create glass renderers.
On press, Haze updates the touch highlight while the draw transform keeps the backdrop coordinates stable. This lets the capsule grow without recording a new backdrop just because it changed size.
The trailing home actions use the same material on 48dp circles. On a liquid press a lone action grows by one third with its glyph and brightens. Adjacent actions brighten at a fixed size. Only drawing changes, so the touch target and backdrop coordinates stay fixed. On the compact Glass Agents home the selected tab opens list settings when connected. When it has to explain the connection, a separate More button opens list settings.

The folded Glass Agent header uses the shared neutral chip fill for its centered title. In compact windows the bare accent-colored More button opens the same session actions as the expanded header. The composer uses the Shell's opaque card with a compact idle height and native Android touch targets. The expanded toolbar can dismiss the keyboard, and its model chip uses the room left by the other controls to show the model and thinking effort. Expand opens the same draft editor. Attachments and mentions are in the add menu.

### 1.1 Switching and saving

- Entry: Settings › Interface style (`AppearanceSettings`). Each of the three options has a small preview drawn with that style's real components; tapping one applies it immediately, no restart. The preview is a one-third-size Agents page: one computer, one of its spaces and three sessions, with the same two-destination navigation above it.
- The choice is stored on the device (`AppStyleStore`, SharedPreferences `persona-appearance`), not on the hub, and survives re-pairing.
- Debug builds can set it at launch: `am start … --es debug.style glass|brief|board` (used by the screenshot script).
- Layout density (#5564), in the same page under Light/Dark: Standard (the default) or Compact. Compact scales spacing (`Tokens.Space` and `N.dp.dense`, `LayoutDensity.spaceScale` 0.5), the page margin (`pagePadding`, `pageScale` 0.625), corner radii (`Tokens.Radius`, `PersonaTheme.shapes`, `N.dp.corner`, `radiusScale` 0.6; pills stay pills) and minimum row heights (`N.dp.row`, `rowScale` 0.8), applied at once in every window (the scales are snapshot state that the getters read); text and icons keep their sizes. Kept with the style in `AppStyleStore` (`layout-density`). Something sized with a spacing or radius token uses `Tokens.Space.Standard` / `Tokens.Radius.Standard`, which keep their size; a file-level `val` that holds a gap is a getter, so it follows the setting (`docs/design/DESIGN_SYSTEM.md` §2.3).

### 1.2 Glass transparency and fallbacks

| Situation | Effect |
| --- | --- |
| Android 13 and later, transparency "Auto" | Refractive glass (Haze 2's glass, `GlassLevel.Liquid`) |
| Android 12 | Blurred glass (`GlassLevel.Frosted`) |
| Transparency set to "Reduce transparency", or the phone is in battery saver | Opaque panels (`GlassLevel.Solid`) |
| Sustained dropped frames while scrolling (`GlassFrameMonitor`: over 60% slow frames after at least 120 frames, or over 30% of 240 frames exceeding 1.5× the frame budget) | Drops one level for this run: refractive → blurred → opaque |
| Terminal page (always) | Opaque panels: the terminal changes every frame (every redraw by the program, every scrolled line), and glass over it would have to recompute the blur of the top bar, key bar and edges every frame (2026-11-01) |

Only pieces floating over scrolling content (top bar, input field, decision panel) use refraction or blur; cards inside the page are a translucent fill plus a gradient stroke with no live blur, so scrolling costs nothing extra.
The default "scroll edge" blurs and washes content toward the background under the full height of the top bar and bottom overlays (input field, decision panel), then fades out over the next 28dp into the content,
so the gaps between overlays (between the title capsule and the task bar, between the status line and the input field) never show legible text. It washes toward the page's own background layer (the same status light, `PageBackdrop`), not a solid color:
with no content underneath the edge is invisible, and empty pages (e.g. a chat just created in Persona) get no colored band at the top or bottom (the hard cut the user pointed out on 2026-11-01).
List pages draw the edge only when content has actually scrolled under an overlay (not while resting at the top, saving one blur). A `JPage` whose top controls stay put below the bar passes `underTop` the same way, since the edge's 28dp would blur them: the to-dos page passes `{ false }` on the calendar, whose grid and time axis scroll in their own boxes, and its list's `canScrollBackward` (#6159). Pages without a top bar (a document embedded in a link card) draw no top edge. The opaque level does not blur; it washes the content from dense to light toward the background.
The Assistant home, chat screens and the Agents tab use `ScrollEdgeStyle.Gradient`, a background wash with a 16dp fade. Chat measures the whole top bar including any sibling tabs. When the tab strip is visible, the top edge uses 8dp of the existing gap under the bar to finish the fade, and the measured content padding stays the same. The gradient looks the same at every glass level while floating controls still draw their own glass. Without an app dock, as in the Agents tab, there is no extra wash above the system navigation area.
The setup checklist uses the standard top edge. Its completion buttons scroll with the list, so the list ends above the system navigation inset and draws no bottom edge.
A page embedded in another (the chat inside the Persona page) fills the whole page and slides under the host's top bar and input overlays: the host tells it how much to leave via `ChromeInsets(top, bottom)`, and it draws the edges itself (the host uses `JPage(edges = false)`).
Implementation note: Compose's `Canvas` does not clip by default, and glow centers laid out relative to the window often fall outside this page, so `AmbientLight` must `clipToBounds()`, or it paints onto the neighboring column.
The blur input is quarter resolution (`LocalHazePerformanceMode` = `Performance` in `PersonaTheme`): measured on a phone, full resolution doubled the chat page's frame time, and the reduced version looks no different.
Performance measurements are in section 5.

## 2. Design system (`core:designsystem`)

### 2.1 Tokens

| Accessor | Contents |
| --- | --- |
| `PersonaTheme.style` | current style `AppStyle` |
| `PersonaTheme.palette` | `PersonaPalette`: background, surface (translucent in Glass), surfaceOpaque, surfaceStrong, sunken, line, ink / ink2 / ink3, action / onAction, accent, marker, neutral `statusSurface`, per-state `StatusColors(dot, text, tint, onDot)`, diff and terminal colors |
| `PersonaTheme.type` | `PersonaType`: largeTitle, title, headline, body, bodyStrong, callout, caption, micro (tabular digits), label, labelSmall, number, voice (the line Persona speaks), code |
| `PersonaTheme.shapes` | corner radii for cards, panels, controls, chips, buttons, bottom sheets |
| `PersonaTheme.motion` | durations and curves (springs in Glass); `count` is the duration for numbers rolling to a new value and chart bars growing to a new height (#2811). Chat open/close is `Modifier.unfolding` (below), not this size motion |
| `SharedMotion` / `Tokens.Motion` | Shared iOS motions from `spec/tokens/motion.json` (`expand`, `reveal`, `conceal`, `drawer`, `springBack`, `keyboard` via `IosMassSpring`, plus composer send and Needs You breath). Use these where the iPhone / Duo / iPad counterpart moves; Brief and Board keep their tweens only for the style-local state/layout springs. `SharedMotion.instant()` is the shared immediate change for Reduce Motion; pages do not choose raw animation specs. Literal animation specs are ratcheted by `scripts/app/android_motion_baseline.py` (#9897) |
| `PersonaTheme.glass` | the glass level actually rendered |
| `SpinnerTokens` | `JSpinner`'s fixed stroke widths; `compactStroke` is the 1.8dp compact activity arc, not density-scaled spacing |
| `ContentTokens` | Existing mail, media, profile, reaction and task-content dimensions that cannot be expressed by the common spacing tokens; keeps page geometry unchanged while adopting tokens |
| `RichTextTokens` | Rich-message geometry outside the common scale, including content-driven Markdown table minimum / maximum column widths (160 / 220 dp before applying the message's font scale) |
| `MetricColor` | Machine-monitoring series in light and dark, resolved independently of style, Agent states and theme accent. Values are registered in `spec/tokens/color.metric.json`; Android's disk-only addition is neutral slate |

Material 3's ColorScheme, Typography and Shapes are also generated from the current style, so Material components not yet replaced change colors and fonts along with it, but pages should switch to the components below.
The old `PersonaTypography.*`, `statusTone(...)`, `PrimaryButton` / `SecondaryButton` / `Card` / `EmptyState` still work and now map to the current style internally; new code uses the new components directly.

**Interface and reading text (#7321):** `PersonaTheme` caps the interface's `LocalDensity.fontScale` at `InterfaceFontScaleCap` (1.35), Persona's conservative, rounded conversion of iOS xxxLarge body text (23 / 17 ≈ 1.3529). At and below the cap it retains the original `Density`; only larger system scales change the interface. The uncapped chosen density is retained through nested themes for reading. Apply `ReadingContent` to a semantic message, document, transcript, note or typed-editor leaf, never a whole screen or a neutral shared renderer; `InterfaceContent` re-caps its decorations and other embedded controls. (`BasicTextField` resolves its own text layout outside `decorationBox`, so wrapping only the inner field is insufficient.) Shared overlays retain both densities across their window boundary above the cap, while preserving the legacy window's rendering at and below it; an older raw `Dialog` / `Popup` captures `currentTextDensities()` before the window and restores them with `RetainedTextDensity` inside it. When an expanded reading body's arrangement depends on the chosen scale, make that decision from the retained reading density too: the capped interface density must not suppress the expansion. Placeholders, labels, buttons, metadata, previews, tool output, diffs and terminal text remain interface. This is a product scale conversion, not a claim of identical Apple/Android font metrics. The classification is `docs/design/DESIGN_SYSTEM.md` section 6.2.

Page stacks share `rememberPageTransitions()` (`PageTransitions.kt`). Glass push and a tapped pop take 350 ms on cubic-bezier(0.28, 1.02, 0.48, 0.96); the page behind travels round(0.3 × width), a black dim of 0.10 × coverage darkens that page, and the front card casts a black shadow at opacity 0.04, radius 12 dp, offset (0, −3 dp), only during the transition. The shadow is a horizontal gradient about two radii wide: `Paint.setShadowLayer` blurs a non-text shape only on the software pipeline, and `RenderEffect.createBlurEffect` is API 31, above minSdk 30. A predictive pop keeps that 350 ms and travel but uses a linear ease, so the back gesture tracks the finger; seeking the cubic would move the page about two thirds of the way on a quarter of the drag. Brief and Board predictive pops stay their eased pop. Measured on the iPhone simulator with Xcode 27.2 by sampling the navigation coordinator, the parallax card's shadow and the dimming view.

Repeating that measurement: boot a stock simulator with `scripts/app/sim-boot.sh --profile stock` (the pass used an iPhone 18,1 at 402×874 pt, an iPad 17,4 at 1032 pt wide, and an iPhone 19,4 at 466 pt wide, all on iOS 27.2). A foreground app has to own the run loop. `CADisplayLink` on `.common` does not tick while a unit test pumps `RunLoop` itself, so the sampler is a small app, not a `PersonaTests` case, and it stays out of this repository. Each vsync reads `layer.presentation()` in window space: frame, opacity, shadow opacity, radius and offset, and background components. Push and pop run on a `UINavigationController` and a SwiftUI `NavigationStack`. The coordinator reports `duration=0.35000`. There is no `CAAnimation` on the page layers; the cubic is a fit of presentation x over that 0.35 s, progress 0 at the first sample where the incoming page is still past half the width (or the outgoing card is still at x ≤ 1), with a per-run shift of at most one or two 60 Hz frames. The fit is `cubic-bezier(0.28, 1.02, 0.48, 0.96)`. The page behind is the other card in that transition (`round(0.3 × width)`). `_UIParallaxDimmingView` is the scrim (black at alpha 0.10, opacity tracking coverage); a second dimming view in the same transition has no background and is not the scrim. `_UIParallaxTransitionCardView` is the shadow (opacity 0.04, radius 12, offset (0, −3)); a child layer with shadow opacity 0 is the CALayer default, not the card. An interactive edge pop on the phone tracks the finger linearly and keeps the same behind travel. PNG frames are `render(in:)` of the presentation layer on the next vsync at or after the mark; `simctl screenshot` cannot hit these times. Brief and Board keep the opaque trailing-edge push (300 ms), quarter-width move-back and pop (260 ms, departing page on top), mirrored in RTL; predictive pop seeks that same eased pop. `PersonaTheme.reduceMotion` (including system animations off) makes all three transitions instant. On a regular window, switching sidebar place replaces the Assistant stack's root with no push, pop or fade (`personaSceneRootSwapped`); with the column over the page, that column's slide is the only motion of a place switch. System Back at a place root returns to the conversation as a root switch with no animation; system Back at the conversation leaves the app. A page handler on that root runs before the place-root Back. Drill-downs and the phone drawer keep the transitions above. An Agents list pick in an upright regular window **replaces the detail immediately**: only the overlaid list slides away, copying `SplitNavigation.swift`'s sidebar value links and `hideOverlay()` (lines 125–208). `JSidebarColumn` uses `Theme.Motion.layout`'s 300ms, zero-bounce spring on Glass (`Tokens.Motion.Layout`); Brief and Board retain their 240/160ms tweens. The phone drawer keeps its separate drawer spring. On a phone, and on a foldable's outer screen, that drawer follows the finger on the Assistant root (`DrawerDrag.kt`): a child already handling the touch keeps it, and a sideways scroller keeps a rightward drag only while it has room toward its start. At that root with the drawer closed, a left-edge strip is excluded from system gestures (`RootEdgeExclusion`, width = the left `systemGestures` inset, height at most 200 dp centred on the page) so the edge opens the drawer as on the iPhone (`SwipeBack.swift:11-16`); the trailing inset still refuses, and a pushed page keeps the drag off. The foldable list column excludes the same centred band over its 22 dp open zone while hidden and `detailAtRoot` (`SplitColumnControl.swift:132-137`). Tracking, the 300 dp/s flick and the 0.2 s projection copy `AssistantDrawer` and `DrawerPan` (`apple/Persona/Views/Assistant/AssistantSidebar.swift`) and `SwipeRelease.goes` (`apple/Persona/Views/Shell/ShellPager.swift:193-196`). Glass carries the finger's speed into the 0.32 s drawer spring, and that finger settle keeps the spring when Reduce Motion is on (`Theme.Motion.drawer` does not read Reduce Motion). A button, Back, or another write of the open flag keeps `PersonaTheme.reduceMotion`, and unfolding into the regular-width sidebar snaps. Brief and Board keep the tween above for a finger settle that is not on Glass. Agents and Inbox rows move only when a tap changes them (#9600, `ListTapMotion`): Glass uses the state spring, and the layout spring when the Agents grouping changes; Brief and Board keep the tweens above; animations off, the rows jump. A hub update does not animate. The iPhone lines and what stays still are in `docs/design/DESIGN_SYSTEM.md` section 2.7.

### 2.2 Components

A component with a composable slot ends with a function-typed parameter, so a caller can pass the slot as a trailing lambda. Add a parameter before the slots, never after (#4146, checked by `scripts/app/android_slot_order.py`; see [android.md](android.md) "Design-system slot order").

| Component | Use |
| --- | --- |
| `JPage` | A page with custom content. Pass the `PaddingValues` it gives you as the scroll container's contentPadding: in Glass the top bar and input overlays float over the content, and this is what leaves room for them |
| `JListPage` | List pages (root pages and most second-level pages). Includes a large title, pull to refresh and content padding; `summary` is Persona's one line about this page, `greet` adds the date and a greeting (home only) |
| `JTopBar` | Page top bar; already included in `JPage` / `JListPage`, used alone for special pages. In Glass, while the large title is still on screen (`showTitle = false`), back and actions are separate floating round buttons; only after the large title scrolls away do they merge into a capsule with the title |
| `JFullScreen` | A full page over the current page (in-session search, full-text reading, task progress, spaces, past sessions): extends under the system bars, status bar icons follow dark/light. Do not build full pages with Compose's `Dialog` directly |
| `JBottomBar` | A row of actions at the bottom of a page (paging, load more): a floating capsule in Glass, a bar flush with the bottom in Brief and Board. The page frame keeps it within `ReadingWidth + 40dp` and centers it; a bar that should be narrower takes `Modifier.widthIn(max = …)` on the bar itself, not on the row inside it, which would leave Glass's capsule wide around a narrow row (the to-do page's: `Tokens.Size.readable` times the font scale, #9009) |
| `ChatTopBar` | Chat page top bar: title, one status line (state, which computer and directory), actions |
| `JSectionHeader` | Section heading within a page, optionally with a count and an action. Measures the complete title/count and actions in one layout pass; only when they do not fit, the actions move into a `JMenu` and the title wraps to stay fully visible. Fitting layouts are unchanged. |

| `JGroup` | Small groups that need no lazy loading (settings pages) |

| `JNotice` | In-page notice (connection lost, permission needed), with one action |
| `JEmptyState` / `JLoading` | Empty state (an icon, or a `leading` slot in its place), loading |
| `JLoadable` / `jLoadableContent` | One container for a page that loads inside `JListPage` (iOS `Loadable` / `LoadableContent`): `Loading` is a centered `JLoading` (optional text), `Loaded(value, refreshing, failure)` draws the content (`refreshing` goes to the list page's pull indicator; `failure` is one `JNotice` line above the kept content with an inline Retry), `Failed(message, title)` is a `JNotice` with the reason and Retry. `isEmpty` + `empty` draw the page's own empty state, but a `Loaded` empty value that carries a `failure` shows the failure, not the empty state. `onRetry` null hides Retry. Glass press scales about the centre by `1 + 16/width` (held growth was 16.00 pt at 61 pt, 15.79 at 160 and 15.17 at 300, so 16 dp is the rule and the wide button is 0.83 pt short), on a 270 ms spring with bounce 0.36, and releases on a 400 ms spring with bounce 0.62. ### 2.3 Rules for writing pages

1. Assemble pages only from the components above. Do not use Material 3 visual components directly: `Scaffold`, `TopAppBar`, `NavigationBar`, the `Button` family (icon buttons and floating action buttons included), `Card`, `TextField` / `OutlinedTextField`, `FilterChip` and the other chips, `AlertDialog`, `ModalBottomSheet`, `DropdownMenu`, `Snackbar` / `SnackbarHost`, `Checkbox`, `Switch`, `RadioButton` or segmented buttons. Primitives such as `Text`, `LazyColumn`, `Box` / `Row` / `Column` are fine, and so are `MaterialTheme`, `Local*` and `material3.adaptive`. Import Material 3 names one by one: no wildcard `material3` imports outside the design system. `scripts/app/android_token_baseline.py` counts these components per file and lets the existing ones only go down ([android.md](android.md) "Design token adoption baseline").
2. Colors come only from `PersonaTheme.palette`, font sizes only from `PersonaTheme.type`, corner radii only from `PersonaTheme.shapes`; no `Color(0x…)` or numeric font sizes. Icons are named by meaning, as on iOS: `PersonaIcons` (generated from `spec/icons/meanings.json` by `scripts/assets/gen_icon_meanings.py`, one property per iOS `Theme.Icon` meaning) drawn with `JIcon`; only the design system names Phosphor glyphs (`PhIcons`) directly. Not material-icons. A meaning Android lacks gets an entry in `spec/icons/meanings.json` (and, for a new glyph, a name in `scripts/assets/gen_phosphor_icons.py`). A domain space's icon token (the web's names) is drawn through `SpaceIcons.of(token)`, which falls back to the stack glyph for a token it does not know; an information category's name comes from `infoCategoryLabel`.
3. Page structure: root pages use `JListPage` (without `onBack`, automatically a large title); secondary pages use `JListPage(onBack = …)`; non-list content (chat, terminal, reader) uses `JPage`.
4. Always use the padding provided by `JPage` as the scroll container's contentPadding, not just padding on the outer container (otherwise content in Glass does not slide under the overlays).
5. Groups use `JGroupItem(GroupPosition.of(i, n))` or row components with a `position` argument, one row per lazy item; do not wrap many rows in one item (long lists will stutter).
6. "Things for you to decide": `DecisionCard` in lists, `DecisionDock` cards in a `DecisionStack` in chats, `DecisionOption` for options (`recommended = true` for the recommended one), `DecisionButtons` for buttons, `DecisionAdvice` for Persona's suggestion.
7. Use `JActionSheet` for long-press menus, `JMenu` for anchored menus with two or three items; its `content` slot takes a short list whose rows are more than labels, above the actions (the assistant switcher's roster). Full-screen pages use `JFullScreen`, bottom action bars use `JBottomBar`; do not float text buttons directly over content.
8. Do not join metadata strings with "·": pass machines, directories, Agent types, loops and background work as component parameters (`machine`, `folder`, `agent`, `facts`).
9. No `if (PersonaTheme.style == …)` in pages. Style-dependent behavior belongs in components; if a component lacks a parameter, say so in the report and have the design system owner add it.
10. Button text stays on one line; shorten it or use an icon when space is tight (project rule).
11. Something a card only offers or notes (the rule it suggests after the same answer three times, a decision held for the next briefing, #5802) is quiet text, not another card: `caption` in `ink2` for the sentence, `ink3` for what qualifies it, at most one small mark by meaning (`PersonaIcons`), and for actions one `JButtonSize.Small` secondary button with a quiet one beside it. It sits under the card, `Tokens.Space.s` below it and inset `Tokens.Space.m`, so the card's own solid primary stays the only one of its group. Its result replaces it in place as one line (a check mark in `positive` and the words); it never opens a dialog.

### 2.3.1 Color hierarchy and visual noise (#6184)

These rules apply to all three styles, including extension-rendered content.

- **Red is exceptional.** Use `danger` only for an actual error/failure or an explicitly destructive action. Routine approvals, reviews waiting for the user, permission requests and extra permissions during installation use `needsYou` / `caution`, never red. The one exception is an agent's **Allow Everything** permission mode, which is drawn in `danger` on the header's mode button and the composer's Mode button, as on iOS and the web (#3719, #3957): amber read as Working. A quota approaching its limit is caution; an exhausted quota is a failure. Stderr alone is not a failure.
- **Neutral containers.** Cards, rows, banners, status bars, receipts, advice, draft previews and received-message bubbles use `surface`, `surfaceStrong`, `sunken` or the semantic `statusSurface` token. Glass's own-message bubble instead uses the shared iPhone-derived `userBubble`; it identifies authorship, not a work status. Do not fill the container with `StatusColors.tint`, `accentSoft`, the highlighter or a state color. Put state on a small dot/icon, readable words or a thin edge. Board retains its strip geometry and glyph column, with a 2dp state edge instead of a broad color block. Glass retains translucent surfaces, strokes and rounded overlays; Brief retains paper, ink and small highlighter marks.
- **One broad colored area at most per screen.** Glass's subdued, single-state ambient backdrop is that area; the content above it stays neutral. Other styles need no broad colored area. Charts, photographs, source images and syntax/diff content are information, not status backing; never reuse their colors as a card skin. Small badges, switches and selected-control marks do not count as broad areas.
- **One solid primary per action group.** Use the style's neutral `action` / `onAction` pair for the main action; alternatives are Secondary or Quiet. Approval is not destructive. Recommendations/selected options use a border, icon and label, not another solid primary or colored option fill. Extension review/composer button tones must not make every positive choice primary or a negative review destructive; explicit destructive roles still use the destructive treatment.
- **Contrast in light and dark.** Brief and Board: all enabled text, including status, timestamps, hints, links and destructive labels, reaches 4.5:1 on its actual backing (composite transparent fills first). Glass holds iOS's floors instead: body words and words on the bubble 4.5:1, white on the accent 3.5:1, the accent as a link 3:1; its other words are iOS's own colors, which `StyleContrastTest` reports without failing. Informative graphics need 3:1, or a redundant label/shape explaining the same state. Never rely on color alone. Preserve resource-based localization and single-line button labels.
- **Evidence before shipping.** Capture matching synthetic before/after cases for Glass, Brief and Board in light/dark and inspect them. Prefer actual app/emulator captures. Native Robolectric images are useful component/page evidence but do not prove system bars, navigation, WebViews, glass refraction, device behavior or performance; explicitly disclose when those checks could not run.

## 3.1 Tablets and foldables

Layout depends only on the window, not the device model: the shell uses material3-adaptive's `currentWindowAdaptiveInfo()` (WindowSizeClass plus posture from Jetpack WindowManager's FoldingFeature)
to calculate a `WindowLayout` for the design system; pages do not measure their own width. Split-screen, freeform windows, rotation, folding and unfolding only recompose

### 3.1.1 Tabletop pages

Tabletop layout is selected only from the window's horizontal separating hinge, never from a device model. Glass, Brief and Board all measure the actual top bar and bottom dock before choosing their geometry in one `SubcomposeLayout` pass; there is no second-frame size correction.

- **With a bottom dock:** reading and scrolling stay above `hingeTop`; the composer, terminal key bar or page actions start at or after `hingeBottom`. The dock keeps `ReadingWidth`, does not receive another ordinary navigation-bar padding, and is centred in the measured lower safe area. Content leaves `Tokens.Space.m` before the hinge.
- **Without a bottom dock:** the top bar and all content end at `hingeTop`. The hinge and everything below it draw only the same page background: no content slot, focusable node or clickable control is placed there.
- **Fallback:** a missing or zero-height hinge, an upper side that cannot hold the measured top bar plus `Tokens.MinTouch.android` of content, or a lower side that cannot hold the measured dock uses the ordinary flat single-page layout and its system insets. A short lower side is allowed when there is no dock because it is only background. Returning between flat and tabletop reuses the same content slot, scroll state, draft, selection and focus; it does not navigate or recreate a ViewModel.

Acceptance covers Glass in light and dark and samples Brief and Board in both appearances. Generic Fold's real book posture can provide real `FoldingFeature` evidence. A fake tabletop supplied through `debug.posture` is visual and layout evidence only; the real tabletop posture still needs device verification. No frame-rate, memory or power improvement is claimed without measurement.

### 3.2 Message pointer menus

- In a regular or expanded window, a mouse or trackpad secondary press on a message opens `JPointerMenu` beside the pointer. The shell supplies `LocalLargeWindowInput`; the message menu does not measure the window or infer a device type. Compact and wide-phone secondary clicks retain the bottom `JActionSheet`.
- Touch long press and TalkBack More actions always use `JActionSheet`, including on tablets. Swipe to quote still quotes on release; the message springs back with `Tokens.Motion.SpringBack` (0.3 s, bounce 0.25) in every style (#9575), including when the system's animations are off, because iOS `MessageActionBarHost.ended` (`MessageMenu.swift:470`) always uses `withAnimation(Theme.Motion.springBack)` and does not read Reduce Motion. iPhone and iPad share that gesture. Message dimming, link taps and the chat reading anchor are unchanged. There is no message lift, blurred preview or hover-only command.
- Both presentations receive the same `messageMenuActions` list and callback, including order, icons, disabled reasons and destructive actions. Dismissing the pointer menu clears only its presentation anchor; Rewind's second confirmation, Select's reader and Share's page keep their existing state and can open and return.
- `JPointerMenu` reuses `JMenu` rows and tokens. It grows right/down from the pointer, flips when the opposite direction fits, clamps the measured menu to the safe physical window (left and right insets are not exchanged again in RTL), scrolls long actions and closes once on Escape. Verification uses real `BUTTON_SECONDARY` instrumentation or a hardware mouse, not adb hover / console success messages.

### 3.3 Page-sized Settings and hardware shortcuts

`JSettingsSheet` reads only `LocalLargeWindowInput`; it does not duplicate the window breakpoints. On a large window `JSettingsPresentationFrame` centers a card within the safe drawing area. `SettingsPageSizing` names its maximum width and height (both aliases of `ReadingWidth`) and minimum window margin (`Tokens.Space.xl`), so expanded windows retain visible margins and a minimum regular window can be nearly full. One `JSheet`, one presentation frame, one content invocation and one window scrim stay mounted; only the transparent container and card geometry change, preserving non-saveable state and running effects as well as the fixed-key saveable holder. `focusRestorer` returns to the previously focused field after a presentation transfer; an existing focus is never replaced, and the outer blank-tap callback explicitly disables restoration when the user dismisses the keyboard. Root Close and child Back keep their existing meanings, and the existing list-detail directive degrades to one pane when necessary.

`HardwareShortcutHost` is attached to the large-window shell and the Settings dialog. When a window becomes large, the shell host uses public focus state to request its own focus only when that window has none; an already-large resize does not request focus again. Settings disables host auto-focus because its dialog content owns the focused field. Sheets, dialogs, full-text reading, message sharing and chat search register their existing close actions in LIFO order. Escape reaches these listeners only after the focused child declines it, closes at most one layer, and is a no-op when nothing transient is open. Shared text inputs handle only Ctrl+/ before the editor consumes it; terminal and other child keys are never intercepted by a parent preview handler. Expanded composer and pointer menus keep their own Escape handling; a focused terminal keeps its consumed control, navigation and Escape keys.

Ctrl+/ opens a centered, scrollable shortcut-help dialog above the current layer. The help lists only working send/newline, close, help and terminal keys in English, Simplified Chinese and Japanese. It leaves drafts, selection and terminal state alone, and Close stays on one line. Compact and wide-phone windows keep the same content parent but receive no controller or key modifier, so they do not register the new behavior.

## 5. Performance
