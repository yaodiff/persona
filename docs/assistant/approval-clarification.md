# Approval clarification

An assistant-owned permission card can carry **Have a question** in addition to Allow and Deny. A question asks about the exact proposal on that card; it is not an approval decision and never executes, declines, closes, or cancels the operation.

## Owner flow

- Web shows a question editor when the interaction has `can_clarify`. `POST /api/v1/interactions/{id}/clarify` takes only `{text, client_msg_id}`. The trimmed question is at most 1,000 Unicode code points. An unchanged retry reuses its `client_msg_id`; a deliberate new question uses a new one.
- Feishu shows the same action only on a public card. Every press must be a fresh, one-time owner action bound to that channel, card, and permission kind. The answer run returns to the card's explicit chat and message target as well as the originating assistant conversation.
- The owner's original text is delivered to the interaction's exact machine and session. An archived conversation is explicitly reopened. A deleted conversation or ended room returns a visible error; delivery never falls back to another conversation.
- The hub issues a short-lived, one-time proof for an authenticated Web question, bound to the card, exact text, destination and `client_msg_id`. Feishu gets the same bound proof only after its fresh owner action succeeds. The opaque token travels only inside `session.send_once`; the hub consumes it before sending and the devices manager writes `owner_input`. A manager-written `owner_input`, caller or submission is never accepted. Missing proof on an older hub/manager combination keeps the previous unmarked delivery; proof never grants Apply or another owner action.
- A successful question returns the original tool call with a non-final Clarifying outcome. Its result says that the question is not an approval decision, that it arrives as a separate owner message to be answered then, and that the same card remains valid and must not be recreated. The card stays pending for Allow or Deny, and further questions are allowed.
- Private interactions remain in their private Web conversation: they are not drawn or answered in Feishu. Field cards may be questioned, but field values are never put in the question and channel Allow remains unavailable. Only the owner can clarify; an assistant, supervisor, answer-only principal, remembered grant, or standing authorization cannot execute the prepared operation.

## Prepared operation and compatibility

`approval.Operation` is the process-local continuation behind one immutable proposal. It contains Apply, optional Discard, replacement identity, and the existing Denied/Unanswered tool results. Public interactions gain only the additive `can_clarify` boolean; older clients ignore it and keep their existing Allow/Deny behavior. Clarification is an action, not a new `proto.Resolution`.

For a hub-owned setting, `fleet.ask_prepared` retains the executable handle in the hub and returns `approval.Outcome` to the manager. Only the opaque interaction ID crosses the trusted bus. `fleet.approval_apply` consumes that manager-owned handle once after a fresh owner Allow; `fleet.approval_discard` releases it without applying. A structured stale result survives the bus boundary. Existing `fleet.ask` callers retain one-shot approval behavior.

Immediately before Apply, the operation re-reads current state and verifies that it still produces the visible before/after proposal. A revision-checked operation keeps its original revision baseline rather than rebasing it. A stale proposal applies nothing and ends as stale/cancelled with a request for a fresh card. An equivalent newer proposal replaces and closes an older Clarifying card so both cannot execute. Subscription deletion uses an atomic revision predicate.

A prepared operation without a live origin conversation uses the older one-shot card instead: `can_clarify` stays false, a fresh Allow applies once, Deny or expiry applies nothing, and the original caller is the only terminal recipient. No approval journal or other conversation receives a fallback result. Legacy wait failures and pre-Apply validation errors say definitely that nothing was applied; an error after Apply begins remains uncertain. `repository_add` finishes argument and current-state validation before presenting its card.

## Timing and terminal delivery

Before the first question, the card keeps its original decision deadline, but the original tool call holds the turn for at most 75 seconds (or until that deadline when it is sooner). While an accepted question is being answered, the remaining decision time is paused. The pause has a cumulative 24-hour budget per card; repeated questions do not reset it. The turn that produced the card does not count as its answer turn, and a question accepted during an answer turn waits for the next turn before timing resumes.

Every pending snapshot carries the current effective `expires_at`: during a pause it is the remaining pause-budget deadline, and after all answers finish it is the resumed decision deadline with exactly the preserved time left. Same-ID interaction updates publish those changes without another arrival or push. Android replaces its card and delivered notification with that current deadline, including notification action metadata and system timeout. A genuinely expired current card still cannot execute; stale notification timestamps alone cannot revive it.

### Unanswered cards keep waiting (#10096)

A notification is only a way to tell the owner that a card is waiting; the card itself must still be there when they open the Persona app or the web. When no notification reaches their devices (no working push route, the app in the background), they may only look much later. So when a prepared card's 75-second initial wait ends unanswered while its caller still waits (or its original decision deadline arrives first), the coordinator keeps it (`keepWaiting` in `server/internal/assistant/approval_clarify.go`) instead of expiring it:

- it is recorded in the approval journal, as on a first question, so its final outcome reaches the original conversation;
- its deadline moves to the end of a 24-hour waiting window, and the apps are told the card again with that deadline, without a second push; the app and the web already load pending cards when they reconnect (`GET /api/v1/interactions`);
- the original tool call returns the non-final `approval.WaitingText`: nothing changed, end this turn, the card is still pending, do not retry or create another card, a later message reports the outcome;
- a later owner Allow applies once (the operation still re-checks current state), Deny changes nothing, and the end of the waiting window expires it without changing anything; each is reported in the conversation. A question on a waiting card pauses the remaining waiting time as on any clarified card.

A card whose caller already went away (a caller that bounds its own wait, such as the scheduled-check probe) is not kept: it expires at its decision window as before.

The coordinator makes one final claim under the fleet mutex. An in-flight question and a final Allow, Deny, expiry, or replacement are explicitly arbitrated. Allow executes at most once, Deny executes nothing, and a proxy-attributed Allow executes nothing.

Once a card has clarified, every terminal path sends exactly one result containing the literal interaction ID to the original conversation, including Allow, Deny, expiry, replacement, stale cancellation, and restart cancellation. Delivery uses the stable ID `approval-result-<interaction-id>` and the durable relay queue. A result its conversation cannot take yet stays in the journal and is retried a minute later, for as long as the manager that tried runs; once that manager stops, the next one delivers it when it starts, and the stopped one's retry does nothing (#16045). The journal stores only the ID, original target, minimal safe summary, delivery state, occurrence creation time or SHA-256 call digest, retained decision deadline, finalization state, status, and result text—never field values, secrets, raw tool arguments, callbacks, or executable closures. When a restart or stale handle invalidates a card without executing it, the notice includes that safe summary, states that nothing was applied, and asks the conversation to create a fresh approval card.

Before the first question, a card whose caller still waits is normally kept waiting when its window ends ("Unanswered cards keep waiting" above). When it cannot be (its journal entry could not be written) or its caller already went away, an unanswered expiry returns through the original tool result instead of starting a second delivery. It contains the literal interaction ID, says the approval expired, and explicitly says nothing was executed. Expiry remains distinct from the owner's Deny: it never becomes a user refusal.

After a manager restart, an unanswered detachable command stays pending under its original interaction ID and deadline when the journal and stored resumable command agree on the retained deadline, occurrence and complete input. Older journals without this deadline and cards involved in a clarification cannot establish that the original hook released into an ordinary waiting window. They keep their previous restart behavior. A window already over when the manager starts follows the existing stale-card cleanup. Replaying its original hook returns the pending approval ID without executing. A later owner decision follows the same one-time continuation flow as a live card. An interrupted `applying` entry reports an uncertain outcome. Unfinished cards whose operation cannot be reconstructed keep their restart cancellation.

Recovery finalizes all terminal results in a batch before delivery, including results whose interaction rows are still pending. Finalization is occurrence-bound: a missing row gets a non-executable terminal tombstone, a different pending occurrence is preserved and keeps the old journal undelivered, and a different terminal occurrence prevents the original from replaying. Recovery suppresses intermediate automatic delivery, synchronously verifies each terminal interaction write, and retains and retries the whole batch after a failed write. Its status mapping matches the live finalizer (`denied` and `covered` use `resolved`; `failed` stays `failed`) rather than manufacturing a conflicting terminal row. Legacy unfinished journals retain their original update-time occurrence cutoff; entries created by the current process carry a process-local `live` marker, so a delayed initial-load retry cannot cancel them. A transient per-row restore read retries only the pending snapshot, without expiring stale interactions a second time.

A persisted continuation can be consumed only when the candidate grant's own journal has a completed `approved` result or that result has been handed off and its journal removed; a normal retry's fresh interaction ID does not bypass this check. An `applying`, waiting, denied, cancelled or failed entry returns a non-executing dismissal even if its grant book still contains the grant. Revocation re-reads the durable book on every attempt and deletes only the grant matching that journal occurrence; an older denial cannot revoke a newer same-ID call's grant. Result cleanup retries a failed revocation and retains the journal until the persistent delete succeeds, including when the original conversation was deleted; a successful revocation for that deleted destination still avoids an endless delivery retry.

## Detached command approvals

A node command gate in an assistant conversation marks its permission card `detachable`. The manager validates that capability against the conversation and requires the complete tool input plus `execution_cwd`, the directory where the command actually runs (which can differ from the card's display directory). An older or incomplete request keeps the ordinary blocking approval instead of receiving a detached grant. After the same short initial wait — or immediately if the owner sends a new message to that conversation while the card is still in its initial wait — `interaction.create` returns `{dismiss:true,pending:true,approval_id,message}`: this is not a denial, no command ran, and the model is told to end the turn. The card stays pending under its authoritative interaction ID; transcript reconciliation ignores prepared approvals and non-final `WaitingText` / `ClarifyingText` tool results so the hook's release message never dismisses the retained card (#12918). An owner-facing permission, question, or plan card whose remaining lifetime exceeds 30 minutes schedules at most one follow-up push reminder after 30 minutes (`armPendingReminder`, #16159), including when a detached or prepared card enters its 24-hour waiting window; the reminder is cancelled when the card is answered, withdrawn, muted, paused for clarification, or expires.

That non-final tool result is not evidence that the owner answered in the terminal. While the detached card is in its waiting window, transcript reconciliation ignores the matching result and a late node `interaction.dismiss` cannot withdraw it; the terminal reconciliation rechecks this state under the fleet mutex so a read begun before the wait cannot win the race. Ordinary terminal dismissal before the waiting result retains its existing behavior.

A later ordinary Allow stores a continuation grant in `assistant.detached_approval_grants` before its result is journalled. The result message asks the original conversation to retry the same tool once. The grant covers the exact machine, session, execution directory, kind, tool and complete canonical JSON input value. JSON object-key order and formatting are not identity because PostgreSQL JSONB may change them; the command and every other value must still match. Grants already persisted in PR1's raw-JSON representation remain consumable and idempotent after the upgrade. Consuming it deletes and persists the grant before returning Allow; a failed write allows nothing, a changed input does not match, and a second retry cannot reuse it. Replaying the original resumable interaction never consumes its own grant, including when an Always rule now covers the call. The returned `approval_id` keeps the sent-command ledger attached to the card the owner actually answered. An explicit Always allow remains a separate durable grant under the existing Always rules.

Continuation delivery is serialized with grant consumption. If a matching call consumes the grant before its result reaches the conversation, the delivered result says not to retry automatically instead of requesting a duplicate execution. The check runs again under the same lock at the final durable-queue drain, so consumption while the conversation is busy cannot leave a stale retry instruction. A relay persistence failure leaves the journal entry intact for a later attempt or manager restart. A newer Always decision closes covered detached sibling cards: an original hook still waiting receives its ordinary answer, while an already released sibling creates no second grant and requests no automatic retry.

The manager never starts a second shell for this continuation. An editable command's grant carries `edited_text` into the ordinary node-side edited-answer path, so only the original body word is changed and the edited command is classified again. Deny and expiry store no grant. Grants expire after 24 hours and are bounded to the 128 most recent unused approvals. A restart loads the durable grant book but never replays an approval by itself; recovery revokes any grant whose approved result was not completely recorded, including an interrupted `applying` entry, before reporting that outcome as failed or uncertain. A disconnected resumable hook keeps its ordinary reconnect grace, and the reconnecting caller replaces the cancelled caller for the initial-wait timer.

## Main-conversation and direct-chat copies (#11310)

`assistant.approval_mirror_main` defaults on and is available in Assistant Settings and through `persona_settings`. For new cards, a non-private, write-operation permission from a non-main Assistant conversation gets a display copy in the current main conversation. Agent sessions, conversations in spaces the main conversation may not read (including health), private interactions and other interaction kinds keep their existing routing. Turning the setting off affects new cards; an existing copy remains synchronized until its authoritative card ends.

`assistant.approval_mirror_tools` is the write-tool allowlist for both new routes, configurable through `PUT /api/v1/assistant`; `GET /api/v1/assistant` returns the effective list. The default covers file writes (`Write`, `Edit`, `MultiEdit`, `NotebookEdit`), the assistant's write tools (including `persona_settings`, `schedule_routine`, `conversation_new`, `todo_create`, `todo_complete`, `todo_delete`, `todo_reopen`, `repository_add`, `skill_import` and `agent_autoname`), and `mail_send`. A node command gate contributes only calls it explicitly classifies as writes (`write_operation`); an unknown Bash command, variable method or GET/HEAD confirmation does not qualify through its title or Always keys. Older nodes without that metadata keep their original cards but do not gain copies for generic Bash or gate-titled calls. An installed extension's own write declaration also admits its actions by default. Read confirmations such as `Read`, `lark_messages`, `kb_get` and `inbox_suggest` get neither a new main-conversation copy nor a new direct-bot card, even when a custom allowlist names one. Their original card, short return and retained waiting behavior are unchanged. An explicitly configured list replaces the default write list, command-gate metadata and extension fallback; an empty list disables both new routes. The `mcp__persona__` prefix is normalized. Changes apply only to new cards, so narrowing the list never strands an existing main copy.

The copy has a deterministic distinct ID derived from the authoritative ID and its occurrence creation time, and `mirror_of` naming the authoritative interaction. A delayed click on an earlier occurrence therefore cannot answer a later card whose runtime reused the original ID. Resolution events, including startup cancellation of stale rows, carry that occurrence timestamp; the hub refuses to withdraw a different current occurrence, and a later reused-ID occurrence replaces the durable terminal row instead of being discarded by an ID-only insert conflict. The copy keeps the originating conversation's title. The manager holds only the authoritative pending operation: reconnect snapshots contain both display cards, while aggregate request lists, counts and notification transitions contain only the authoritative one. Conversation views show the copy at its destination and the original where it was raised.

Before its resolve or clarification gates and before relaying, the hub normalizes a valid copy action to the authoritative ID and path. It also pins the occurrence in the `X-Persona-Interaction-Created-At` relay header and operation receipt. Current clients send the exact occurrence they displayed on an initial resolve; the hub preserves a mismatch for stale rejection instead of rebinding it to a same-ID replacement, and does not normalize a mirror whose supplied occurrence differs from its origin. The manager rechecks that timestamp under the same first-answer-wins claim lock, so replacing the card after normalization cannot make the old click or question land on the replacement. Older hubs and managers retain their previous behavior when the additive header is absent. Original-card updates refresh every existing copy without moving it; the authoritative resolved event withdraws every copy. An orphaned, nested, same-conversation or private copy is rejected, and a second click on a withdrawn copy is stale.

With the bot's existing `cards` feature on, the same eligible write permission is posted to the owner's direct bot chat even when that chat does not currently drive the originating conversation or its only existing run is in a topic. This path is independent of `approval_mirror_main`, but shares `approval_mirror_tools`. It does not enable or broaden `all_cards`: unrelated Agent cards and read confirmations still need that existing switch, and private, space, secret-field and sensitive-content restrictions stay enforced. Like `all_cards`, this direct-owner path does not carry a non-driven card whose words or track redact. Bot-driven conversations retain their previous routing before this new direct-owner path is considered.

## Exact replies for an owner-action batch

`owner_action_prepare` is the opt-in batch boundary for 1–20 side-effecting connector calls, managed `persona_settings` `set` / `add` / `remove` operations, `model_profile_switch` and `model_profile_rollback`. Reads, unknown tools, non-connector runtime prompts, `model_profile_capture`, incomplete JSON and items that cannot be displayed in full are refused; use their ordinary approval path. Each item receives a durable proposal ID and its own one-shot grant, including when two items are identical. The tool returns the approved canonical calls in item order. Connector calls retain their existing Apply path; an exact built-in call consumes its grant through the ordinary built-in tool and executes without a second card.

A built-in item's batch and item cards show its managed before → after proposal as well as the complete redacted canonical arguments. Preparation runs the existing setter validation or the profile switch/rollback dry-run without writing. Model-profile items share one private catalog plan: each edit sees the preceding approved edits' after-images and the catalog revision advances only in that plan. Execution compares the freshly rebuilt display and expected revision with the approved item under the existing state lock. Thus sequential profile edits and a switch to an edited profile work, while any external catalog write still conflicts instead of being rebased.

Call approved items once in the listed order and stop at the first error. A built-in item cannot overtake an earlier granted or running built-in item. The first failure records its exact item position, completed items and unexecuted later items; later unused grants become stopped. A completed write whose read-back fails is recorded as completed and still stops the batch, never as an unexecuted failure. Denial grants and executes nothing. An outcome that cannot be recorded is reported as uncertain with an instruction not to retry or continue. Ordinary direct built-in calls without a matching grant keep their previous behavior.

The approval authority is the complete canonical input, not a prose summary. Canonicalization sorts object keys and removes insignificant whitespace while preserving every string, number, array position and recipient/body/account/attachment field. Duplicate object keys are rejected. A SHA-256 fingerprint locates a candidate grant, and complete canonical-byte equality decides the match; a digest alone never authorizes a call. Generic connectors have no common recipient schema, so this complete-payload comparison is also the recipient binding. Display redaction does not remove a secret from the comparison. An edited sentence, changed recipient, different tool or different origin receives no grant: its connector call first waits on a fresh ordinary card and executes nothing.

Both `owner_reply_approval` and `persistent_owner_action_cards` default to false. With reply approval off, `owner_action_prepare` is unavailable and all existing calls behave as before. `owner_reply_approval_phrases` defaults to `["发","同意"]`; surrounding whitespace is trimmed and only ASCII `A`–`Z` are folded to `a`–`z`, but there is no substring, fuzzy or model interpretation. An empty phrase list disables reply approval without disabling ordinary Allow and Deny. Changing either switch does not revoke a grant that already exists.

A batch card and each item card advertise `owner_proposal`, `approval_batch_id`, optional `approval_item_id`, `owner_approval_phrases`, `resumable` and, for persistent cards, explicit `no_expiry`. An exact answer to the batch approves every pending item once; an exact answer to one item approves only that item. Ordinary Allow and Deny on those cards use the same durable decisions. Neither path creates an Always rule or a standing authorization. An answer claims its exact live occurrence against timeout before writing the durable decision. A definitive rejection with the durable target still pending releases that temporary claim and lets the waiter arbitrate again. An ambiguous storage error is reconciled against the durable target before any release; while its outcome is unknown the card remains claimed, fail closed. A settled decision completes with the first durable answer, which may differ from a later conflicting request.

Feishu accepts an exact phrase only in the authenticated owner's DM, directly replying to the stored parent message for that exact proposal. The channel, card, batch/item, occurrence and origin must agree, and a fresh one-use hub proof binds the event before a decision is recorded. Web, Apple and Android send `{text,client_msg_id,approval_reply_to,approval_reply_created_at}` on the existing authenticated session-message endpoint; the timestamp is the card's exact RFC3339 occurrence and older clients may omit it for legacy ID-only retry behavior. The target is explicit rather than inferred from nearby prose. The send must be the owner's own full-device input with no `via`, reply wrapper or extension/manager attribution. A successful reply returns `{ok:true,approval_reply:true,interaction_id}` and is not delivered to the node or model. A client treats a missing or mismatched receipt as failure, never as success or a reason to fall back to ordinary delivery. Relayed claims, forwarded text, another conversation, an unauthenticated principal, a stale occurrence and an altered proof cannot approve; a later connector call still needs its ordinary fresh card. An absent live card is an idempotent success only when the durable target is terminal; a durably pending proposal during restoration is not acknowledged.

The first terminal decision for a target wins under revision-checked storage. Duplicate events, concurrent decisions and restart recovery cannot create another grant. The connector or built-in gate consumes the exact grant before an ordinary approval card or direct write can proceed, so concurrent calls can produce at most one execution and every other connector call waits for its own approval. An exact built-in call whose durable state is pending, denied, cancelled, stopped or consumed fails rather than bypassing that decision; a newly prepared batch is a separate explicit operation. Deny consumes no operation and executes nothing. Disabling the feature never converts a pending or granted item into a standing rule.

With persistent cards enabled, an unanswered batch and its items have `no_expiry:true`; zero `expires_at` is not globally reinterpreted. Startup restores only valid owner proposals carrying the complete persistence metadata. They remain in the original conversation and Feishu across the former deadline, caller departure and restart until Allow or Deny. Startup cancels nonpersistent pending proposals instead, while already granted items remain available for their original connector or built-in continuation. A restart never executes an operation by itself, and an interrupted Apply with an uncertain external result is never replayed automatically.

The advanced Assistant settings on Web, Apple and Android expose both reversible switches and the phrase editor only when the hub supplies the new fields. Native clients confirm both the PUT response and a fresh GET before treating a value as saved. Older hubs keep the existing UI and connector approval behavior. The design intentionally uses the narrow explicit `approval_reply_to` envelope rather than guessing a batch from chat text, retains direct card decisions as an equal entry to the same durable book, and falls back to ordinary approval for third-party runtime prompts that cannot supply the required proof.
