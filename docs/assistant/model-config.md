# Model providers and model configuration

## What the three entry points control

- **Settings › Model Providers**: connection method, API protocol, gateway, encrypted credentials, default model, and existing launchers on your computers. The old “Models” page lives here; existing synchronization, hiding, details, and quota features remain.
- **Settings › Model Settings**: configures six default-model categories: conversation defaults, Agents, information processing, information screening, question delegation and translation. Each selects a provider, specific model, and supported thinking effort; launcher-backed purposes (`kind: "launcher"`) also support an optional unified `permission_mode` (`default`, `acceptEdits`, `plan`, `auto`, `bypassPermissions`, filtered by what the selected launcher supports; never exposed for direct API or plugin purposes). Their purposes follow them, with opt-in exceptions: translation has its own setting and starts from information screening's provider/model, using a cheap Haiku model for Claude Messages connections; the Inbox's **AI twin** and **Lark /agent** can each override Agents and can be reset to follow it, and **Meeting minutes** and the **In-meeting conversation** can each override their category (Information processing, Main chat) the same way (#7980, "Meeting minutes and the in-meeting conversation (#7980)" below). Named [model profiles](model-profiles.md) switch the category bindings and launcher model fields together; `agent_start` and `task_plan` can select a profile tier or explicit model override. The assistant's shared default launcher / model is selected under “Conversation defaults”; “Main chat” can override it for the main conversation only; a chat switched to another model in the chat keeps that until it is reset (“A conversation's own model”). Effective permission mode follows `explicit caller/session override > tier preset > purpose binding > CLI native default`, normally applies only to new starts/conversations; the Inbox exception below also applies when a stopped chat resumes, and neither path restarts a running one, and never weakens `readonly: true` task constraints, Inbox AI twin allowlists, or guest tool sandboxes.
- **Settings › Assistant**: Persona itself: proactive work (scheduled tasks, run history), understanding you (about me, memory), Skills, the machine it runs on, and its working directory. It neither displays nor configures models (#1291): the “Assistant” row on the settings home page has no launcher name, and the page has no “Chat model” entry. This is consistent across iOS, Mac, web, and Android. Switching one chat's model from the chat itself is not configuration either: the pick stays with that chat (“A conversation's own model”).

The home page has six category rows and separate **AI twin runs** and **Lark /agent** rows, each showing whether it is separately configured or follows Agents, and the **Meeting minutes** and **In-meeting conversation** rows, each showing whether it is separately configured or follows its category. “Applies To” remains read-only and collapsed by default; those rows open their own editors rather than a category. The manager supplies the catalog and descriptions (forwarded by hub; see “Who owns models” below). Model names take priority; provider details live in the editor. “Unverified” is not repeated across the home page, but real errors and rate limits still appear.

| Category | Preserved configuration ID | Scope |
| --- | --- | --- |
| Conversation defaults | `assistant` | Direct chats with the current persona, scheduled tasks, a meeting's room conversation unless the In-meeting conversation is separately configured (`meeting.room`, #7980) |

The web settings editor exposes the independent translation row. Native SwiftUI and Compose action bars do not share this React settings view; native model-settings parity remains a separate follow-up.

The background supervisor (`docs/assistant/unified-entry.md` "Background supervisor") runs under the purpose `assistant.supervise`: it follows Main chat until it is given its own launcher, model or effort with `PATCH /api/v1/model-config/purposes/assistant.supervise` (sparse, revision-checked, a record of its own under `model_config.assistant.supervise`), so it can run on a cheaper or a stronger model than the main chat. The catalog `GET /api/v1/model-config` returns lists it (#5806; see “The background supervisor in the catalog” below), and a hub before that answers it by its own ID only. A Persona-managed provider it runs on is not deleted underneath it (“Deleting a provider in use”). It applies when the background supervisor's conversation starts and on every message sent to it.

## Providers and execution methods

| Execution method | Used for | Constraints |
| --- | --- | --- |
| Direct API | Triage, assessment, translation, drafting, knowledge processing, titles | Messages, Responses, or Chat Completions; the manager reads / decrypts credentials and sends requests itself |
| Launcher | Claude Code / Codex chats and Agents | Must exist on the execution machine; the CLI/app-server must actually receive the specific model |
| Plugin model | Integrated voice services | Only models provided by that plugin can be selected; the plugin's own provider and credentials are not changed |

Persona's own model gateway requests use `User-Agent: Persona/<version>` by default; a provider's custom `User-Agent` takes precedence where custom headers are supported. Agent processes send their own headers.

The original `/launchers` API remains. New connections have `kind` of `launcher` or `api`; omitted on legacy entries, it still means launcher. Messages-protocol API connections (`api` empty or `messages`) can also be selected for the main chat and Agents: node starts claude with their address and key (#2455; see `docs/integrations/claude-integration.md` for environment variables). Responses and Chat Completions connections support only direct calls; `finishModel` refuses to treat them as launchers. Chat Completions can be configured manually, while extension provider declarations accept only Messages and Responses. Legacy API connections (`ai`, `inbox.*_ai`, `kb.ai`, in the manager's `manager.json` since 2026-11-06, in `hub.json` before) appear as compatibility sources; authentication-file paths and values are not returned to clients.

## Execution form

`ModelPurpose.launch` is a read-only value derived from the purpose's `kind` and ID or parent, not from its provider.
It is returned by the model-configuration list and detail endpoints, never stored in a binding, and rejected in PUT/PATCH.

| Purpose | `kind` | `launch` | Execution |
| --- | --- | --- | --- |
| `assistant`, `schedule`, `task.*`, `assistant.supervise`, `meeting.room`, `inbox.agent`, `lark.agent` | `launcher` | `headless` | Background process, without a terminal panel (`meeting.room`: always Claude Code's CLI, #7980) |
| `agent.new` | `launcher` | `engine` | Interactive Agent in the target computer's terminal host |
| `kb`, `inbox.triage`, `agent.delegate`, `meeting.minutes`, other API purposes, `extension.*` | `api` | omitted | HTTP requests sent directly by the assistant; with a Claude Code, Codex, or Antigravity launcher that has no Messages gateway picked, one isolated headless CLI run (`claude -p`, `codex exec`, or `agy -p`) per request on the main chat's computer (#5823, #12027) |
| `plugin.*` | `plugin` | omitted | The plugin's own model service |

Non-launcher purposes always have an empty launch value, even if their parent is a launcher.
`applyModel` overwrites any caller-supplied `launch` in node-call params. `startOn` requires `headless` before
`assistant.send`; a new `AgentStartParams` requires `engine` before `session.start`. Existing launcher, model, effort,
permission and resume choices are unchanged.

The web page groups purposes by `(kind, launch)`: **Persona chats · Background process**, **Agents · Interactive**,
**Background processing · Direct API**, then **Extensions** (only when installed; extensions' own API purposes stay here).
These groups describe execution, not inheritance levels. The AI twin and Lark /agent sit alongside the main chat in the
background-process group, each with **Inherits the Agents model · Runs as a background process** when following Agents, or
**Separately configured** when overridden. Their reset action still says **Follow Agents**. Only **New agent** sits in the interactive group.
The In-meeting conversation sits in the same background-process group right after Main chat and the background supervisor,
and Meeting minutes in the direct-API group right after Information processing (#7980): each says **Follows Main chat** or
**Follows Information processing** while it follows, **Separately configured** when overridden, and its reset action
**Follow Main chat** or **Follow Information processing**.
Scheduled tasks follow the main chat's category; this presentation does not add independent task settings.

Each row's neutral execution chip has a fixed form and a backend that follows the effective provider:
`Background process · claude -p`, `Background process · codex app-server`, `Interactive · herdr · claude`, `Direct API · Messages` / `Responses` / `Chat`, or `Direct API · claude -p` / `codex exec` / `agy -p` when a launcher without a Messages gateway is picked for an API purpose (#12027).
The terminal host is a computer setting, not a provider property: only a purpose bound to a known computer shows its
configured default host; `agent.new` says **By machine**. The editor previews backend changes before saving.

The trailing **?** expands an inline explanation on desktop hover, keyboard focus or click (including touch).
Click pins or closes it; Escape or a click outside dismisses it. This stays inside the settings card so long explanations
remain readable on narrow screens and at larger text sizes, without nesting a help button inside the edit button.
The explanation covers environment, configuration directories, compatible providers, typical uses and the current backend:
headless processes use the assistant's working directory and the launcher's environment/configuration;
interactive Agents use the target computer's terminal host environment and launcher configuration;
direct API purposes use provider connections/credentials and no terminal or Claude/Codex profile;
plugins use their own environment, configuration and credentials.
**Unverified** means launcher execution on the target computer has not been confirmed, not that a paid model request succeeded or failed.

### Testing background Direct API drafts on the web

The editors for information processing, information screening, and question delegation fetch the selected connection's
model list through `POST /api/v1/launchers/discover`, while retaining manual model-ID entry. Reasoning choices follow the
selected model's metadata; an existing unlisted value remains visible rather than being silently replaced.

**Test connection** sends the draft connection name, model, and effort to `POST /api/v1/launchers/test`. The manager resolves
the saved connection's encrypted credentials and network route and issues a small request, with the same effort translation
as real API calls (`off` becomes Chat Completions or Responses `none`, for example). A successful result echoes the tested effort and includes
`ms`, the elapsed provider request/response time in milliseconds. If a Chat Completions gateway rejects the parameter itself and the bounded
without-effort retry succeeds, the result returns an empty `effort`; it must not mark the requested level verified. Unsupported effort cannot be reported as verified.
Authentication, missing-model/endpoint, timeout, and other failures keep actionable details, with credentials redacted.

Omitting effort (or sending `null`) tests the saved connection's default effort, which real API calls also inherit when
their purpose has no effort override. An explicit string overrides that default; `""` tests clearing it in a provider
draft. The purpose editor sends its resolved inherited effort when one is shown and otherwise omits effort for **Use
default**, while the provider wizard sends its draft value, including an explicit clear. A stored `no_effort` Chat
capability can resolve the requested effort to empty; that empty echo is expected because real calls apply the same
capability. Connection tests never inherit an unrelated purpose's effort.

A test never saves the draft or changes purpose/provider defaults. Verification belongs only to that open draft:
changing the connection, model, or effort invalidates it, including while a request is outstanding. Closing the editor
discards it. Launcher execution health is a separate status; an API probe does not verify a launcher.
The iOS and Android purpose editors do not yet provide this draft test; Android also retains its free-text purpose effort
field. Native parity is tracked in #6887.

### Managed sample diagnostics with `model_probe`

The assistant's `model_probe` MCP tool runs 1–10 caller-supplied samples through one **saved** provider. Unlike the web
editor's draft connection test, its public input has no draft connection fields: a caller can select only the registered
provider name, `messages` or `chat` on that same gateway, and optional model/effort overrides. The manager alone resolves
the sealed key, custom headers, proxy and `via_machine` route. Unknown fields, including `api_key`, `headers` and
`base_url`, are rejected before any request is sent, and neither credentials nor arbitrary connection overrides appear
in the result.

This is configuration-read-only, not side-effect-free: every sample is a real provider inference request and may consume
quota. It does not write settings, profiles, purposes, launchers, conversation state, launcher health, or Chat
compatibility cache entries. Restricted Inbox handling chats do not receive the tool.

Each sample has a required nonempty `user` and optional `system`, `id`, and `label`. Combined system+user input is at most
16 KiB per sample; IDs and labels are at most 128 Unicode code points. Concurrency is 1–4 (default 1), `max_tokens` is 1–1024 (default
256), and each sample's end-to-end timeout is 1–30 seconds (default 30). A direct provider response is read up to 1 MiB.
A `via_machine` response is first buffered by the existing `model.http` transport under its separate 16 MiB cap, then
subject to the same 1 MiB probe parsing cap. Returned text is credential-redacted and UTF-8-safely truncated to 8 KiB;
redaction replaces every occurrence of a stored credential/header value, even when it appears as ordinary answer text.
Provider-controlled block types and `Retry-After` are redacted too. A usage entry whose field name requires redaction is
omitted rather than returned under a colliding `***` key; ordinary numeric usage is unchanged.
Results remain in input order and report `index`,
optional `id`/`label`, `ok`, full sample `ms`, `http_status`, redacted `error`, ordered unique `block_types`, bounded
`text`, separate `text_truncated` (the 8 KiB output cap) and `generation_truncated` (the provider's token limit), optional
numeric `usage`, and the number of compatibility `attempts`. Messages block types include `thinking` and
`text`; Chat reports `reasoning_content` and `text` without returning reasoning as answer text. The top level reports the
resolved provider/API/model/effort and total/succeeded/failed/total_ms.

Messages requests use non-streaming responses; Chat uses the normal SSE stream. `effort:"off"` always puts
`thinking:{"type":"disabled"}` on the Messages wire and `reasoning_effort:"none"` on Chat rather than silently using a
model-specific low-effort fallback. Existing bounded Chat compatibility retries may remove a rejected effort field,
rename `max_tokens` to `max_completion_tokens`, or remove `stream_options` after a 400/422 rejection; the per-sample
`effort` describes the final attempt and becomes empty
when effort was removed, while the top-level `effort` remains the requested/resolved value. A 429 is never retried: its
status and credential-redacted `Retry-After` header are returned (ordinary values are unchanged). HTTP, network, timeout, malformed-response, stream-error,
HTTP-200 provider errors, refusals and empty/unfinished-stream failures remain attached to their sample instead of being
silently counted as successes. A provider token-limit ending remains a successful inference with
`generation_truncated:true` so partial text cannot be mistaken for a complete answer.

## Sending through a computer (#4775)

API purposes are HTTP requests the manager sends from its own machine. When that machine has no route to the provider
(a locked-down server, a home server behind a restrictive network) while one of the user's computers does, an API
connection can name that computer under **Send through** (`via_machine`). Empty is **The hub itself**, the behavior
before this setting.

- **What moves**: only the network hop. The manager still builds every request (prompt, model, parameters, headers)
  and reads every answer (stream parsing, errors, the upstream gate); the request goes to that computer's node as one
  `model.http` call (`docs/protocol/protocol.md`, "hub ↔ node RPC"), and the node sends it with its own network and
  proxy settings. "Test connection" and "Fetch models" go the same way, so a test says what real calls will do.
- **Credentials**: the manager decrypts the key as before and puts it in that one call's headers. The node never stores,
  logs or shows it, never puts it in an error, and zeroes the params once read. No key is configured on the computer.
- **Streaming**: the node reads the streamed answer to its end (at most 16 MB) and returns it whole; the manager parses
  it as it would a direct stream. Calls that only use the final text behave the same.
- **Cancelling**: when the manager stops waiting (a timeout, a stopped conversation) it sends `rpc.cancel` and the node
  ends the request; the call's deadline goes along as `timeout_ms` (capped at 10 minutes on the node).
- **Redirects**: the node never follows one; it returns it, and the manager's client decides as it would without the node.
- **Offline or gone**: an offline computer fails the purpose at once with "<computer> is offline", without falling back
  to the manager's network and without retries; a computer this manager no longer has says so; an older node without
  the `model_http` capability says to update it.
- **Which computers**: only a direct API connection (`kind: "api"`), and only a computer this manager carries (another
  manager's machines are not its to call). Others are 400. Changing it clears the connection's recorded failures.

## Running API purposes on a launcher (#5823, #12027)

Many users have no API key, only Claude Code, Codex, or Antigravity (`agy`) logged in on a computer (a subscription), which is what runs their
main chat and Agents. An API purpose (`kb`, `inbox.triage`, `agent.delegate`, their uses, `extension.*`) may therefore
pick a launcher provider too (with no extra `ModelBinding` field): each request then runs that launcher's CLI headless,
once, on a computer and returns its final text. Nothing reads, copies or re-serves the login (#4220 is a different thing):
only the prompt and the answer travel.

- **Which providers**: a launcher whose CLI is Claude Code (`claude`), Codex (`codex`), or Antigravity (`agy`) — plain
  CLI, `~/.zshrc` / `PATH` launcher, built-in Antigravity companion launcher, or a managed launcher that does not speak
  Messages — on that computer and in its scope. A managed launcher that speaks Messages keeps being called over HTTP with
  its own address and key, as before; direct API connections are unchanged. Other CLIs/runtimes without a verified
  zero-tool contract (such as `omp` or external runtimes) are not offered. A launcher deleted since it was picked fails
  with "can't call this provider", never a run.
- **Which computer**: the main chat's (Settings › Assistant), which the purpose's `machine_id` in
  `GET /api/v1/model-config` names. With none set, the purpose says so.
- **What is sent**: the manager resolves the purpose as always, then sends one `model.run` call to that computer's node
  (`docs/protocol/protocol.md`, "hub ↔ node RPC") with the launcher, the chosen model and effort (empty: the launcher's
  own), the system prompt and the conversation. A single user turn goes as it is; several are rendered as one transcript
  (`prompts/tools/launcher_run_input.md`). The answer is the run's final text, with the CLI's token counts when it
  reports them.
- **Counting**: these runs leave no transcript on the computer, so the manager logs one `model_usage` line per
  completed purpose call on any route (`api`, `api_via_node`, `cli`): purpose, operation (Inbox event grouping is
  `inbox_group`), provider, model, result and input / output / cache read / cache write tokens (#10492). A call that
  never ran (paused, nothing configured) is not logged. Extensions' `model.complete` calls are logged the same way, one
  line per request to the model. Each logged call is also added to the manager's `model_usage` table, one row per UTC
  day, purpose, route, provider and model (calls, failures, the four token sums); a write drops the days older than 60.
  `GET /api/v1/model-config` gives each listed purpose its last 7 UTC days as `usage` (its own calls and those of the
  unlisted uses under it: Information processing's titles, translation and the rest), and the web's Settings › Models
  shows "Last 7 days: N calls · M tokens" under a purpose with calls (#10498), then "· K failed" in red when any of
  them failed, so a purpose whose every call fails does not read as merely busy. Its tokens are input + output + cache
  writes; cache reads are left out of that number, since they cost a fraction and would swamp it, and the line's
  tooltip lists all four. The Apple and Android apps do not show it yet.
- **How it runs and isolation guarantees**: the node runs the launcher in a fresh `persona-check-*` temporary directory
  that is removed afterwards. Prompts and system instructions are passed through `0600` temp files / stdin (never argv)
  and are never logged. Each supported CLI enforces zero-tool, zero-MCP, zero-hook, and no-session-persistence boundaries
  and **fails closed** (refuses with an update error rather than retrying without isolation) if the installed CLI rejects
  any required isolation flag:
  - **Claude Code (`claude -p`)**: `-p --output-format json --max-turns 1 --no-session-persistence --tools '' --strict-mcp-config`,
    `--system-prompt-file` for the system prompt, `--settings` with `{"disableAllHooks":true}`, and prompt on stdin.
    Any residual Claude project entry for the temp directory is removed on exit.
  - **Codex (`codex exec`)**: `exec --ephemeral --ignore-user-config --ignore-rules --skip-git-repo-check -s read-only --color never --json`
    with `-c approval_policy="never"`, `-c mcp_servers={}`, `-c web_search="disabled"`, `-c agents.max_depth=0`,
    `-c include_apply_patch_tool=false`, and `--disable` for `shell_tool`, `unified_exec`, `apps`, `plugins`, `hooks`,
    `multi_agent_v2`, `multi_agent`, `sleep_tool`, `view_image`, `goals`, `code_mode_host`, `browser_use`, `computer_use`,
    `image_generation`, and `memories`. System prompt goes via `-c model_instructions_file=...`, effort via
    `-c model_reasoning_effort=...`, and the user prompt via stdin (`-`).
  - **Antigravity (`agy -p`)**: runs with a workspace-scoped custom agent (`.agents/agents/persona-model-run/agent.md`)
    declaring `tools: []`, `commandExecutionPolicy: off`, `mcpServers: []`, `skills: []`, `plugins: []`, `subagent: false`
    (with the system prompt as its Markdown body), paired with defense-in-depth `--settings` (`agentMode: ""`,
    `toolPermission: "strict"`, `allowNonWorkspaceAccess: false`, `disableSlashCommands: true`, `statusLine`/`title`
    disabled, and `permissions.deny` covering `command(*)`, `read_file(*)`, `write_file(*)`, `read_url(*)`,
    `execute_url(*)`, `mcp(*)`, and `unsandboxed(*)`), `--disable-slash-commands`, and `--input-format stream-json --output-format stream-json`
    so the prompt is fed on stdin as a single NDJSON user turn. An isolated `HOME` inside the temporary directory symlinks
    only read-only auth/runtime assets (`antigravity-oauth-token`, `installation_id`, `bin`, `builtin`, plus macOS
    `Library/Keychains` when present; read-only copy fallback on Windows) so global `~/.gemini/config/` hooks/MCP are never
    loaded and zero session files or SQLite rows are written to the user's real `~/.gemini/antigravity-cli/`.
    When the installed `agy` advertises native per-session `systemPrompt.append` over `agy acp`, the node reuses at most
    one on-demand isolated warm `agy acp` worker (`--include-default-customizations=false --disable-telemetry`, `mcpServers: []`,
    per-session `session/new._meta.antigravity.systemPrompt.append`, immediate per-session cleanup after `session/close`,
    120s idle eviction, and 50-request rotation; its reuse key includes the stat of `antigravity-oauth-token` and, on macOS,
    the dates of the login-keychain sign-in item, so a new sign-in starts a new worker, #17860), transparently falling back to cold `agy -p` on slash-command prompts,
    conflicting model/effort arguments, concurrent second requests, missing capabilities, or transient startup failures;
    unexpected permission, elicitation, or tool requests fail closed and destroy the worker (any error or abnormal
    `stopReason` such as `cancelled` or unknown also destroys the worker, while normal terminal stops—omitted/empty,
    `end_turn`, `max_tokens`, `max_turn_requests`, or `refusal`—preserve the answer and warm worker, except that an answer which
    is only agy's quota or sign-in error line drops the worker).
- **Concurrency and time**: at most two runs at a time on one computer; others wait for a slot within their own time.
  The call's deadline goes along as `timeout_ms` (2 minutes without one, at most 10); when the manager stops waiting it
  sends `rpc.cancel` and the node kills the run. Each run pays a CLI start (seconds) on top of the answer, so this suits
  background work.
- **To-do titles on a launcher wait longer** (#13443): the title `todo.title` gives a to-do a task opens is asked for
  in the background (`docs/assistant/todos.md`, "To-do titles"), within 15 s on an API connection and 50 s on a
  launcher, inside that naming's one minute: agy runs that answered took 12 to 48 s in the issue's logs, so 15 s cut
  off runs that would have answered. `POST /api/v1/todos/retitle`, which its caller waits for, keeps 15 s.
- **Purposes that call tools**: no API purpose uses the provider's native tool calling. Inbox event grouping
  (`inbox_group.go`) asks for its tools in its JSON answer and the manager runs them, so it works unchanged, each step
  within its 45 seconds; a step that runs out of time falls back to the rule grouping, as any failed model call does.
- **Errors**: an offline computer fails at once with "<computer> is offline", without a fallback. A CLI that is not
  logged in, a run past its time and a node too old for `model.run` (capability `model_run`) each say so, localized.
  Other failures carry the end of what the CLI printed, without keys, URLs or addresses.
- **What does not change**: the automatic fallback of an unconfigured API purpose still picks only HTTP connections;
  "Send through" (#4775) belongs to HTTP connections and is not involved; the upstream rate-limit gate does not apply
  (the CLI's own subscription limits do).

## Editing and inheritance

The web model, profile and scheduled task editors group launcher models when at least two catalog IDs share a base
and end in their advertised default effort. The model picker shows the base name, searches the concrete IDs, and
accepts custom IDs. The effort selector shows the levels the catalog and save path support. Choosing a group starts
at Medium when available, or the first listed level, and keeps an explicit effort choice the group supports.
The saved model ID carries the level. A supported legacy effort takes precedence over the suffix and is cleared on
save once the catalog identifies the group. An effort override on a followed variant pins the matching concrete ID.

Each category shows both “In Effect” and “Model Settings”:

- Empty provider: inherit; empty specific model: use that source's default model.
- Changing providers clears the previous model and thinking effort, preventing fields from different providers being combined.
- “Restore defaults” clears only that category's choices; it takes effect after “Save,” and all its purposes reset together.
- The web provider wizard can test all three direct API protocols and discover paginated model lists. Catalog context windows take precedence over server-reported values; a server value fills a missing catalog window. If discovery fails, a valid model ID can be entered. Saving is not a paid-availability test. Chat Completions uses Bearer authentication and supports direct model purposes; the server accepts reasoning effort for Responses, Messages and Chat Completions. The web purpose editor offers the same saved and cleared effort controls for Chat Completions on direct categories and purposes with their own records, using stored model capabilities with discovery as a fallback in the direct editor and the direct-purpose protocol levels when metadata is unknown. `providers[].models` carries the stored capabilities used by Chat requests and named probes; `providers[].model_aliases` resolves legacy Chat tier aliases to those stored model IDs. Current hubs mark Chat providers with `chat_effort: true`; an unmarked hub that already lists `effort` for the effective Chat provider remains supported. When an older hub lists effort only for Messages or Responses, switching to a different Chat provider hides the field and omits it from purpose saves. Voice uses its own real-time provider configuration, independently of these model connections.
- Offline, protocol mismatch, missing provider, and similar states are explicit. An invalid explicit configuration never silently switches providers. Direct-API Messages, Responses and Chat Completions providers carry sealed custom headers on saving, named connection testing/discovery and real calls, including Send Through and compatible launcher HTTP fallback. Values never return through the read API; `header_names` identifies configured fields without exposing them. Reserved protocol and credential fields are rejected, same-origin redirects retain headers, cross-origin redirects omit them, and probes never follow redirects. Direct-API proxy and no_proxy remain rejected because the manager cannot honor those settings. Existing stored entries remain available for repair: explicitly clear these proxy fields in the provider settings; saving, named connection testing/discovery, and direct calls otherwise refuse the unsupported configuration. Antigravity and omp outside its documented Anthropic-compatible custom-gateway path cannot launch with arbitrary headers, so their header-dependent checks fail explicitly instead of implying runtime support.
- **The main chat on a computer's own launcher** (#11772): `provider_ids` lists Model providers only, and they leave out a runtime's launchers. A main-chat purpose (`assistant`, `schedule`, `assistant.supervise`, a task's) set to a launcher that its computer's main-chat picker offers (`?purpose=assistant`, "A conversation's own model (#5033)": a runtime that declares the assistant capability, or a hub.json wrapper only that computer names) gets the status any launcher there gets (unverified, computer offline, node outdated), not "Provider missing or incompatible". The check reads the computer's launchers as last seen and asks no node, by the picker's rule: a Persona-managed provider in that computer's scope takes the place of the computer's own launcher by the same name, so the provider's own compatibility decides. It does not ask whether a provider that skips computers with their own service is used there either: an answer missing or out of date counts as no own service, so reading Model settings never waits on a node (the pickers still ask). A launcher gone from that list, or one there that can't run assistant chats (a runtime without the capability), is still reported incompatible. `meeting.room` keeps its own status for a runtime ("Meeting minutes and the in-meeting conversation (#7980)"). Code: `mainChatOffers` in `server/internal/assistant/launcher_mainchat.go`.
- Concurrent edits to the same item from two devices use revision checks. Conflicts retain the draft and require reloading before saving again.

For launcher purposes without a bound machine (such as Agents), saving a specific model uses the model picker's online-machine selection among the provider's reported machines. This also applies to effort-only edits with an existing model and to model-profile switches. If every candidate is offline, the binding can still be saved without a live model check; it remains unverified. A purpose bound to a known machine still validates there, and an online node's model-validation error still rejects the save. These checks do not make a paid model request.

For API purposes (triage, assessment, drafting, translation, knowledge processing, titles), when there is no override or legacy `ai` configuration in the manager's `manager.json`, automatically choose a connection directly callable from the hub: first the first `kind: api` entry, then the first Persona-managed launcher with a key and Messages protocol (excluding hidden entries or those missing an address / default model / key). Use its default model. “Inherited From” shows “Automatic selection”; no override is written, and later selections here still take priority. Automatic selection by these built-in categories alone does not block provider deletion when another eligible connection can take over: the next eligible connection takes over, while an explicit provider choice (or deleting the last provider that leaves no eligible connection) still returns 409. If none exists, status and errors explain where to configure one (#388, 2026-11-02: with only “Claude Code default” configured, reply drafting immediately returned no model configured). Responses, Messages and Chat Completions protocols support thinking effort configuration; Information screening (`inbox.triage`) defaults to no thinking (`effort: "off"`), including after a provider-only selection, while explicit effort levels are preserved. The caller maps `off` to Chat Completions or Responses `none` and the model's supported Messages no-thinking mode (`thinking: {"type":"disabled"}`, or `between_tools` for Sonnet 5.5); Messages models that cannot disable thinking use `output_config.effort: "low"` instead. Chat sends `reasoning_effort`, and like Responses it passes accepted levels such as `max` through without a local clamp; direct-purpose validation rejects `ultra` for both. For Chat, a provider model entry with `no_effort` suppresses the field, as does a nonempty direct capability list (`all_efforts` when present, otherwise `efforts`) that excludes the requested level (`off` counts as `none` for `all_efforts`); empty lists remain unknown, and an `efforts`-only entry keeps `off` as a separate control. A 400 that explicitly rejects the parameter itself causes one logged retry without it; for an off request only, a 400 rejecting `none` as a value gets the same retry. Explicit non-off levels, effort ceilings and other 400 responses are not retried, and `X-Should-Retry: false` prevents both retry and learning. Whole-field and none-only rejections are cached separately for one hour by Base URL, credential, route computer and model (128 connection/model entries at most process-wide), so subsequent probes and real calls skip the field without first failing again.

Launchers such as “Claude Code default” are only CLIs on computers, without an API address or key, so automatic selection never picks them. Chosen explicitly, they run each request headless on the main chat's computer (“Running API purposes on a launcher”); `off` / `none` effort then leaves the launcher's own.

## Background model groups in persona_settings

The assistant can read and change the four independently stored background API categories through `persona_settings`: `model_config.kb`, `model_config.inbox.triage`, `model_config.agent.delegate`, and `model_config.translate`. Uses that merely inherit from one of these categories are not separate settings. `list` exposes all four; `get` returns the category's override, effective provider/model/effort, revision, compatible `purpose.provider_ids`, and credential-free provider metadata.

For `set`, `value` is exactly one provider ID string from `purpose.provider_ids`, for example `{"action":"set","key":"model_config.kb","value":"launcher.example"}`. Unknown, unconfigured, and incompatible IDs are rejected before a card is created, and the error lists the valid configured choices. The phone card shows the effective before → after bindings, including the provider default model. Nothing is written before approval. Approval revalidates the record revision, provider catalog, compatibility, and exact proposal under the model-configuration lock; a different provider clears the old model, effort, and permission mode just as Model Settings does. Setting the previous provider again is the rollback path.

`test` takes the same provider ID string, for example `{"action":"test","key":"model_config.kb","value":"launcher.example"}`. It reuses the existing bounded Direct API or computer-launcher connection check and returns its structured result without creating an approval card or changing the model-group record. It is intentionally separate from `set`: Model Settings permits saving an unverified or offline provider, so a successful probe is not a new save requirement. Neither `get` nor `test` returns credentials, sealed credentials, tokens, or secret header values.

## Lark /agent override (#5921)

`lark.agent` is an editable launcher purpose with `parent: "agent.new"` and `category_id: "agent.new"`, not a sixth default category. It supports the same provider (including launcher providers), model, and effort fields as Agents. Nonempty fields override the Agents binding; choosing a different provider drops the inherited model and effort before applying this purpose's selections. With an empty binding, every `/agent` conversation inherits Agents, including subsequent changes to Agents. The current binding applies to new conversations and to an existing topic conversation on its next input; it does not interrupt a running turn or change its permission mode. A different execution engine uses the durable logical-switch flow: the original input is queued behind the switch and carries its context handoff, rather than silently running on the old model. An explicit launcher or model on one message still takes precedence (#14750).

GET `/api/v1/model-config/purposes/lark.agent` returns this purpose's own revision, override, effective binding, and writable fields. PUT and the compatibility PATCH endpoint share sparse updates and optimistic locking. To restore following Agents, send the current revision and explicit `null` for `provider`, `model`, and `effort`; omitting fields leaves them unchanged. Stale revisions return 409 without overwriting a draft.

**Dormant settings do not revive:** new user saves use `model_config.overrides.v1.lark.agent`. The retired `model_config.lark.agent` record, its revision, and old extension launcher defaults are neither copied nor consulted. Before the first new save, the independent revision is 0 and the override is empty, even when the old record exists. Reset stores an empty binding at the next revision in the new namespace; it never falls back to the retired record. Category-default/provider assignment does not populate the opt-in record, and provider deletion protects a provider used only by this override.

The web catalog includes the separate row and a reset-to-follow action. Android uses its existing `/agent` model entry and editor. The Apple editor edits a child with writable `fields` in place and redirects a read-only one to its category (#5925, #6029).

## AI twin override (#4232)

`inbox.agent`, the model the Inbox's AI twin starts its handling chats on (`docs/assistant/inbox.md`, "AI twin: handling chats and suggestions"), is set apart exactly like Lark /agent: an editable launcher purpose with `parent` and `category_id` `agent.new`, the same fields, validation (Agents' launchers only, no effort on Codex) and API, its own revision, and **Follow Agents** to reset. The twin is a high-volume, short-lived background job, so people run it on a cheaper or faster model than the Agents they start themselves; before this, that meant changing every new Agent too.

- **Unset follows Agents for provider, model and effort**: with nothing saved, or after a reset, the next handling chat starts on Agents' binding, including later changes there. Nobody who doesn't open this row sees a change.
- **Permission is the safety exception**: with no `permission_mode` saved on `inbox.agent` itself, a handling chat uses `default`, never an inherited Agents `bypassPermissions`. Only an explicit AI-twin permission choice replaces that default; clearing it restores `default`. A caller-supplied mode cannot elevate Inbox, and Plan or an unsupported mode on the resolved launcher falls back to `default`; the settings API rejects a new Plan choice. The choice applies to new chats and stopped chats when they resume, without restarting a live process. It travels separately as manager-only `inbox_permission_mode`, so an older manager's caller-controlled mode cannot elevate a new node and an older node retains its default clamp. Manager/node origin policy and tool gates remain independent of the launcher mode.
- **Its own namespace**: a save goes only to `model_config.overrides.v1.inbox.agent`. The retired `model_config.inbox.agent` record, its revision and the old `inbox.agent.launcher` are neither read nor copied; before the first save the revision is 0 and the override empty.
- **Its machine**: launcher and model checks run on the computer the twin starts on (`inbox.agent.machine` when the hub has it, else the assistant's). That choice, the twin's switch and its rules are Inbox settings and are not part of this purpose.
- **Unchanged elsewhere**: saving changes neither Agents nor Lark /agent, and running handling chats keep the launcher they started on. Provider deletion is refused while only this override uses the provider; category-default assignment never writes it; model profiles switch categories only.

Clients find these rows by data, not by ID: a purpose with `parent: "agent.new"` and writable `fields` is an Agents override (web `agentsOverride`, Android `agentsOverride`, Apple `ModelConfigurationModel.followsAgents`), shown with "Separately configured" / "Follow Agents". An older hub that still sends `inbox.agent` with `fields: []` keeps it a read-only use of Agents.

## Extensions' own purposes (#6102)

An extension granted the `models` scope (docs/extensions/extensions.md "Model calls") gets an API purpose `extension.<extension id>`, named after the extension, in the group "Extensions":
`kind: "api"`, `parent: "kb"`, `category_id: "kb"`, with its own record (`model_config.extension.<id>`), revision and writable `provider` / `model` (`effort` with a Responses, Messages or Chat Completions connection), the same shape as Lark /agent.
With an empty binding it follows "Information processing" (`kb`), including later changes there; a pick here is the extension's alone and does not touch `kb`. Its `model.complete` calls resolve this purpose at the start of each call,
so a change applies from the next call. The extension never chooses the connection and never sees a key. The prefix is not `plugin.`: the apps take `plugin.<id>` for a voice plugin and fetch its own model list for it. No budget and no cap (the user's decision).

**Candidate models (#10398).** A call may name candidate models (`models`, docs/extensions/extensions.md "Model calls"), tried in order. Each candidate runs only on a provider the user configured here that
the manager calls directly and that offers the model: one that lists it, the purpose's own provider for the model the purpose is bound to, or the purpose's own provider when it declares no model
list (#10657: a provider set up with only a default model refused every other model, the user's own pick for the purpose included); the extension names models, never providers or keys.
Listing the models on a provider (Settings › Model providers) makes the choice explicit and lets another provider take a model the purpose's provider does not list. The purpose's `candidates` object shows and keeps the user's control:

- `mode`: `extension` (the default: the lists the extension sends), `off` (ignored: every call runs on the purpose's model, as without candidates) or `custom` (the user's own list, used for every call
  whatever the extension sends).
- `custom`: the user's ordered list, `{model, configured_model?, provider, provider_name, available, problem?}` per entry; `requested`: the lists the extension sent lately (newest first, at most 8, each with `last_used`), each model
  with the provider it resolves to now or `available: false` and why. `modes` and `most` (8) say what the hub takes.
- PUT / PATCH take `"candidates": {"mode": "off"}`, `{"mode": "custom", "custom": [{"provider": "launcher.<name>", "model": "<id>"}]}` (1 to 8 entries; each provider one of the purpose's
  `provider_ids` that can be called directly, the model a model ID or empty for the provider's default), or `null` to go back to the extension's lists, with the purpose's `revision` like its
  other fields. Other purposes refuse it (400). Changing the purpose's provider or model keeps the candidate setting. The record is `model_config.extension.<id>` (`candidates`); the requested lists
  are kept apart in `model_candidates.requested.<id>`, written only when a list is new or was last seen over an hour ago.
- `direct_provider_ids` lists the IDs of managed providers the selected manager can call directly for this purpose. Each eligible connection has a configured URL and key. Offer only its intersection with the purpose's `provider_ids`. An empty array means no eligible connection. Older hubs omit the field. Their editors can narrow the purpose’s provider list to visible, keyed, managed API or directly callable Messages connections; the hub still validates the write.
- `configured_model` is the saved model ID for a custom entry. It can be `""` to follow the provider’s current default, while `model` gives the effective ID for display. Open the editor with `configured_model ?? model` so reordering or changing another entry preserves an explicit provider default. Requested entries have only the resolved `model`.

In Settings › Models, open an extension to see its requested lists, their last-used times, and the provider or unavailability reason for each model in order. These are the models the extension offered; the manager may have finished the call with an earlier candidate. The three modes use the extension’s lists, use only the ordinary purpose model, or use an ordered custom list. The custom editor accepts one to `most` distinct provider/model pairs, supports adding, removing and moving them, and allows a model ID to be entered directly. An unavailable saved entry remains visible for correction or removal. Built-in purposes and extension purposes from hubs without `candidates` use their ordinary editor.

Save candidate changes with the selected manager and the purpose revision. A binding-only save omits `candidates`, a candidate-only save can omit the binding fields, and a change to both can use a single revision-checked request. On a 409 the editor keeps the local draft. Reloading explicitly discards it and opens the current server revision.

`GET /api/v1/model-config` lists these purposes after Lark /agent; the manager tells the assistant which extensions have one (`app.call plugins.models`: enabled, compatible, granted `models` itself; the legacy `hub_api` full access does not count).
A switched-off or uninstalled extension's purpose is gone (404) and its record stays dormant until the extension is back. Each call's usage goes back to the extension in the result and into one log line of the manager; nothing is metered or limited. Chat Completions calls ask the server to stream that usage (`stream_options.include_usage`); a server that rejects the field gets the request once more without it and its usage reads zero.

Deleting a Persona-managed provider used by a current extension purpose returns 409, naming the extension in the same localized "still used" error as categories and Lark /agent. The provider and the extension's binding remain unchanged. Switch the extension to another provider in Model configuration, or clear its binding to follow "Information processing" before deleting; deletion is still refused if that inherited configuration or another current purpose uses the provider. Dormant records for extensions absent from the current catalog do not block deletion.

### Deleting a provider in use

`DELETE /api/v1/launchers/{name}` of a Persona-managed provider reads `providerModelUses`: every purpose of the catalog (the six categories, the AI twin, Lark /agent, the background supervisor since #5806, Meeting minutes and the In-meeting conversation since #7980) and every current extension purpose whose effective provider is that one. Any use answers 409 with the localized “still used” error (`assistant-models_launchers.err_in_use`) naming the purposes in the request's language, and nothing is changed. The background supervisor counts with its own provider, and with Main chat's while it follows it (the error then names both). Before #5806 it was not counted, so a provider only it ran on could be deleted underneath it. To delete such a provider, give the background supervisor another one or clear its override so it follows Main chat. An automatic selection by an API category is not a use when another provider would be selected without this one. The same list decides `in_use` when an import offers to hide an alias.

## Legacy configuration compatibility and unified application (#697)

No configuration copying or bulk database changes: reuse the four existing records `model_config.assistant`, `model_config.agent.new`, `model_config.kb`, and `model_config.inbox.triage` as category settings, preserving revisions and atomic concurrency checks. Without explicit selections, main chat uses the assistant's original default; Agents uses the original new-Agent default (Claude Code); information processing uses the old `kb.ai` / compatible triage-API baseline; information screening uses the old triage-API baseline. If the API baseline has no connection, continue automatically selecting a connection callable from the hub.

Other `model_config.*` purpose records, old `inbox.agent` / `lark.agent` dedicated launchers, assessment-specific APIs, and scheduled tasks' `Launcher/Model/Effort` no longer create hidden overrides. Original records remain for traceability. Resolution reads the owning category, except a newly saved opt-in AI twin or Lark /agent binding or a task's own binding, all in their separate namespaces. Do not claim every legacy purpose is preserved exactly.

Creating or normally editing a task through the tasks API or the app does not accept model settings, and returned task views do not show the legacy `Launcher` / `Model` / `Effort` fields; a task's own model configuration goes through its model purpose instead. Scheduled tasks (purposes `schedule`, `task.<task id>`) follow “Main chat” (#1570, old tracker #1544, decided 2026-11-04; they belonged to Agents before #697): they run in the assistant's working directory with its instructions, memory, and tools, so they are assistant chats, not newly created Agents. Under Agents, an unconfigured task used default Claude Code, making the “Morning briefing” fail every time with `Not logged in` on a hub machine not logged into it. New task runs and resuming their own chats resolve `task.<task id>`, which inherits the main-chat category until that task is given its own launcher / model / effort. An override is written through `PATCH /api/v1/model-config/purposes/task.<task id>` (sparse, revision-checked) or the `schedule_routine` / `schedule_followup` `launcher` / `model` / `effort` arguments, and is validated against the machine that starts the task's new runs. Its record lives under `model_config.overrides.v1.task.<id>`, so the dormant pre-#1570 `model_config.task.<id>` records never revive, and deleting the task clears it. The override applies when a run starts or continues the task's own conversation; a run sent into the conversation the task came from keeps that conversation's launcher, so the tools refuse a task's own launcher for a follow-up that continues its source conversation (`new_conversation: true` gives it one). A model or effort given without a launcher pins the launcher the task runs on at that moment, so a later Main chat change cannot pair the model with another agent. Messages the user sends into that task's conversation, and follow-ups sent back to it, still follow “Main chat” for every message, just like the main chat, rather than retaining the previous turn's launcher. Returning to a source chat (a follow-up the assistant schedules for itself with `schedule_followup`) is a turn in that assistant chat, using the same rules as phone messages: the main chat, scheduled tasks' own chats, leader conversations and the background supervisor use “Main chat” (leaders and the background supervisor since 2026-11-13: the hub's supervision messages drive them and pick nothing, so a model a failed turn's recovery stepped one down to — Opus to Haiku on a run of 429s — stayed for good); the assistant's other chats retain their running launcher and model (#1518: previously classified as Agents, a follow-up switched the main chat to default Claude Code, which was not logged in on the hub machine; every later message returned `Not logged in`). Task permissions, run history, and session associations remain unchanged. GET for old purposes returns read-only information; PATCH is rejected. Apple's old purpose-editing links open the owning category editor and explicitly explain that changes apply throughout the category. Old hubs without the four-category catalog prompt for an update rather than pretending different effective models are four category defaults.

## Tier candidates are not a silent change

An Agent preset (a model profile's tier) may list several ordered candidates (`docs/assistant/model-profiles.md` "Candidates and aliases"). Choosing a later one at dispatch, by quota headroom or past results, is not a silent model change: the user listed every candidate and ordered them, nothing outside the list is ever chosen, and each dispatch says on the plan card which candidate ran and why (`dispatch.reason`: `score`, `quota`, `unavailable`, `over_pace`, `kept`, `switched`). A tier with one candidate, and every configuration outside presets, still never switches providers on its own.

Model configuration belongs to the **manager** (the assistant process `personad assistant`, `docs/assistant/assistant.md`, “Boundary with hub”). hub neither uses models nor stores model configuration:

- The manager owns: the four category records `model_config.*`, providers added in Persona and their sealed keys (settings `launchers.managed`), hidden ~/.zshrc launchers (`launchers.hidden`),
  each computer's last reported ~/.zshrc launchers (`launchers.zshrc`; offline computers still show their last report), presets, and rate-limit pauses. Code lives in `server/internal/assistant/models*.go`. Keys and tables are unchanged; no data migration.
- Routes: CRUD for `/api/v1/model-config…`, `/api/v1/launchers`, and `…/check`, `…/restore`, `/api/v1/launchers/presets`, `…/quota`, `…/test`, `…/discover`, `…/import`, plus the new-Agent picker
  `GET /api/v1/machines/{mid}/launchers…`, belong to the manager (`assistantwire.Routes`). hub forwards them unchanged: paths, fields, and errors stay the same; no app changes needed.
- Every model consumer calls the manager's own configuration directly: triage, assessment, drafting, translation, knowledge, titles, Agent label names and triage, new Agents (`applyModel`), and Agents opened from Lark cards.
- The manager names Persona-added launchers to the computers in each one's device scope (after changes, when it connects, or when a node connection is new, `launchers.catalog`; `launchers.managed` for old nodes), and a node fetches a provider's key when it needs it (`launchers.pull`, `docs/integrations/launchers.md` "Device scope and on-demand delivery"). Keys pass through the manager's connection to the node; hub neither stores nor decrypts them. A launcher purpose bound to a computer (the main chat's) cannot pick a provider out of that computer's scope, and its status says why when one picked before the scope changed is still set.
- The legacy baseline is the manager's own: `ai`, `kb.ai`, `inbox.triage_ai` / `judge_ai` and `inbox.agent.machine` come from its `manager.json` (`docs/operations/config.md` ("manager.json")). hub supplies only the facts it knows: each computer's `machines[].launchers` from hub.json
  arrive with the handshake (`models.launchers` in `manager.hello`'s answer, `manager.updated` on changes). Inheritance rules remain unchanged. The manager queries plugin provider presets, voice-plugin models, and which enabled plugins need “Information screening”
  through `app.call plugins.presets` / `plugins.voice` / `plugins.quota` / `plugins.need_triage` (these three are removed after the plugin system moves into the manager).
  `api_key_file` is a path read by the manager on its own machine: the default child process runs on the same computer as hub, as the same user, so it can still read it.
- The manager answers the two questions hub plugins need: whether “Information screening” is currently callable (`models.usable`, governing whether dependent plugins can be enabled), and requests that quota plugins or plugin launcher panels need to send with a key
  (`models.launcher_http`: the manager sends with keys for Persona-added providers; for ~/.zshrc providers, the computer's node sends, and the key never leaves that computer). The quota route `…/launchers/{name}/quota` and its one-minute cache also belong to the manager: it selects the gateway and machine, asks hub's quota plugin to read (`app.call plugins.quota`), and requests the plugin needs to send return to the manager through `models.launcher_http`.

**Key encryption**: `server/internal/secretkey`. The built-in manager uses its own `secret.key` (`~/.persona/managers/assistant/secret.key`, copied once from `~/.persona/secret.key`, the file the hub sealed the keys with before they were the manager's, so existing keys remain decryptable; [managers.md](managers.md) ("The built-in manager's own files"))
to seal and decrypt provider keys. It creates the file if missing (even if both processes create it simultaneously, only one writes successfully). hub's own secrets (Lark bots, connectors, plugins, linked-hub credentials) still use the same file and package, but hub does not touch provider keys.
If the manager runs elsewhere (`assistant.external`), copy the hub machine's `~/.persona/managers/assistant/secret.key` to the same place on that computer (0600) before the manager first starts there: once it has started it has a key of its own, which a copy put in `~/.persona` afterwards does not replace. Otherwise old keys cannot be decrypted; status says “Provider key decryption failed,” and the user can re-enter the key in Settings › Model Providers.

**When the manager is unavailable** (restarting, or the `assistant.external` computer disconnects): the routes above return `503 assistant_offline` and resume normally when it returns. Configuration lives in Postgres and survives both hub and manager restarts.
Quota returns `503 assistant_offline`; plugins needing “Information screening” cannot be enabled (same error), and such plugins configured in the manager's manager.json do not receive items yet. Model-powered features already live in the manager and stop with it.

## How the main chat runs (#9799)

Every assistant conversation on a Claude Code launcher runs on Claude Code's CLI (`claude -p` with stream-json,
`docs/integrations/claude-integration.md` "Headless assistant (Chat tab)"): the main chat, side chats, scheduled tasks, guest
conversations and meeting rooms. How it runs is not a setting. A hub before #9799 could also run the main chat on the
Agent SDK; what older data, clients and nodes get:

- **Stored bindings**: a binding an older hub saved with `runtime` (`"agentsdk"` or `"cli"`), in `model_config` or a
  model profile, reads as the CLI without an error. The key is ignored on read and is gone after the next save.
- **Older clients' saves**: `runtime` in a `PUT` / `PATCH` body, on any purpose and with any value (`null` included), is
  accepted and ignored: the save succeeds and stores no runtime.
- **What clients read**: the `assistant` purpose has no `runtimes`, and no purpose lists `runtime` in `fields`. The
  clients show a runtime picker only when `runtimes` is present, so it is hidden here and kept for an older hub that still
  sends it (one device, several hubs).
- **What the node gets**: the manager never puts `runtime` in the params of `assistant.send` / `assistant.warm` and
  deletes one a caller left there (`finishModel`, `sendParamsOwn`), so `model_fingerprint` does not depend on it and an
  older node starts the CLI. A conversation an older node ran on the Agent SDK continues on the CLI with `--resume`, keeping its
  id and history (`docs/protocol/rolling-upgrade-compatibility.md`, "Assistant conversations on the CLI only (#9799)").

For an ordinary assistant chat that retains its running model, the next turn uses the model ID recorded when the node started its process, not the name echoed by the gateway in the transcript. A gateway may rewrite that display name without changing the requested model. An explicit launcher default stays the default. Older nodes without this metadata retain the previous transcript-based behavior. If the recorded model really disappears from a readable launcher list, the existing localized launcher notice explains that the message uses its default model. Conversation picks and chats that follow Model Settings keep their existing precedence.

A binding without a model means the launcher's default, on a resume too (#2487). Claude Code resumes a session on the model it last ran on unless `--model` or a model variable (`ANTHROPIC_MODEL`, `ANTHROPIC_DEFAULT_*_MODEL`) names one; a `model` in its settings does not. So when node resumes a conversation the hub resolved with no model, it passes what a new session of that launcher would use: the `model` from Claude Code's settings, else `default`. It passes nothing when the launcher names a model itself or when its start cannot be seen (a managed launcher, a wrapper script); see `node/assistant_resume_model.go`.

## Recovering an unavailable Assistant launcher (#11491)

A resolved launcher missing from one discovery snapshot does not immediately change the conversation to another account. The manager waits up to 30 seconds by default, asking for fresh `launchers.list` discovery immediately and then polling rather than accepting the node's ordinary one-minute cache. The whole wait is bounded (at most 120 seconds when configured), includes discovery time and ends on request cancellation. A failed refresh, or a forced response containing only managed/built-in entries, is not evidence that the requested shell launcher recovered and does not release the message early. Node output without discovery's begin marker does not publish a Claude-only catalog or replace the previous cache. An ordinary picker read may retain that last good list, and independently usable runtime or app overlays remain available if its shell read fails; a forced recovery read returns the error instead, and its overlays preserve that error. The last fresh result and its catalog are reused at the deadline—there is no additional discovery outside the budget—so a launcher found by the final in-budget read runs with the original model. Receipt and Processing feedback start before this wait, as before.

Advanced per-machine `machines[].launcher_recovery` in `hub.json` configures the wait and, independently, the only permitted substitutes (`docs/operations/config.md`, "hub runtime config (hub.json)"). `fallbacks` maps the resolved launcher to an ordered list. Candidates must currently run Assistant on that computer, have the same Agent kind and pass the existing health check. When the original launcher has disappeared and neither its managed configuration nor its last successful shell snapshot identifies that kind, no substitute is eligible, including an explicitly listed `claude`: the manager does not guess that an unknown custom launcher was Claude. The built-in `claude` is otherwise eligible only when explicitly listed; it has no priority and is never selected implicitly. A present but Assistant-incompatible launcher skips the discovery wait and uses the same explicit-substitute rule. An inherited task baseline on another computer first gives its original launcher the same bounded fresh recovery, then follows that same allowlist instead of choosing an arbitrary available local launcher. With no usable configured substitute, the send fails with the original launcher's explanatory refusal. Approved substitutions keep the existing model-preservation and localized `launcher_note` behavior.

The policy is deliberately an advanced machine configuration for people operating Agent launchers, not another everyday model or account choice in Assistant. Removing the recovery section does not restore the old implicit-default behavior; a full rollback restores the previous hub, manager and node binaries together.

## Main chat's profile for new conversations (#4633)

“Main Chat” adds “New chats' Claude profile”. It decides which Claude config directory a conversation the user starts gets when the start names none (`docs/assistant/assistant.md`, “New conversations”). The choices:

- `private` (the default, stored as none): Persona's own profile, `<PERSONA_HOME>/profiles/<launcher>`.
- `legacy`: this computer's existing Claude Code setup, resolved once per conversation the way an explicit `config_dir: "legacy"` is. That is the setup the node's service environment, a login shell's `CLAUDE_CONFIG_DIR`, a launcher's own profile or the machine's `claude_start_dir` names, else `~/.claude`.

It is the Settings side of #4633's decision: reusing an existing profile means choosing it, and nothing is copied between profiles. A machine whose only sign-in is a gateway and token in `~/.claude/settings.json`'s `env`, or an OAuth login in `~/.claude`, picks `legacy` here, and its new main chats start signed in.

- **Where it applies**: only `assistant` offers it, as `config_dirs: ["private", "legacy"]` with `config_dir` in its `fields`. Agents, API purposes and a task's own purpose do not accept it, and PATCH returns 400 `err_config_dir_assistant_only`. A value other than `private` / `legacy` returns 400 `err_config_dir_invalid`. The main chat's other uses inherit it through the binding; a provider change keeps it.
- **What reads it**: `startOn` (`withNewConversationProfile`) puts it in `assistant.send` when the start names no `config_dir`, is not a guest's, and runs on Claude Code. It is read from the main chat whatever purpose the conversation starts under, so one an extension opens for the user under its own purpose (Lark `/agent`'s `lark.agent`, which inherits from Agents) starts there too, rather than in Persona's own profile, which may not be signed in (#10859). The Inbox AI twin (`inbox.agent`) is left out on purpose: it acts on what other people sent, so it stays in Persona's own profile, where the user's allow rules, hooks and MCP servers do not reach it. A launcher known to run another agent gets none, the same rule as #6467. The warm spare for the next new conversation (`assistant.warm`) gets it too, also when it is warmed on a pick carried over `/clear`, since a spare is adopted only in the same profile: node compares the profile each Claude start resolves to, Persona's own included, with the spare's, so a spare warmed before the choice changed, either way, or before a start that names `legacy` itself, is left and the conversation starts in its own (`node/assistant_spare.go`).
- **What it leaves alone**: a start that names its own profile (the hub's own conversations' `legacy`, a meeting room's, an API caller's) and existing conversations, which keep the profile they were started in. Messages never carry it, and it is not in `model_fingerprint`, so choosing it restarts no running process. Model profiles leave it alone: a switch and its rollback keep the choice, and a model profile that sets it is refused (`err_config_dir`). One stored holding it anyway is read without it (`readModelProfiles`), so it shows no change it cannot make, can still be switched to and edited, and the next write stores it clean.
- **Older nodes, unknown agents**: one too old to be told a profile (`node_outdated`) gets the start, or the warm-up, again without it, and the conversation starts where it always has. So does a launcher whose agent the hub cannot tell (the machine's launcher list did not come): it is asked for in the profile, and the node, which alone has profiles for Claude Code, refuses it for another agent before starting anything (`profileRefused`, #6884).
- **Clients**: the web edits it in the Main chat editor, for a Claude Code provider only, and shows it under what runs now (`web/e2e/main-chat-profile.mjs`). The Apple and Android editors do not show it yet. They send sparse PATCHes, so they leave a saved choice as it is. Without an editor it is set through `PATCH /api/v1/model-config/purposes/assistant` (`{"revision": <n>, "config_dir": "legacy"}`).

## A conversation's own model (#5033)

The model panel of a Persona chat switches that conversation to another launcher, model or reasoning effort, and the choice stays with the conversation: its next messages run on it, on every device, until the user switches again or goes back to the default (the user's ask on 2026-11-12). Model configuration › Main chat stays the default: a conversation without a pick follows it (the main chat, a scheduled task's own conversation, a leader conversation and the background supervisor) or keeps what it runs (the others), as before.

- **Private-profile launcher switches** (#10453): a Claude conversation whose newest transcript is still in another catalogued managed connection's private assistant profile cannot resume on the selected launcher there. The node refuses before replacing its existing process or delivering input, including a model ID from the previous provider. It does not copy sign-in credentials, move transcripts or silently substitute a model. Choose the previous connection to continue, or start a new conversation with the desired connection and one of its models. The hub's saved pick remains visible and can be changed back. Continuing on the same launcher, legacy shell-launcher profiles, and resuming a transcript already moved to the user's profile retain the existing rules. The guard needs the managed catalog; it does not infer ownership of a removed or unknown connection.
- **Shell launchers' private profiles** (#11694): a conversation whose newest transcript is in another, non-managed launcher's private profile (`<PERSONA_HOME>/profiles/<launcher>`, for example a shell function that sets a gateway and its token in its environment) resumes on a selected launcher that sets no profile of its own only where that launcher is signed in. When `claude auth status`, run as the start runs it, says the launcher is signed out of that profile, the node copies the transcript and its directory (subagents, tool results) into the first profile where it says signed in, Persona's own profile of the launcher, then the user's own setup (`claude_start_dir`, the service's or login shell's `CLAUDE_CONFIG_DIR`, else `~/.claude`), and resumes there. The original copy stays, so picking the previous launcher again resumes the newest copy as any switch does. Signed in where it is, a state Claude Code can't tell, no signed-in profile, or a live process that has the conversation keep the resume where it is. Answers are kept per launcher and profile (10 minutes signed in, otherwise a minute). Code: `server/internal/node/assistant_resume_signin.go`.
- **Which conversations** (#9248): every assistant conversation may have a pick: the main one, a leader, the background supervisor, a scheduled task's and a one-off conversation (#6911 had limited it to the main one so that a pick nobody saw could not lock a leader onto a small model; the pick is now published as `model_pick` on its conversation, so what the apps show is what runs). A conversation that is no assistant conversation (an Agent, an unknown id) is refused (`err_not_assistant`). A pick an older build had stored for a side conversation applies again, and shows. The web draws the picker on all of them. Without a pick it shows what the next message runs on: Model configuration › Main chat for the main conversation, a leader and every conversation a scheduled task started (origin `task`; the hub follows Main chat for all of them, also once the task moved on to a new one, `startedByTask`); the background supervisor's own purpose (`assistant.supervise`, read with `?purpose=assistant.supervise`) for the supervisor, which the hub uses for a message typed to it as for the ones it relays; what it started with for the others. The hub's own messages to a conversation (supervision, notices, another conversation's) run on its pick like typed ones (`relayOnPick`); one the pick can't run is sent on what the conversation ran last and the reason goes to the log. iOS and Android still draw it on the main chat only (not yet changed).
- **Kept on the hub side** (`assistant/model_pick.go`): `PUT /api/v1/assistant/conversations/{id}/model` `{launcher, model?, effort?}` keeps the pick in the manager's settings `assistant.model_picks` (Postgres, by session id with its computer; at most 512, the oldest go first but never the main conversation's; a change is computed under the book's lock and written outside it, so reading the picks never waits on the database); `DELETE` on the same path goes back to the default. Assistant conversations are never deleted (they archive, and `DELETE /api/v1/sessions/{mid}/{sid}` refuses them), so an archived one keeps its pick for when it comes back. Every device sees it as `model_pick` on the conversation (absent: it follows the default), so a client can tell "the default" from "picked for this chat" and offer a reset. Feature `assistant_model_pick`; an older hub keeps nothing, and the apps send the pick with each message there as before. API details: `docs/protocol/protocol.md`, "REST (App → hub)".
- **Picked when the conversation starts**: `POST /api/v1/assistant/conversations` takes `launcher`, `model` and `effort` for the first message, checked like a message's pick (a model ID, typed ones kept; refused for a launcher that sets its own model or takes none, before anything starts), and keeps what was named as the new conversation's pick when it named a launcher or a model (a start under another purpose or a guest conversation keeps none). An effort alone keeps nothing: iOS sends its last effort with every start, and that must not tie a new conversation, a new main one least of all, to the default launcher of that moment. A launcher that isn't on the computer follows the bounded recovery rule above: it can run again after fresh discovery, use an explicitly configured substitute, or fail; it never silently falls back to built-in `claude`, and no pick is kept when the start fails. An older app that sends only `launcher` now gets that launcher kept for the conversation too. The apps name nothing when nothing was picked: the web's new-conversation panel and, since #11472, the iOS starter's model menu (a model picked under a launcher goes as `launcher` + `model`, its Default entry as `launcher` alone).
- **Applied to every message that picks nothing** (`sendModel`, `sendOnPick`, `applyPick`): the pick's launcher, model and effort, checked and fingerprinted like a message's pick (`applyPickedModel`); an effort sent with the message wins over the pick's. A pick without a model runs what its start ran: Model configuration › Main chat's model when the launcher is the one configured there (and that model's later changes), else the launcher's own default (`applyModel`). An effort the apps set later through `POST …/modes` (#2416) becomes the pick's effort (the manager sees the hub's `session.modes` call go through, `nodeCallDone`), so the next message doesn't put the old one back. A launcher or model sent with the message (an older app) still wins for that message, as before. A scheduled task's follow-up into the conversation and a rich view's message run on the pick too, and `POST /api/v1/assistant/warm` with no launcher warms the main conversation's pick, on the main conversation's machine.
- **Clearing and new main chats**: `/clear` ("Clear context", #5095) starts the main conversation over under a new session id; its pick goes with it (`mainHandoff.pick`, kept when `/clear` comes again before a new main conversation started): the next main conversation starts on it and keeps it, unless that start names its own launcher or model. That start is held to what a message on the pick is held to: a pick that can't run there any more refuses it once with the same codes (409 `launcher_out_of_scope` / `launcher_own_service` / `launcher_missing`, 400 when the launcher can't run assistant chats or its model can't reach the agent) and is dropped, so the next start runs on the default; it never falls back silently. The start's own effort (iOS sends its last one with every start) is the first message's only; the pick keeps its own. `POST /api/v1/assistant/warm` with no launcher warms the carried pick until then. "New main chat" (`POST /api/v1/assistant/main/new`) is a fresh start: the new main conversation follows Model configuration › Main chat, the old one keeps its pick in the archive, and after `/clear` it drops the carried pick.
- **An existing main chat on the other agent kind** (#4662, web): changing Model configuration › Main chat does not migrate its transcript. With no conversation pick, the launcher list loaded, both the configured and actual launchers known, and their agent kinds different, the main chat's model pill and setup name the session's actual launcher, model and effort rather than presenting the new default as already running. A notice above the composer explains that a new main chat uses the configured launcher and opens the existing **New main chat…** dialog; the Main chat editor shows the same explanation and updates it as the provider draft changes. Another launcher of the same kind, an unloaded list, an unknown default and a conversation's own pick keep their existing behavior and show no mismatch notice.
- **Limits**: picks are this manager's, for its own conversations on its own computers; a conversation on a computer another manager carries keeps none here. A start keeps its pick right after its first message was handed to the computer, so a second message sent in that moment runs as if there were none.
- **Never replaced**: when the default's launcher can't run here, the hub follows the bounded recovery and explicit-substitute rule above (`finishMainChatModel`). A pick is the user's choice, so a message on one that can't run any more is refused with why, and the pick stays until the user changes it: a provider out of the computer's device scope or skipping a computer with its own sign-in (409 `launcher_out_of_scope` / `launcher_own_service`, the scope's words), a launcher gone from the computer (409 `launcher_missing`, worded by the hub with the "connect a model" action), or one that can't run assistant chats (400). A launcher of the other agent kind than the conversation's (Claude Code can't resume a Codex thread, nor Codex a Claude transcript) is refused with 409 `launcher_other_kind`, as a message's own pick is (`launcher_kind.go`). The PUT refuses the same before keeping anything. With the computer's launcher list unreadable nothing is refused on a guess (`mainChatFit`).
- **What a pick can be**: a launcher the computer's main-chat picker lists (`GET /api/v1/machines/{mid}/launchers?purpose=assistant`: its rc-file aliases and PATH wrappers, plain `claude`, and the Model providers that can run the main chat, launchers and Messages-protocol direct APIs, within the computer's device scope); a model that is a model ID (`proto.ValidModelID`), refused for a launcher that sets its own (`locked`) or whose agent takes none, and kept when the launcher's list lacks it (a typed one, "Typing a model ID"); an effort that is `auto`, one of Claude Code's levels or one of Codex's.
- **What can't, and why**: `?purpose=assistant` also answers `unavailable`, so the panel shows these disabled with the reason rather than hiding them: the computer's launchers that can't run assistant chats (`not_main_chat`: a Paseo provider, a runtime without the assistant capability), then the Model providers that can't run here: Responses / Chat Completions direct APIs (`api_protocol`), an agent that can't (`not_main_chat`), out of the computer's device scope (`launcher_out_of_scope`) or skipping it for its own sign-in (`launcher_own_service`). Reasons come in the request's language; hidden launchers stay out entirely. A launcher that an assistant runtime on the same computer declares it runs the assistant for (`assistant_for`, [runtimes.md](../integrations/runtimes.md) "Assistant") also has `instead`, that runtime's launcher, and its reason names it ("For assistant chats, choose Grok"); a pick or a message on it is refused with the same pointer. Only that declaration counts, never a likeness of names or agents, and nothing ever runs on one in the other's place: the user chooses it.
- **Typed IDs**: the hub remembers a typed model (`models.used`, "Typing a model ID") when a message carried it. A pick's model is not sent with the messages, so a typed model kept only as a pick is not offered again under "Typed before" until a message carries it.

## Importing providers from shell aliases (#2455, #5024)

`GET /api/v1/launchers/import?machine=` previews; `POST` confirms (see `docs/protocol/protocol.md`, “Model providers and per-purpose configuration” for the API). The manager calls that machine's node `launchers.zshrc` (`assistant/models_import.go`), which reads `~/.zshrc` (`$ZDOTDIR` first), `~/.bashrc` and `~/.bash_aliases` in the login shell's order (zsh: `~/.zshrc`, `~/.bashrc`, `~/.bash_aliases`; bash: `~/.bashrc`, `~/.bash_aliases`, `~/.zshrc`). Each alias says which file it came from; a name defined in two files is read from the first of them in that order (inside one file the last definition counts, as in the shell). The manager then merges them with the pure function `mergeZshrcAliases` (same file):

- One `ANTHROPIC_BASE_URL + key` group (`ANTHROPIC_AUTH_TOKEN` first, using bearer; otherwise `ANTHROPIC_API_KEY`) is one provider. Name and other settings come from the first alias; every alias's `ANTHROPIC_MODEL` is merged into `models`. Entries without a gateway address (ordinary Claude Code) are skipped.
- **Aliases that differ.** A group of two or more aliases also carries `variants` (each alias as a provider of its own: its name, settings, its model) and `differs`, what the aliases set differently apart from the model (`tiers`, `effort`, `args`, `limits`, `proxy`, `headers`, `env`, `auth`, `custom_model`; `importSettings`). `POST` with `split` imports such a group as its variants; without it the group is merged and only the first alias's settings are kept. A merged provider stands in for every alias of the group, so when the user picks “One provider” for aliases that differ (the dialog says the others keep only their model), the others are checked and hidden like the first. A variant lands in a stored provider only when that provider has the same `base_url + key` and was imported from the same alias (`source` `zshrc:<alias>@<any computer>`); a merged group lands in any stored provider with the same `base_url + key` (`existing`), which gets only the new models; its other settings in Persona take precedence.
- Model names ending in `[1m]` lose the suffix and record a context window of 1000000 (node adds the suffix back at startup according to the window). `ANTHROPIC_CUSTOM_MODEL_OPTION`, `_NAME` and `_DESCRIPTION` fill the provider's custom model fields.
- **Environment** (`models_import_env.go`). Variables with a field fill it and never go into `env`: the base URL, key and token, `ANTHROPIC_CUSTOM_HEADERS`, the model and tier models, `CLAUDE_CODE_SUBAGENT_MODEL_FORCE`, `CLAUDE_CODE_EFFORT_LEVEL`, `CLAUDE_CODE_AUTO_COMPACT_WINDOW`, `CLAUDE_CODE_MAX_CONTEXT_TOKENS`, `API_TIMEOUT_MS`, the custom model option and every spelling of `HTTP_PROXY` / `HTTPS_PROXY` / `NO_PROXY` (`proxy` is the first of `HTTPS_PROXY`, `https_proxy`, `HTTP_PROXY`, `http_proxy` that is set; `no_proxy` is `NO_PROXY`, else `no_proxy`). The others go into the new provider's sealed `env` as `NAME=value` lines sorted by name, quoted with `"…"` when the value has a blank, `#` or a quote and with `'…'` when it has a `"`, so the node's `envLine` reads back exactly the value. Left out, each named in the preview's `skipped_env` with its reason:
  - `credential`: a name with an underscore-separated word (any case) KEY, KEYS, APIKEY, TOKEN, SECRET, SECRETS, PASSWORD, PASSWD, CREDENTIAL, CREDENTIALS, COOKIE or COOKIES (`CLAUDE_CODE_MAX_OUTPUT_TOKENS` is kept), or a value with a user in it: its authority (after an optional `scheme://` or a leading `//`, up to the first `/`, `?` or `#`) has an `@`, or it does not parse as a URL and has an `@` anywhere. That catches what Go's URL parser refuses but Claude Code takes (`http://user:Ab^9{x@proxy.example:8080`), `user:pass@host:8080` without a scheme and `//user:pass@host`; an e-mail address is left out too, on the safe side. A proxy with a user, in any of the four spellings, is left out this way and leaves `proxy` empty: the proxy is stored and shown in the clear.
  - `shell`: a value with `$` or a backquote, or starting with `~` (Persona stores text, not what the shell would expand), or one no env line holds (a line break, NUL, both kinds of quote).
  - `computer`: `PATH`, `HOME`, `PWD`, `OLDPWD`, `SHELL`, `USER`, `LOGNAME`, `TMPDIR`, `CLAUDE_CONFIG_DIR`: the provider runs on every computer in its scope.
  - `limit`: beyond the 50 lines an env takes (`checkEnv`).
- Preview includes neither keys, request headers nor env values, only `has_key` / `has_headers` / `has_env` and the names (`env_names`, `skipped_env`). On confirmation, the manager rereads them; keys, request headers and env pass only through the manager and are encrypted at rest like manually added entries.
- A created provider is named after its alias (a group: its first alias), but never with a name Persona already lists: the alias itself (listed from the rc file), a launcher of another computer or a stored provider; it gets `-2`, `-3`… The preview's `create_as` says that name. One rule names both (`importNames`): groups in the preview's order, a group and its variants each against what earlier groups may take (merged or split is the user's choice), and every name a group may take taken for the groups after it. `POST` works the names out again under the configuration lock and saves under them, so they differ from the preview only when something changed in between; `name` stays the group's identifier for `POST`.
- A created provider is `own_service: use`: the alias makes its computer count as having a Claude service of its own, so `skip` would keep the provider off the computer it came from. Its share and delivery are a new provider's defaults (every computer, on demand).
- **Hiding the imported aliases** (`models_import_hide.go`). After an import the alias and the provider made of it would both be listed, so `POST` with `hide_aliases` adds each imported alias whose check is `ok` to `launchers.hidden` (Settings › Model providers › Hidden restores it; the shell files are never touched). The preview's `sources[].hide` and the import ask the same question, `aliasHide`, against the provider the alias lands in (created, a variant's, or `existing`); the import asks again under the configuration lock, against the provider list it is about to save, and changes no purpose, task, profile or Agent preset. The preview reads what the check needs only when Persona lists one of the aliases, and never fails over it: when the tasks, profiles or model records cannot be read, every alias is `none` (logged). The import with `hide_aliases` refuses instead, writing nothing. It reads `launchers.hidden` again under the lock and writes it with the providers in one transaction (hiding and restoring an rc-file launcher take the same lock); with a store that writes one setting at a time, the providers go first and a failed hide answers 500 saying they were imported but the aliases were not hidden:
  - `none`: Persona does not list that name (no computer's rc-file list has it the way Settings › Model providers lists one), it is already hidden, or it is `claude` / a reserved name.
  - `in_use` (stays, `uses` says what in words): a current purpose names it (`providerModelUses`, extensions' purposes included), a scheduled task's own record does, a saved model profile's purposes do (in use or not), or a profile's Agent preset runs on it. Hiding it would move a start to another launcher (#4661).
  - `elsewhere` (stays, `elsewhere` names the computers): a computer that lists the alias would not get the provider in its place with the same account: out of the provider's scope (`scopeReason`, a work computer for a new provider); every computer when the provider is `own_service: skip` (the alias stays in the file, so the computer keeps counting as having its own service); a computer for which the provider has a key of its own (`machine_keys`) other than the alias's key; or another computer whose own alias of that name does not reach the same base URL (after `proto.MessagesBaseURL`) with the same key (`ANTHROPIC_AUTH_TOKEN` without `Bearer `, else `ANTHROPIC_API_KEY`). The manager asks each such computer's node for its aliases (`launchers.zshrc`, once a request, at most 5 seconds) only for an alias nothing uses; the import asks before it takes the configuration lock, and its check under the lock reads only those answers (a computer not asked then counts as `elsewhere`); offline, a node too old to answer, an error, no alias of that name there (a shell function, say) or another address or key all count as `elsewhere`. The keys are compared in the manager and never logged or returned.
  - `ok` otherwise.
- A body without `split` and `hide_aliases` (iOS, Android, older web clients) merges every group and hides nothing; the env passthrough and `own_service: use` apply to every import.
- **One alias** (#5193, feature `launcher_import_parse`): `GET …/import?machine=&alias=` and `POST` with `alias` read only that alias of the computer, so the groups are that alias's alone; an alias the computer does not have previews nothing. “Found on your computers” on the web and iPhone opens the import this way.

The assistant exposes the same engine as the managed MCP tool `launcher_import` (`assistant/launcher_import_tool.go`). `{action:"preview", machine, names?}` is read-only; a preview provider name selects its whole group, while a raw alias or variant name selects that alias, and omitting `names` previews all groups. Its explicit response DTO contains only `name`, `aliases`, `base_url`, `models`, `has_key`, `has_headers`, `has_env`, `env_names`, `existing`, `create_as`, `differs` and `variants`. `{action:"commit", machine, names, split?, hide_originals?}` requires a nonempty selection and produces one ordinary owner-confirmation card. Approval recomputes discovery, grouping, landing and collision names; a different proposal is stale and writes nothing. The approved operation uses the existing `importLaunchers` sealing, model merge and hiding path, then returns only created/updated/hidden names and safe stored-provider readback (`id`, `name`, `base_url`, `models` and credential-presence booleans). The strict JSON decoder rejects every unknown field, including `api_key`, `headers`, `env` and `base_url`; neither preview nor commit accepts connection overrides. Model-facing errors use fixed redacted messages rather than node/store error text. Restricted Inbox conversations cannot call this tool.

## Starting a provider from a pasted configuration (#5193)

`POST /api/v1/launchers/import/parse` `{text}` reads what a user already has into drafts for the web and iPhone wizards (API in `docs/protocol/protocol.md`, “Model providers and per-purpose configuration”). It is read-only: it reads no computer, saves nothing and keeps nothing; the wizard is filled with a draft and the user saves it as any provider. The readers are pure functions in the manager (`assistant/models_import_formats.go`), so import links call the same ones on their decoded payload. What it reads (`format`):

- **`shell`**: `alias x='K=V … claude …'` lines (the node's alias rules, shared through `internal/shellcmd`), a bare `K=V … claude …` command, `export K=V` lines and plain `K=V` lines (`.env`). Exported and plain assignments collect an environment in order; each claude command makes a draft from it plus its own variables (its own win), and with no claude command the assignments alone make one. Aliases group as the alias import does (one draft per Base URL and key, models combined), except that aliases differing in more than the model are drafts of their own. Comments and blank lines are skipped.
- **`settings`**: Claude Code's `settings.json`: its `env` (string values), and `model` as `ANTHROPIC_MODEL` when `env` has none. Without a key in `env`, an `apiKeyHelper` (it runs a command for the key) is named (`key_helper`, in place of `no_key`) and the key is typed.
- **`curl`**: one request to the gateway. `…/v1/messages` (or `…/messages`) is a Claude Code gateway on what comes before it; `…/chat/completions` and `…/responses` are a direct API (`chat`, `responses`) on what comes before them, its `/v1` (or `/v1beta/openai`, or no version at all) kept; `…/v1/models` a gateway on what comes before `/v1`; any other path is used whole and named (`curl_path`). `x-api-key` gives an `api_key` key, `Authorization: Bearer` a `bearer` one; the JSON body's `model` is the model; `-x` / `--proxy` (without a user) and `--noproxy` fill the proxy fields. Options that only shape this one request (`-X`, `-s`, `-i`, `-L`…) are ignored; any other is named (`curl_option`).
- **`cindy`**: a provider in the cindy v1 import format (`kind: custom`, one object or `{providers:[…]}`, at most 50): its Anthropic Messages endpoint as a Claude Code gateway, else its first OpenAI Responses or Chat Completions endpoint as a direct API; every other endpoint is named (`cindy_endpoint`). The endpoint's key, else the provider's; `name` as the display name; no sign-in method for a Messages endpoint (v1 does not name the header; the wizard's check finds it, #5329, #5420); models from the endpoint, else the provider, with their context window and thinking levels (only levels Persona knows). `preset` and `builtin` kinds name catalog entries of another app (`cindy_kind`); `oauth` sign-in is not supported and `none` leaves the key to type (`cindy_auth`); an endpoint's own `requestPath` is named (`cindy_request_path`): Persona calls the usual path.
- **`link`** (#5420, feature `launcher_import_link`): a provider import link, cindy's `cindy://provider/import?v=1&data=…` or the web's `…#import=…`. It is checked as strictly as cindy checks one (`docs/integrations/launchers.md`, “Import links”): a refused link gives one note (`link_invalid`, `link_version`, `link_too_long`, `link_field`) and no draft; one that passes is read as `cindy` (a batch `{providers}` is refused: links carry one provider).

What a draft carries and leaves out:

- The provider's fields as the alias import maps them (“Importing providers from shell aliases” above: the key, tiers, `[1m]`, limits, proxy, custom model, `env` with its `credential` / `shell` / `computer` / `limit` skips), and for an alias a suggested startup ID named the way the import names one (the alias, `-2` while taken). Unlike the alias import, the draft goes back to the client, so it carries the key the user pasted and nothing else that may be a secret. On top of the import's rules it leaves out:
  - **Variables** whose name holds a secret's word (any case, `_` aside: `KEY`, `TOKEN` but not a word `TOKENS` (`CLAUDE_CODE_MAX_OUTPUT_TOKENS` stays), `AUTH`, `SECRET`, `PASS`, `COOKIE`, `SESSION`, `BEARER`, `CREDENTIAL`, `JWT`, `SIGNATURE`), has a word `PAT` or `PWD` or ends in `_HEADERS` (`GITHUB_PAT`, `OPENAIKEY`, `SESSIONID`, `OTEL_EXPORTER_OTLP_HEADERS`), or whose value looks like a secret (it holds `Bearer `, any case, or starts like a common service's key: `sk-`, `ghp_`, `gho_`, `ghs_`, `github_pat_`, `xox`, `AKIA`, `AIza`, `glpat-`), and a proxy with a query or fragment: named in `skipped_env` (`credential`).
  - **Headers** (`skipped_headers`): a name holding one of those words, however written (`XApiKey`, `X-AccessToken`, `Authorisation`), or with a word `PWD`, `HMAC`, `SIG`, `SIGNATURE`, `OTP`, `SID`, `ACCESS` or `API` (words split at `-`, `_`, `.`, blanks and camelCase), or a value that looks like a secret as above (`credential`); a request's own protocol headers (`protocol`: `anthropic-version`, `content-type`…); a value with a control character, a backslash or a `$` (`unsafe`: a line break would start another header); any header on a direct API, which takes none, nor a proxy (`unsupported`; a `curl` proxy there is named as an option). A name that is no plain token (`[A-Za-z0-9_-]`, up to 64) may be a value run into it: it is not named at all (`header_unreadable`).
  - **Arguments**, all of them (`args_left_out`), when an option is named for a secret, by its words (`KEY`, `APIKEY`, `TOKEN`, `AUTH`, `SECRET`, `PASSWORD`, `PASS`, `PASSWD`, `PWD`, `COOKIE`, `BEARER`, `CREDENTIAL`, `CREDENTIALS`, `JWT`: `--api-key …`, `--apiKey …`), since its value may be the secret; or when a value (an argument, or an option's after its `=`) holds a `{` or an `=` (`--settings '{…}'`) or looks like a secret. `--permission-mode bypassPermissions`, `--fork-session` and `--allowedTools "Bash(git:*)"` stay.
  - **A key** with a blank or a control character in it (`no_key`).
  - **The draft itself** when its address carries a user name or password (`url_user`) or a query or fragment (`url_query`; a `curl` request URL loses its query instead).
- `matches`: every stored provider calling the draft's API on the same Base URL (as stored: a Messages URL without its trailing `/v1`), with `same_key` when its key is the pasted one. A Messages draft meets Claude Code and omp providers and direct Messages APIs; a Responses or Chat draft only a direct API of that protocol, never a Codex provider (its models are what Codex is offered). Keys are compared in the manager, and only those providers' keys are opened, only for a draft with a key; a key that is a provider extension's reference never matches. The web and iPhone offer adding the draft's models to a provider with the same key, or replacing only the key of one with another key, through that provider's edit wizard.
- `notes`, top-level and per draft: everything the reader did not use, as a code with a line number or a name and never a value (`unrecognized`, `invalid_json`, `line_unused`, `not_claude`, `no_gateway`, `url_shell`, `url_user`, `url_query`, `key_shell`, `no_key`, `key_helper`, `args_left_out`, `header_unreadable`, `curl_option`, `curl_path`, `cindy_kind`, `cindy_auth`, `cindy_endpoint`, `cindy_request_path`, `link_invalid`, `link_version`, `link_too_long`, `link_field`, `too_many`). A key or address the shell would expand (`$KEY`) is left out: Persona stores text. A `curl` option is named without its value (`--user=…` as `--user`); a cindy kind, protocol or sign-in method only when cindy defines it.

On iPhone, **Settings → Model Providers → Add** offers **Paste a configuration** and, when the list contains an unimported gateway alias, **Found on your computers**. Both require the hub’s `launcher_import_parse` feature. Picking an alias previews just that alias on its displayed computer. The owner confirms the import in the preview. Pasted configurations open an editable draft, and changing or canceling that draft leaves the saved providers alone.

The text is never logged. At most 256 KiB is read, and the answer stays small: at most 50 drafts are returned (`too_many` past them); shell lines are read up to 500 claude aliases and commands and 500 variables, and cindy providers until one past 50 drafts (the rest not read, `too_many`), so every line of an rc file below its aliases still counts (sixty aliases on one gateway that differ only in the model are one draft with sixty models); at most 200 notes in all and 100 `skipped_env` and 100 `skipped_headers` per draft.

## Choosing a model for a new Agent (#794)

After choosing a launcher for a new Agent, select this run's model from the “Model” list. It is the same list shown by `/model` in the terminal when that launcher runs Claude Code / Codex on this computer.

- **Start host**: New Agent requests the catalog for the selected host and keeps separate lists for each host on the same computer. Without an explicit selection, the catalog and the start both use the machine's default host. Changing the host, including by selecting or clearing a workspace, clears Antigravity's selected model, effort, and preset. An explicit Antigravity pick uses the launcher's native effort unless the user picks an effort for this start.
- **Ask the CLI, not configuration files**: settings.json, config.toml, and launcher environment variables contain only defaults and gateway addresses. The CLI combines its own aliases with the gateway's `/models` response; parsing configuration yourself misses variables set by ~/.zshrc launchers and alias mappings. node starts the CLI once using the launcher as-is (`node/launcher_models.go`): Claude Code receives an `initialize` control request in headless streaming-JSON mode; the response's `models` is the `/model` menu (default / opus / sonnet / haiku resolve to actual models under this launcher's settings, plus every gateway model). Codex uses `model/list` from `codex app-server` (paginated, excluding `hidden`). Kill the entire process group once the list arrives; no messages are sent and no model is called. This Claude run uses `disableAllHooks` (merged with the launcher's own `--settings`), so neither Persona nor user hooks mistake it for a session start.
- **In the user's shell**: a shell launcher runs in the shell the node runs every launcher in (`interactiveShell`; `docs/integrations/launchers.md`, "Which shell"). On a Mac that is the account's own bash or zsh as a login shell (`-lic`), so a `claude` that nvm puts on PATH only from `~/.bash_profile`, or Homebrew from `~/.zprofile`, is found as in Terminal; before #16217 the launchd node ran `zsh -ic` and the list failed with `command not found: claude` while sessions, typed into a login tab, started.
- **A managed provider's gateway models, read by the node** (#8417): with `CLAUDE_CODE_ENABLE_GATEWAY_MODEL_DISCOVERY` on, Claude Code adds the gateway's `/v1/models` entries ("From gateway") to `/model`. It keeps them in one file per config directory (`<config dir>/cache/gateway-models.json`) for the base URL it fetched last, and fetches in the background. The `initialize` answer therefore holds the list of whichever provider was asked about before. For a managed Claude Code provider whose discovery is on, the node makes the same request while the CLI starts (`node/launcher_gateway_models.go`): `GET <base>/v1/models?limit=1000` with the launch's credential, `anthropic-version`, custom headers and proxy. The switch, the headers and the proxy are read as Claude Code reads them: the provider's env, then the user's settings env, then the environment. The credential is only the provider's own (its key, or one its env sets): a token from the user's settings or the shell belongs to another gateway, and a launch never sends it there. Anthropic's own API (`*.anthropic.com`) is not asked, as Claude Code does not ask it. The node keeps only the IDs Claude Code keeps (`claude` or `anthropic` in the ID) and adds those the CLI's answer lacks after it, matching by ID or by what an alias resolves to, with or without `[1m]`. Discovery off, no credential of the provider's own (a withheld provider before its pull), a failed request or a non-2xx answer: the CLI's answer stands alone. The models run with the provider's context settings like any picked model (`CLAUDE_CODE_MAX_CONTEXT_TOKENS`).
- **One row per model** (#10365): Claude Code lists each tier alias as a row of its own, and on a gateway provider whose tiers all name one model (Persona fills a tier left empty with the provider's model) they all read the same: such a provider's live list showed `opus`, `fable`, `sonnet` and `haiku` as four "Opus 5.5" rows, and the gateway's entry for another route of that model (`kiro/claude-opus-5-5`) as a fifth. The manager folds the list once, after the provider's and its preset's models are added (`foldModels` in `assistant/models_launchers_fold.go`), so every picker on every client gets it (`purpose=assistant`, New Agent, Model configuration, Lark's `/model`): within one launcher, the rows that run the same model (what an alias resolves to, else the ID) with the same context window become one row, at the first one's place. The window is the one the provider declares for that model (a model over 200K runs as `<id>[1m]` with it, so both spellings count it), else 1M for a `[1m]` name, else Claude Code's own: `x` and `x[1m]` stay two rows unless the provider declares `x` over 200K. The Default row never folds (it sends no model and follows the launcher's configuration), nor `opusplan` (outside plan mode it runs another model), nor an ID typed before. On a Persona-managed provider (a launcher, or a Messages API provider, which is started as Claude Code too) whose effective Base URL (its env's `ANTHROPIC_BASE_URL` over its own) is not Anthropic's API, the row's ID is the concrete model (a member that runs as itself, else what the aliases resolve to), so a pick sends an ID the gateway serves; elsewhere it is the first member's, which Claude Code resolves. Its name is the first member's own name, its efforts and speeds the first member's that lists any. The other spellings are the row's `aliases` and stay the launcher's: a kept pick, a Model configuration model or an Agent preset naming `opus` keeps working (`listsModel`, `launcherModelSet` and the alias map readiness reads), is not remembered as a typed ID, and selects the row in the web. Nothing folds across launchers, routes or windows: `kiro/claude-opus-5-5` may reach another upstream service than `claude-opus-5-5`. Rows of one launcher that still read the same with different IDs get the route before the ID's `/` after the name, "Opus 5.5 (kiro)" (`assistant-models.model_route_name`), and the one without a route keeps the plain name. The node's own list, whose order the assistant's fallback follows, is not folded. Apple and Android match a saved pick by exact row ID first, then against `aliases`, so the existing folded row is selected without a duplicate typed row or a redundant write: Apple in its conversation, starter, running-model and New Agent pickers, Android (which decodes `proto.AgentModel.aliases`) in the Persona, running-Agent and New Agent panels.
- **Cache**: node caches by “launcher + managed-launcher settings” for 10 minutes, sharing one CLI invocation across simultaneous requests. After that, a list up to 24 hours old is still answered at once while the CLI is asked again in the background, so the picker does not wait for it every ten minutes (#1501). `?refresh=1` (pull to refresh or retry after an error in the app) asks again and waits. Measured: about 4 seconds for Claude Code, under 1 second for Codex.
- **Configured model for main and supervisors**: main and leader/background supervisor conversations keep their configured model. A quota reset waits for the existing usage-limit continuation; ordinary 429/service errors use the durable retry scheduler. Their continuation resolves the configured choice again, and a pre-upgrade fallback hold cannot override it. No automatic node model switch is allowed for these conversations. Worker Agent recovery and internal/extension candidate calls are unchanged.
- **Ordered worker fallback**: for the bounded transient recovery in [claude-integration.md](../integrations/claude-integration.md) ("Headless assistant"), this list's order is also the order in which node tries later models after the current model's one same-model retry: the entries after the current model, then from the top; where the launcher declares context windows (Codex's catalog), a model whose window cannot hold the conversation is skipped and those with at least the asked-for model's window come first (#10277). Effort follows the fallback model: an unsupported level resets to the launcher's default, as in the picker. This list is not a new routing configuration and is unrelated to ModelProfile.Tiers' named Agent presets. An unavailable list or a `locked` launcher means no model switch; it never turns `default` into a second request or silently picks a different launcher.
- **Assistant routing**: model discovery with `purpose=assistant` asks the shell launcher or assistant-capable runtime that runs the conversation, even when the Agent engine offers a different provider with the same name. Model IDs, resolved aliases and defaults share the same purpose-specific cache. Assistant follow-ups, fallback validation and readiness checks use this route too. `POST /api/v1/launchers/{name}/check?purpose=assistant` explicitly tests that route; a generic Test without the parameter keeps the Agent engine route. Web catalogs also retain the requesting manager and credential scope; changing assistants cannot reuse another manager's defaults or redirect an in-flight request. Forgetting a shared custom model updates both purpose lists and overlapping reads only within that manager.
- **Launcher defaults**: when an inspectable Claude launcher supplies its own `--settings` model, an unambiguous matching catalog entry is marked as the default for starts without a model override; native aliases and resolutions are preserved. A different command-line or effective environment model leaves the native catalog unchanged. Effort follows the effective environment, then `--effort`, then a supported settings default (`low` through `xhigh`); settings `max` and `auto` are ignored. Without an environment or command-line effort, a nonempty or unreadable `modelSettings` map keeps the native effort because its model matching can take precedence over the top-level setting. Unknown, unreadable, or conflicting inputs keep the native values. The launcher's profile settings env is included, and its explicit `--settings` env takes precedence.
- **Can the selection take effect?** `launcherModelCheck` (`model_probe.go`) also checks whether the launcher forwards `--model` unchanged to the CLI. Launchers hardcoding `--model` return `locked`; the app locks the model row, explains why, and omits the model (node rejects startup if one is sent anyway).
- **This run only**: the selected model travels in `model` on `POST /api/v1/sessions`, overriding “Model Settings › Agents” (`applyModel`). The node adds `--model` when starting Claude Code, Codex or the native omp launcher in herdr or Orca. It does not change global defaults (Claude Code and Codex offer previously typed IDs in the list, see “Typing a model ID”); changing machine or launcher resets to “Default model.” “Default” means no model is sent: use the launcher's own default, or the configured model when the launcher is the one in “Model Settings” (the app's second line says “Model configuration: …”). Choosing the native `omp` launcher and leaving the model blank uses omp's own configured default. Choosing Model Settings or an Agent preset uses the model selected there.
- **Thinking effort follows the model**: each Claude model includes its supported levels (only low…max understood by node are retained). The app lists only these; if the current choice is unsupported, reset to “Follow launcher.” Models without levels cannot select thinking effort (the control is disabled or marked unsupported). With no model selected, use the model that will run: the “Model Settings” model (if its ID is absent from the list, treat support as unknown and list all levels), otherwise the default model. New Codex sessions do not send thinking effort (“When changes take effect” above).
- **Without a list**: an internal Codex fork and runtime launchers (DSH…) return `models: []`; the app hides the model row. Old hubs return 404 and also hide it; if hub is new but this computer's node is old, hub returns 404 too (`code: node_outdated`), avoiding a retry that will always fail. If listing fails (CLI missing, not logged in, timeout), the model row shows the reason and retry, while “Default model” can still start.

## Choosing a model in model configuration (#943)

When a Claude Code / Codex launcher provider is selected in “Model Settings,” “Specific model” also selects from that launcher's `/model` list, using the same list and picker as new-Agent creation (web `ui/ModelPicker.tsx`, Android design-system `JModelSheet`).

- **Which computer is asked**: Model configuration belongs to the manager, not a computer. `GET /api/v1/model-config/providers/{id}/models` chooses an online computer with this launcher and asks node's `launchers.models`: the one specified by `?machine=`, the assistant's computer, the local hub computer, then the others, in that order (`pickMachine` in `assistant/models_launchers_routes.go`). ~/.zshrc launchers exist only on the computer defining them; Persona-managed launchers (`personad launch`) run on every computer in their device scope, and “Claude Code default” on every computer. The response includes `machine`, and the page identifies the source computer.
- **“Default” means empty**: Empty here means inherit. If neither provider nor model was selected, the “Default” row shows the inherited model (the one under “In Effect”); with a selected provider, it shows that provider's default model (the list's default entry).
- **IDs outside the list still work**: The list may be incomplete (new gateway models, different settings on other computers). If the ID entered in search has no exact match, add a “Use ‘…’” row. Already-configured models outside the list still appear, marked “Not in list.” Saving remains separate from paid-availability testing.
- **Tier aliases on a direct call (#9165)**: the `/model` list includes Claude Code's tier aliases (`opus`, `sonnet`, `haiku`, `fable`, `best`, `opusplan`, `[1m]` or not), which a launcher's CLI resolves on its computer. When a purpose runs on a Persona-managed provider as a direct API call instead, `apiConfig` (`assistant/models_tier_alias.go`) sends the model the provider's tier field names (`sonnet_model` for `sonnet`; `opus_model` for `opus`, `best` and `opusplan`; `haiku_model`, else `small_model`, for `haiku`, as on a computer), never the alias itself, which no gateway serves. A provider with no model for that tier (or another alias in it) refuses the call with `assistant-models.err_tier_alias_unresolved`, so the use shows as not usable instead of failing at the gateway. A purpose that runs a launcher's CLI on a computer still passes the alias to the CLI.
- **Without a list**: Plugins use their own lists (as before); API providers have no list. Old hubs, outdated nodes (404), or listing failures fall back to the original text field, with the failure reason and “Retry” below.
- Thinking effort: the web client lists only levels supported by the selected model; Android still uses free-form input.

## Typing a model ID (#1644)

The `/model` list is not every model a launcher can run: a gateway behind a `~/.zshrc` launcher serves its own models while Claude Code lists only its tier aliases, and a new model can be newer than the list. Claude Code's `--model` / `/model` and Codex's `--model` take any string, so New Agent, a running session's model switch and the Persona chat's model chip also take a typed model ID (the apps' entry is the clients' part of #1644; this section is the hub's). A new Agent using the native omp launcher in herdr or Orca also accepts a typed model ID, even when its list is empty. To reuse an omp model across starts, save it in an Agent preset. See [omp](../integrations/omp.md).

- **One rule everywhere**: `proto.ValidModelID` (`server/internal/proto/modelid.go`): a letter or digit first (or `~` and then one), then only letters, digits and `. _ - / : @ [ ]`, at most 256 bytes. That covers aliases (`opus`), variants (`opus[1m]`), a gateway's `vendor/model` and its "latest" aliases (`~vendor/model-latest`, `~vendor/model-latest[1m]`), tags (`qwen3:32b`), dated IDs (`claude-x@20250101`) and ARNs, and keeps out whitespace, control characters, quotes, `$`, backticks, `;`, `|`, `&`, globs and a leading `-`. Checked by the node before anything runs (every start's `modelExecution.check`, the launcher check, the `/model` line typed into a running Claude Code, all answering `invalid model`), by the manager for New Agent's pick and every launcher binding (`applyModel` / `finishModel`), Model configuration's launcher purposes (400), a Persona chat message's pick (`sendModel`, 400), and the assistant's `agent_start` / `task_plan` and a plan card's edit (400) before anything is asked or started. Refusals are said in the App's language: the hub passes the request's language to the manager (`lang` on `agents.start_params` / `assistant.send_params`).
- **Configured before the rule**: a launcher purpose saved with a model that breaks the rule (the old check only refused line breaks, NUL and over 512 bytes) is not passed on: its runs take the launcher's default and the manager logs it, so the main chat, `assistant.warm` and the other purposes keep working. Editing that purpose is refused naming the model until it is cleared or replaced (the node's model check would refuse it anyway).
- **Quoted on every command line anyway**: herdr's start command (`shellQuote`), the resume command herdr runs after a restart (`dquote` inside `eval`), the launcher probe (`shellQuote`), so a leading `~` is never expanded to a home directory; the assistant CLI gets it as a separate argument (`"$@"`), Codex and managed launchers by exec. `node/model_inject_test.go` runs those command lines in a real shell with hostile strings and checks the agent gets exactly one argument after `--model` and nothing else runs.
- **The Persona chat keeps a typed pick**: a model picked with the message is no longer dropped because the launcher's list doesn't have it. Only a model carried over from what the conversation ran is still held to the list (or to the IDs typed for that launcher before), so a model the gateway dropped doesn't fail every later turn; a carried-over value that isn't a model ID (Claude's `<synthetic>`) is not carried.
- **Remembered per computer and launcher, for every device**: once a start (`POST /api/v1/sessions` with `model`), a running session's switch (`POST …/modes` with `model`) or a Persona chat message with a picked model went through, the hub tells the manager (`models.used {machine_id, launcher, model}`, best effort). A start the node answers before it runs (`async`, what the apps' New Agent sends) counts only once the session is listed as started (no longer `starting`, no `start_error`; the hub watches its list for up to 10 minutes, `modelUsedOnceStarted`), since the launcher's model check and the agent coming up happen after the answer; a synchronous start counts when it returns. The manager keeps it in the settings key `launchers.custom_models` (Postgres) unless the launcher's own list has it (an ID or what an alias resolves to) or the launcher takes no typed model (`locked`, or an agent other than Claude Code / Codex); with the list unknown it is kept. Most recent first, at most 8 per computer and launcher, 256 in all. A start that failed, a refused request, or a model the assistant chose itself (`agent_start`, `task_plan`) is not remembered. "Went through" means the agent took the ID, not that the model answered: Claude Code takes any `--model` / `/model` string and only fails on the first API call, so a mistyped ID that started is remembered until the user forgets it (below).
- **Offered in the lists**: `GET /api/v1/machines/{mid}/launchers/{name}/models` (and Model configuration's `…/providers/{id}/models` for the computer it asked) appends them after the CLI's own entries as `custom: true` with a short description and no `efforts` (unknown: the apps offer every level or leave it to the model). A list of a launcher that takes no typed model (another agent's empty list, which tells the apps to hide the model row; a `locked` launcher) gets none. They count for the carried-over check above. Older apps just see more rows.
- **Forget**: `DELETE /api/v1/machines/{mid}/launchers/{name}/models/custom?model=<id>` drops one (idempotent). Forgetting doesn't stop a running session or change any configuration.
- Launchers that hard-code their own `--model` stay `locked`: a typed ID is refused like a listed one. Switching the model of a running Codex session is still not supported.

**In the apps** (iOS / Mac / visionOS and the web; Android later):

- **Same rule, said as it is typed**: `apple/Packages/PersonaWire/Sources/PersonaWire/ModelID.swift` and `web/src/lib/model-id.ts` mirror `proto.ValidModelID` (tested on the server's cases) and name the first thing wrong (empty, how it starts, a space, a control character, the character that isn't allowed, over 256 bytes) under the field; "Use" stays off until the hub would take it. The spaces and line break around a pasted ID are dropped.
- **New Agent**: "Other model…" at the end of the model list (iOS: a sheet with the field, `TypedModelSheet`; web: the field in the list, `ModelIdField`), and the search takes a typed ID too ("Use “…”", or why not). When the list is empty or couldn't be read (Claude Code / Codex only), the row is "Enter model ID…" beside the error and Retry; on iOS a pick typed there has a clear button back to the default. A typed pick stays when the list loads again (it isn't in it) and goes in the start's `model` (`LauncherModelChoice.sent`, web `startPicks`); another computer or launcher still starts over from Default. Its efforts aren't known, so every level is offered. Locked launchers keep the locked row (an empty list too) and send no model.
- **IDs typed before**: listed under the launcher's own models ("Typed before", drawn monospaced as typed; the heading says what they are, so the hub's description isn't repeated on each), with Forget (iOS: swipe or the context menu; web: × beside the row) calling the DELETE route: the row goes at once and comes back, with the hub's reason, when it refuses (`LauncherModelsModel.forget`, web `withoutCustom`; the web popover keeps its pick by ID, so a refused Forget doesn't move it).
- **A running Claude Code session**: "Other model…" in the model menu (the shell composer's, the old layout's thinking chip, BeautifulUI's prompt bar) opens the field with the session launcher's typed IDs; a pick goes through `POST …/modes {model}` (the node's guards), never as a `/model` message (`PromptItems.modelPick`). A session running a model the menu has no alias for (a typed ID) ticks no alias: the menu lists that model by its ID as a row of its own, ticked (`PromptItems.runningModels`), the field starts with it, and Default switches back (`PromptItems.runningModelID`; it used to read as Default and picking Default did nothing). The web popover has the row in its model list: a good ID is staged as it is typed, so its Apply (or Enter) is the one confirm; the list shows what was read last at once and is read again behind it. Codex sessions still have no model switch.
- **The Persona chat's launcher menu**: each Claude Code / Codex launcher's submenu lists its typed IDs after its models and ends with "Other model…" (iOS: the sheet, which also lists and forgets the typed IDs; web: an input row in the menu, plus "Forget a typed model"); the pick is the next messages' model like a listed one. "Other model…" is offered only when the hub lists the `typed_models` feature: an older hub's `sendModel` dropped an unlisted pick without a word while the app said it was in use. A locked launcher says why instead (web; the iOS sheet shows it and keeps Use off).

## When changes take effect

- API purposes resolve configuration at the start of the next call; knowledge uses injectable per-purpose models rather than freezing the old object at hub startup.
- The specific primary model for chats and Agents is passed through CLI arguments or the Codex app-server model field, not just environment variables that a launcher may clear.
- Prewarming / process reuse carries an execution fingerprint, so a launcher with the same name but changed model or credentials does not reuse a stale instance.
- Saving does not kill the current turn or background tasks. If a process switch is needed while still busy, reject the switch and retry at a safe boundary; do not claim lossless Claude/Codex continuation across executors.
- Historical triage is not rerun, and existing knowledge is not rewritten. Translation caches distinguish model configurations so the next translation cannot reuse a cache from the old configuration.
- New Agents default to “Follow model configuration”; a manually chosen launcher overrides only this run. The client's last-selected launcher no longer automatically overrides global configuration. Claude Code and Codex retain their own creation paths; Codex requires a first message, explicitly overrides the model with `--model`, and keeps thinking effort under its own launcher rather than mixing in Claude's permission/thinking arguments.
- Voice models are read only when the next voice session starts/restarts. A legacy hub 404 permits reading old client defaults for compatibility; a read failure on a new hub must not be treated as missing configuration and trigger fallback.
- Model changes neither change permission mode nor authorize automatic message sending.

## Upstream rate limits

Direct-API purposes (knowledge processing, Inbox triage / assessment / drafting, translation, titles) all run in the manager and share the client in `server/internal/ai`. Each connection (address + key, regardless of purpose) has its own gate (`ai/limit.go`):

| Upstream response | Interpreted as | Pause behavior |
| --- | --- | --- |
| HTTP 402, or an explicit budget / quota code such as `budget_exhausted`, `weekly_budget_exhausted`, `api_key_model_limit_exhausted` or `quota_exhausted` | Quota or budget exhausted | Pause for 30 minutes; honor `Retry-After` if present |
| HTTP 429, body mentions quota / usage limit / exhausted, etc. (relay `account_quota_exhausted`) | Quota exhausted | Pause for 30 minutes; honor `Retry-After` if present |
| HTTP 429 with `X-Should-Retry: false` and a positive, valid `Retry-After` | A limit that cannot succeed before its reset | Pause as quota until the requested reset, not busy backoff; do not add a concurrency cap. Zero, malformed or absent `Retry-After` is not this exception: ordinary 429 / 503 / 529 responses keep their existing busy gate |
| HTTP 429 / 503 mentioning concurrency (`account_concurrency_full`), explicit `rpm_limit` / `tpm_limit` / `concurrency_limit`, or other 429, 503, 529 | Concurrency full | Exponential backoff (starting at 5 seconds, doubling on each consecutive occurrence, up to 5 minutes); use `Retry-After` if longer, and add a concurrency cap for this connection |

- **Explicit retry and failure semantics**: `X-Should-Retry: false` makes the original HTTP failure non-transient, but does not disable the gate's upstream protection or a bounded compatibility request with a rejected field changed (`max_tokens` renamed, `stream_options` or `reasoning_effort` removed). Error `code` is read as a string or number from top-level or nested OpenAI- and Anthropic-shaped envelopes, independently of other fields, so a malformed field cannot erase a valid message or type. A recognized code takes priority over message wording, while an unknown code keeps the previous wording-based behavior. `model_not_found` (including a 400 or 404 whose body identifies an unavailable model, or an Anthropic 404 `not_found_error` whose message starts `model:`) and `context_length_exceeded` have separate typed classifications for manager reporting. Overload wording such as `model service unavailable` is not a missing model. These failures never select another model or provider and do not add a same-request retry; refusals and `PausedError` keep their existing behavior.

- **Every call streams**: Messages, Responses and Chat Completions requests all ask for a stream (`"stream": true`), so a gateway's cap on a non-streamed request's total time (often 120 seconds) does not fail an answer a slow model needs longer for (#4245). A Messages server that ignores the flag and answers one JSON message is read as before. A stream that ends before its end event (Messages: `message_stop`, or at least a stop reason; Responses: its terminal event; Chat Completions: the finish reason) was cut: it is a failed connection, retried like one, not a short reply.
- **Limits reported inside a stream**: A Messages `error` event whose type is `overloaded_error` or `rate_limit_error` counts as concurrency full (the HTTP 529 / 429 it stands for; a `rate_limit_error` whose message speaks of quota or credit as quota exhausted). A Responses `response.failed` or `error` event after the 200 whose code is `rate_limit_exceeded`, `slow_down` or `server_is_overloaded` counts as concurrency full, and one whose code is `insufficient_quota`, `credit_balance_exhausted`, `organization_spend_limit_exceeded` or `project_spend_limit_exceeded` as quota exhausted, with the wait in a "try again in ..." of its message (`1.5s`, `250ms`, `20 seconds`, `6m0s`, `1m30s`) used like `Retry-After`. Chat Completions error events use the same explicit-code quota / concurrency mapping and gate behavior. Any other in-stream failure is an ordinary error.
- **No requests during a pause**: Calls immediately receive `ai.PausedError` (`ai.IsPaused`), with the same text displayed in the app: “Quota exhausted; retry in 23 minutes.” Callers treat it as deferred: knowledge-processing loops stop immediately (sessions remain pending compaction, projects pending rewrite, entries untagged); Inbox triage does not mark entries as triaged (new entries go into rule-based groups first and are triaged again after recovery); assessment and translation wait for the next round. None logs it.
- **Only the gate logs**: One line on entry (address, upstream code and message, pause end time, with its day when the pause runs past today), one on exit (pause duration, number of deferred requests). Requests deferred for want of a turn (no slot under the cap, or the probe unanswered when their own deadline came) get a line as well, at most one every 10 minutes: how many were deferred, how many requests are out, the cap, and how long the longest has been out. No request stays out past its caller's deadline (minutes), so a time far beyond that is a slot that was lost, not an upstream at its limit (#6698).
- **Release one request after the pause**: The first request probes recovery; the others wait for its answer (until their own deadline, a background call at most 30 seconds, then deferred) instead of being deferred at once, so a round of Inbox triage right after a pause sorts all its items rather than one (#6698). The gate opens as soon as the upstream answers the probe 200, not when its stream has been read to the end: a long answer no longer keeps everything else deferred while it lasts (the probe still holds its slot under the concurrency cap). Another rejection starts a new pause (without another log) and defers the ones waiting; a limit the probe's stream reports after its 200 holds the connection again with the backoff continued. A probe that fails another way (404, a 5xx no limit stands behind, a dropped connection, its deadline) leaves the gate held, and the next request probes in its place. Matching responses from requests already in flight before the pause do not count and do not compound the backoff.
- **Concurrency cap**: On the first concurrency-full response, set it to half the current in-flight count (at least 1); halve it again on another full response. Then increase by 1 after every 10 successes; stop limiting once it exceeds 8. Requests above the cap queue for a slot until their own deadline; reaching it also counts as deferred. The knowledge base loop's calls are marked background (`ai.Background`): they queue for at most 30 seconds, or until their own deadline if sooner, and are then deferred without being sent, so they give their turn back instead of spending their whole deadline (minutes) in the queue, while a call someone waits for on the same connection keeps waiting (#4246).
- **A turn always goes back**: A request gives back its slot, and as the probe its place, however it ends, a panic that unwinds through it included. The knowledge base loop and its job pool recover from a panic and carry on, so a request left counted as out would keep the cap full, or the probe unanswered, for as long as the process ran: every later request on the connection deferred as busy with nothing sent (#6698).
- **Visible in the app**: In the model-configuration API, purposes whose connection is paused carry `limit` (`reason`: `quota` / `busy`, `until`), and `status` is the text above (apps, web, and Android versions that do not understand `limit` still show it).
  The app displays a warning in purpose rows and details under “Settings › Model Settings” (a `Theme.caution` symbol + `cautionText` text), counting down from `until` while the page is open. Screenshots use mock `MOCK_MODEL_LIMIT=1`.

## Models for each role (#5086)

Persona names no model in code and preselects none (`docs/design/PRINCIPLES.md` 5): every role below is bound by the owner, as a purpose in Model Settings (an empty binding inherits, see "Editing and inheritance") or per task. This table is guidance for those bindings and for the main chat's choice of a task's model; it changes no binding and no default. It follows Anthropic's two guides, [Which Claude model should you build with](https://claude.dev/blog/which-claude-model-should-you-build-with/) and [Choosing the right model](https://platform.claude.com/docs/en/about-claude/models/choosing-a-model), and the reasoning behind each row is in `docs/design/proposals/main-chat-availability.md` section 9. A tier is a step in what a provider offers, from its smallest model to its strongest; the Claude names in brackets are examples of a tier, and with another provider the model of the same tier takes their place. The **daily driver** is the tier the owner has agents use day to day.

| Role | Bound by | What it does | Start with | Move when |
| --- | --- | --- | --- | --- |
| Conversation defaults | `assistant` | Talks with the owner, splits and hands out work, reads outcomes from its snapshot | The daily-driver tier (Opus 5.5) at `medium` | Reply wait on idle days is over its threshold: lower the effort, then try one tier down (Sonnet 5.5) at `low` or `medium`. Plans come out wrong or directions get confused: raise the effort, then the tier |
| Background supervisor | `assistant.supervise` | Reads signals, checks evidence, nudges, reviews | Inherits the main chat, as built (nothing is preselected). Guidance: one tier below the daily driver (Sonnet 5.5) at `medium` | Accepted tasks are reopened, or `needs_user` decisions come back as `undecidable` or `owner_cannot_answer`: raise the effort, then move to the main chat's tier |
| Leader conversation | its conversation's | Supervises one direction over days | The main chat's tier | As the background supervisor; a direction whose tasks are routine can go a tier down |
| Task leader | the task's | Splits one large task, reviews its workers | The top tier (Fable 5.2) at `medium` for a migration or a major refactor; else the worker's tier | Worker rework rounds stay high after the criteria were fixed |
| Worker, well-scoped | the task's (`agent.new`) | A bug fix, a feature against a spec, a read-only investigation | One tier below the daily driver (Sonnet 5.5) at `medium` | A second rework round: raise to `high`, then to the daily-driver tier (Opus 5.5) at `medium` |
| Worker, open-ended | the task's (`agent.new`) | Debugging without a known cause, work across several PRs, computer use | The daily-driver tier (Opus 5.5) at `medium` | Still short at `high`: the top tier (Fable 5.2) at `medium` |
| Independent reviewer | `agents.review` in `manager.json` | Reads a finished change cold and reports findings | The tier of the agent that wrote the change, never below it | Findings miss what the supervisor then catches |
| Triage, routing, done judge, titles, question delegation | The categories `inbox.triage` (Inbox sorting, and with it the read-only `agent.triage`, `inbox.judge`, `info.tag` and `capture.sort`), `kb` (titles, and with it the read-only `assistant.route`), `agent.delegate` | Classify, extract, name, decide who answers | The smallest tier (Haiku 5.5) at its default | A measured error rate that costs more than the tier saves; the delegate first, since a wrong answer there reaches an agent |

- **The main chat's tier is not lowered to make it fast.** What makes it slow is background work in its conversation, which the background supervisor and the owner-first queue remove (`docs/assistant/assistant.md` "Messages from the system wait for the owner", `docs/assistant/unified-entry.md` "Background supervisor"). Only when its reply wait fails on idle days is the model the cause.
- **One model per conversation.** A prompt cache belongs to the model that wrote it, so a changed binding costs a cache write on the whole conversation at its next message. A different model for supervision is free only because the background supervisor is a conversation of its own.
- **Effort before tier.** Each purpose has an effort next to its model; rework rounds and reply wait are answered with effort first.
- **The main chat's rule for a task's model.** The two worker rows and the task-leader row are in the main chat's instructions (`server/internal/prompts/assistant/claude_md.md`) as its rule for `task_plan`: well-scoped work starts one tier below the daily driver at `medium`, open-ended work on the daily-driver tier, a major migration or refactor led by a task leader on the top tier; after a rework round it raises the effort before the tier, and it states the choice in `why`. The instructions name no model. The main chat knows the tiers only from what it is shown: the Agent presets of the model profile in use (the snapshot's model-profile line, each preset with the description the owner gave it; `task_plan`'s `tier`, [model profiles](model-profiles.md)), or what the owner told it. When it cannot tell which model is which tier, or no preset fits, it leaves `tier`, `model` and `effort` all empty, and the task runs on the model and effort the owner set for Agents in Model Settings. It sets `effort` itself only with a preset that carries none, or to raise it after a rework round; a preset's own effort is left alone. The owner's own choice of a model or an effort for a task always wins, and the rule only picks among what the owner configured: it never fills in a model the owner did not give.
- **What this changes for an install with Agent presets.** A preset is the owner's own definition of a tier, and picking one sends its model and effort in place of the Agents binding of Model Settings ([model profiles](model-profiles.md)). Before #5086 the main chat picked a preset only when its description fitted the task; with the rule, a preset whose description says it stands a tier below the daily driver and suits well-scoped work is where every bug fix, feature against a spec and read-only investigation starts, so those tasks no longer run on the Agents binding. The plan says so in each task's `why`, and the owner can change the model on the plan or tell the main chat otherwise. An install with no presets, or with presets that do not say where they stand, runs every task as before.
- **Whether a tier holds on this install is measured, not assumed**: `GET /api/v1/assistant/availability` reports, per model and effort the supervisor ran on, tasks accepted, how many of the settled acceptances were reopened within a day and rework rounds per task, and per day the supervisor conversation's output tokens next to the tasks it accepted (`docs/assistant/assistant.md` "Supervision by model"). The weekly recommended-setup block suggests one tier down for the background supervisor when its reviews held and the provider it runs on has a lower tier that is not its smallest (`docs/assistant/assistant.md` "A lower tier for the background supervisor"); it changes no binding, and nothing suggests a tier up.

What each purpose is for, in one sentence, comes with the purpose from the manager (`description`, see "API"), in English, Simplified Chinese and Japanese (`assistant-models` `desc_<id>`). It is wording only: it names no model and moves no binding.

## API

`purposes` in `GET /api/v1/model-config` returns the five ordered category configurations followed by the editable AI twin (`inbox.agent`) and Lark /agent purposes, the background supervisor (`assistant.supervise`), the In-meeting conversation (`meeting.room`) and Meeting minutes (`meeting.minutes`, #7980) and the extensions' own purposes (`extension.<id>`, see "Extensions' own purposes"), plus `providers`; `GET /api/v1/model-config/purposes/{id}` returns one `purpose` and available `providers`, supporting legacy-purpose queries.

`Purpose` includes `id/name/group/kind`, `description` (#5086: what the purpose is for, one sentence in the request's language; every built-in purpose has one, including `assistant.supervise` and the read-only purposes under a category; a task's own, an extension's and a voice plugin's have none, and a hub before #5086 sends none. Android draws it under the purpose's name since #5802 (`docs/android/android.md`) and the Apple apps do in Model Settings (#5806, `docs/apple/ios.md`); the web shows it under each purpose's name in Settings › Models (#5806), with its own sentence for the background supervisor only on a hub that sends none; the catalog's row for `assistant.supervise` carries it since #5806), `category_id`, `override`, `effective`, `revision`, `inherited_from/status`, `limit` when the connection is paused (see “Upstream rate limits”), and `fields/provider_ids` to constrain the form. The categories' `category_id` equals their own ID, with `uses: [{"name":"Read-only purpose description"}]`. The AI twin and Lark /agent point `category_id` to Agents but have their own `override`, `revision`, and nonempty `fields`; clients determine editability from `fields`, not solely `category_id`. The background supervisor's purpose (in the catalog since #5806) points `category_id` and `parent` to Main chat the same way, with its own `override`, `revision` and nonempty `fields`; so does the In-meeting conversation's (`meeting.room`), and Meeting minutes (`meeting.minutes`) points them to Information processing (#7980). Other legacy purposes point `category_id` to their owning category; `override` is empty, `fields` is `[]`, and revision and effective model come from the category. A task purpose (`task.<task id>`, requested by its own `GET`) points `category_id` and `parent` to Main chat but has its own `revision` and `override` and nonempty `fields` (provider, model, effort); with an empty override it follows Main chat, including later changes there. Real task names do not appear on the configuration home page. The `plugin.<plugin id>` model protocol remains independent and is not added to the four-category catalog. Responses contain no secrets.

Saving one item:

```json
{
  "revision": 0,
  "provider": "launcher.<provider name>",
  "model": "<specific model ID>",
  "effort": null
}
```

Only `assistant` may write `config_dir` (`"private"` or `"legacy"`, see “Main chat's profile for new conversations”). A `runtime` an older client sends is accepted and ignored on every purpose (“How the main chat runs (#9799)”).

“Information screening” (`inbox.triage`) also governs plugins: plugins using the Inbox without their own fallback require it to be callable before they can be enabled. With such plugins enabled, a change making it unusable returns 422 `triage_model_in_use`,
listing plugin names (clearing a selection still saves normally if fallback to `manager.json`'s `ai` / `inbox.triage_ai` or automatic selection remains callable; `docs/extensions/extensions.md`, “General rules for the Inbox”).

Send to `PUT /api/v1/model-config/purposes/{id}` or the compatible `PATCH` endpoint. The five category configurations, the AI twin, Lark /agent, the background supervisor, Meeting minutes, the In-meeting conversation, the extensions' own purposes, and independent plugins are writable; other legacy purposes or task IDs return 400 (purpose models are read-only; edit the owning category). Missing fields are unchanged, `null` clears a selection, and nonempty values override. Success returns the same structure as a single-item GET. Only supported fields may be selected; a revision mismatch returns 409, and unknown purposes are not created ad hoc.

## Main conversation settings (#11936)

The `assistant` category is **Conversation defaults**. It remains the default for new side conversations, schedules and other Assistant uses. **Main chat** is the independent `assistant.main` purpose, with its own launcher provider, model and effort. Changing this purpose does not write the `assistant` category, a scheduled task, a background supervisor, or another conversation's pick.

The manager stores its revision-checked binding in `model_config.assistant.main`, using the existing model-configuration API and Postgres settings table. No backfill changes existing records: an absent or empty binding inherits `assistant`, preserving the previous behavior. Sparse updates retain omitted fields; reset clears the main override and restores inheritance. Older clients cannot clear it by omitting new fields from a shared-default update. Category model-profile changes leave this independent record intact.

An explicit conversation or message pick takes precedence over the main default. A carried pick survives clearing the main chat as before. Without a pick, main creation, subsequent sends, warm preparation and readiness probes resolve `assistant.main`. New side starts still resolve `assistant`. The web's empty main starter and running main pill read the separate effective binding; an ordinary new-conversation page continues to read the shared default.

A launcher of another engine still requires the explicit logical-conversation switch operation from phase 2; saving a model setting is not permission to reinterpret the existing engine's transcript. A switched conversation's explicit segment choice remains ahead of inherited defaults. Resetting the main default does not undo an explicit segment switch or discard its history.

Rollback to a build without main-only settings ignores the extra record and uses `assistant`; the stored main binding is retained for re-enable. A conversation already switched between engines still requires a segment-aware manager for rollback. No deployment or production acceptance is implied by this setting.
