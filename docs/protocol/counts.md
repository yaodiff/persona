# Counts: the numbers people see, computed once per manager

The badges, tab numbers and switcher counts every client draws come from one view per manager: the manager works out
each count from its own sessions, cards and items, the hub relays the view as it is, and each client adds up the
managers in a surface's scope (`docs/plans/plan-derived-counts.md`, #11679). **Who it serves:** everyone. Assistant
users see one number for each name on every screen and device; Agents users can trust that the badge, the list and the
Lock Screen agree. This doc is the contract: what the view holds, what each count id means, and how a count may change.

**Status (#15512, #15650, #15893, #15896, #15397):** the schema, its generated types and the wire samples exist. Each
manager tells the hub its view (step 7a, "The manager's view" below), including the To-dos and Persona counts from
step 12. The hub relays it to clients that ask (step 7b, "The hub's relay" below, and the rows in
`docs/protocol/protocol.md` "Counts view"). No client draws a view yet: they do from steps 8 to 10, keeping views as
`spec/fixtures/counts/views.json` says. Until a client draws the view, every number it shows is still its own.

## The view

`CountsView` in `schema/wire/counts.schema.json`, generated by `scripts/gen/extension_schema.py` for Go
(`server/internal/assistantwire/counts_gen.go`), TypeScript (`web/src/lib/counts-wire.ts`), Swift
(`apple/Packages/PersonaWire/Sources/PersonaWire/CountsWire.swift`) and Kotlin
(`android/core/contracts/src/main/kotlin/persona/core/contracts/generated/CountsWire.kt`). HarmonyOS and the shared Rust
core draw no badges; the schema guards both languages against a hand-written copy (`x-guard`). The samples are
`spec/fixtures/counts/view_samples.json`.

```jsonc
{
  "epoch": "b7e1c2a9",          // one run of the manager; a restart starts a new one
  "rev": 5,                     // goes up with every view in the epoch
  "as_of": 1795593605000,       // Unix ms: only to say how old a kept view is
  "build": "1.0.0",             // the manager build that made it ("Changing a count")
  "counts": {                   // one named field per count id, absent when the build does not work it out
    "agents_needs_you": {
      "n": 2,                                              // the number drawn
      "keys": [{"id": "agent:studio/s3"}, {"id": "card:ix-a", "cards": ["ix-a"]}],
      "held": [{"id": "agent:studio/s1", "why": "muted"}]  // listed, not counted
    },
    "todos_needs_you": {"n": 3, "more": 3},                // a count that lists none of its rows
    "persona_cards": {"n": 1, "keys": [{"id": "card:ix-b", "cards": ["ix-b"]}]}
  },
  "totals": {"agents_needs_you": 2, "todos_needs_you": 3, "persona_cards": 1}
}
```

| Field | Meaning |
| --- | --- |
| `epoch` | One run of the manager, opaque, only compared. A view with a new epoch replaces the one a client keeps, whatever its `rev` |
| `rev` | Within an epoch a lower `rev` loses to a higher one, so a late view never replaces a newer one |
| `as_of` | When the manager made the view, in Unix milliseconds. Only to say how old a kept view is (diagnostics); never a reason to draw a view differently |
| `build` | The manager build that made the view, so a number can be read against the definition that build applies ("Changing a count") |
| `counts` | Each count the manager works out, by id. A count a build does not work out is absent, which means unknown, never 0 |
| `totals` | Optional: each count's `n` again, by id ("Totals") |

## The manager's view

- **Capability and event.** A manager that tells its view names `counts_view` in its `manager.hello` capabilities and
  tells the hub the one-way bus event `counts.view`, whose params are the view (`CapabilityCountsView` and
  `EventCountsView` in `server/internal/assistantwire/counts.go`). A hub from before step 7b drops the event, as it
  drops any event it does not know.
- **When.** The manager's live round (`liveLoop`, `server/internal/assistant/counts_view.go`) makes the view from the
  agents and cards it builds the Live Activity's state and Persona Link's summary from, and tells it after the state,
  so the three agree and a badge is never ahead of the lists the round published. A round whose counts and totals did
  not change tells nothing; a change goes up one `rev`, with a new `as_of`. After each handshake the last view is told
  again as it was, so a hub that restarted has it. Each run of the manager draws a new `epoch`, and `build` is the
  manager's version.
- **The to-dos' counts (#15896).** The manager keeps the counts of the last read of its whole to-do list, the ones
  `GET /api/v1/todos` answers with (every read of the list, of one to-do or of the places works the whole list out), in
  `server/internal/assistant/counts_view.go`, and the next round hands them to `Fleet.View` (below), which writes
  `todos_needs_you` from them; `surfaces.json` names it as that count's `producer` too. Every `{"type":"todos"}` makes
  each app read the list again, which keeps the new counts; when none did a second after one, the manager reads the
  list itself, so the number follows the list while no app is open. It reads one list at a time: a round or a
  `{"type":"todos"}` that asks while a read waits or runs (on a slow store, up to its 30 s) starts no second one, and a
  `{"type":"todos"}` that went out meanwhile has the manager read the list once more after it. Until a run has counted
  its to-dos, each round asks for a count, and the view leaves `todos_needs_you` out.
- **Who writes what.** `fleetcount.AgentsNeedsYou` decides the Agents rows and `fleetcount.PersonaCards` decides which
  cards count for Persona. The live round supplies quiet agents for the Persona count alone
  (`fleetInputsForRound` in `server/internal/assistant/fleet_live.go`). The adapter's `Fleet.View`
  (`server/internal/assistant/fleetcount/fleetcountadapt/view.go`) writes `counts` and `totals` from the same
  tallies. Package assistant adds `epoch`, `rev`, `as_of` and `build`. `spec/fixtures/counts/surfaces.json`
  names `Fleet.View` as each count's `producer`, and the adapter's tests hold it to the table.
- **The bound.** A view takes at most 16 KB as JSON (`CountsViewMaxBytes`), the most the hub keeps.
  Each count's `keys` and `held` list at most 200 rows each. The adapter budgets Agents `keys`, Agents `held`,
  and then Persona `keys`. Each list stops at the first row that would pass its limit, with 1 KB reserved for the
  rest of the view. Counted rows omitted from `keys` are included in `more`.

## The hub's relay

The hub is transport: it passes each manager's view on as the manager wrote it and works out no count
(`server/internal/hub/counts_view.go`). It imports no counting core, domain kit or adapter, which
`server/internal/hub/architecture_guard_test.go` and the archguard's `path-no-core` rule hold.

- **What it keeps.** The last view of each manager's current bus connection, compacted, when the view is a JSON object
  of at most `CountsViewMaxBytes` with a non-empty string `epoch` and a whole `rev` of 0 or more. It reads nothing else
  of it, and drops a view that is not one, or that comes from a manager whose hello did not name `counts_view`. The view
  goes with the connection: a hub that restarted has none until each manager connects again and tells its last one.
- **What it sends.** `{"type":"counts","manager":"<id>","view":{…}}` when a manager tells a view that differs from its
  last one, and for every kept view, by manager id, as a client connects (after `machines`, before the session lists)
  or names the feature in a `client_hello`; `"view": null` when the connection of a manager that told one ends.
  `manager` is always there, the built-in assistant's id included, as a client keeps one view per hub and manager. An
  app never gets a manager's view after a newer one: relays and the views sent at connect are queued under one lock.
- **To whom.** Only full-role clients that ask for the feature `counts_view` (`?features=` or `client_hello`): a view
  lists every waiting session and card of a manager, so it reaches only what may read them all. Scoped and answer-only
  devices get no `counts` message whatever they ask. `counts` is one of the hub's own message types
  (`hubMessageTypes`), so no manager can broadcast one.
- **Feature and flag (D10).** The hub lists the feature `counts_view` always, from the proto feature list
  (`server/internal/proto/features_counts.go`): hub features reach a client only in the hello, so a feature that
  followed the managers would switch the client's rule on every redeploy. Each roster entry says `counts_view: true`
  while that manager is online and its hello named the capability. A client takes a manager as absent, and draws the
  surfaces whose scope holds it from its fallback, when the hello lacks the feature, the manager's entry is online
  without the flag, or it never kept a view of that manager; offline and `view: null` are not absence.
- **What a client keeps (D13).** The last view per hub and manager, persisted, through `view: null`, going offline and a
  hub restart; a new epoch replaces it whatever its rev, and a lower rev within an epoch loses. It is dropped when the
  roster no longer lists the manager, at sign-out and on D10's explicit absence. `spec/fixtures/counts/views.json`
  writes each case as given, one transport event and then (`spec/fixtures/counts/README.md`, "Kept views"); each
  client's reducer replays it from steps 8 to 10, and `TestTheHubReplaysTheRestartCases` replays its restart cases
  through the hub.

## A count

| Field | Meaning |
| --- | --- |
| `n` | The number drawn: the counted rows, as many as `keys` lists plus `more` |
| `keys` | The counted rows, oldest first, at most 200. A manager may list fewer to keep the view small; absent when none |
| `held` | Rows the list keeps but the count leaves out, oldest first, at most 200, each with its reason; absent when none |
| `more` | The counted rows `keys` leaves out, so `n` is the rows `keys` lists plus `more`; absent when 0 |

A row's `id` is the key the shared fixtures use (`spec/fixtures/needs-you`, `spec/fixtures/counts/README.md` "Lane
reports"):

- `agent:<machine>/<session>`: a session that waits. A child's and a side session's cards are under the row of the
  session the hub folds them under (`folded_under`). Its `cards` are its pending cards, oldest first; absent when it
  waits in its terminal with no card.
- `card:<interaction id>` identifies an individual Persona card or a sessionless Agents card
  (`personad ask` outside a terminal engine). Its `cards` hold that one card.

A card id is the interaction id `POST /api/v1/interactions/{id}/resolve` takes, so a client can match the cards the
owner just answered against the rows they belong to.

### Why a row is held

| `why` | Meaning |
| --- | --- |
| `muted` | The owner muted the agent or its space |
| `held` | Its only cards are questions the assistant is still deciding whether it may answer for the owner (D11 of `docs/plans/plan-derived-counts.md`) |

A client draws quiet agent rows from its own list. The manager supplies those agents only for `persona_cards`, where
each eligible card has its own key. Listing quiet agent rows under `agents_needs_you` would require a new optional
reason, `quiet`. A word a client does not know decodes to the generated enum's unknown and is never counted.

### Who writes `why`

`why` is a wire word; no type of the counting core enters the schema. `server/internal/assistant/fleetcount` decides
each row's reason as a `Why` and knows no wire shape, and the hub never decodes `counts`. The adapter
`server/internal/assistant/fleetcount/fleetcountadapt` is the only code that writes a `Why` as its wire word, through
its `WhyVisitor` (`whyWord` in `server/internal/assistant/fleetcount/fleetcountadapt/fleet.go`): a new `Why` case adds
a method to `WhyVisitor`, so the adapter does not compile until the case has a spelling. A spelling the wire lacks is a
new value of `CountsHeldReason` in the schema, which older clients read as unknown; until then `Fleet.View` lists a row
for that reason in neither list, as it does a quiet task's. `TestViewSamplesAreFleetcountsRows` in that package holds
the samples to what `Fleet.View` writes for the needs-you cases they name, each held reason spelled by `whyWord`.

## Count ids

An id names a meaning on screen. Each is a named field of `counts` and of `totals`; there is no `{surface: id}` map
(D5): each client names the ids it draws, and `spec/fixtures/counts/surfaces.json` with its guard stays the one table
of which surface draws which ids, in which scope. Such a map could carry neither a scope nor a sum (the app icon draws
three ids), and the definitions change in the manager, not in the client's id. A map is reopened only for a decided
remap that must reach every device at once, and would then be an optional addition.

### `agents_needs_you`

The Agents that wait for the owner: one row per waiting session, folded to the session the hub folds it under; a card on
no session counts 1; Persona conversations, quiet tasks' agents, muted agents (in `held`), directory-hidden sessions
(`docs/protocol/protocol.md`, "Agent directory visibility") and sessions whose only cards are held (in `held`) are left
out; a card its task's supervisor holds is in no row. Pinned by `spec/fixtures/needs-you` (`badge_rows`), decided by
`fleetcount.AgentsNeedsYou` on its badge surface, written by `fleetcountadapt`'s `Fleet.View`. In the view since step 7a
(#15650).

### `todos_needs_you`

N of the To-dos list (D8 of the plan): the to-dos in its Needs you section, each once; Can wait and quiet tasks' to-dos
are left out, and a step its parent carries counts with its parent. It is the `needs_you` of the counts
`GET /api/v1/todos` answers for this manager's whole list, the to-do projection's `Counts()`
(`server/internal/assistant/todo/projection/list.go`), pinned by `spec/fixtures/todo-counts`. Those counts are numbers
without their rows, so the count lists no `keys` and no `held`: all of `n` is `more`. A client that has the list files
the rows itself; listing them in the view would be a schema addition (a row key for a to-do). Absent until the
manager has counted its to-dos ("The to-dos' counts" above). Written by `Fleet.View`, which is handed the counts as
they are, so no record is made for them. In the view since #15896.

### `persona_cards`

Pending cards for the owner on Persona conversations and quiet tasks' agents (D9 and D11 of the plan), one per card.
The card's asking session determines eligibility even when a child or side is folded under another row.
Muted sessions or spaces, directory-hidden sessions, cards held by Persona or a supervisor and `mirror_of` display
copies are excluded. Pending forms and untold owner cards count. A terminal wait contributes only through its
pending card. A card on no session belongs to `agents_needs_you`. A named session absent from the inventory has
no known Persona or quiet role.

`Fleet.View` writes these cards from `fleetcount.PersonaCards`, pinned by `spec/fixtures/persona-cards`. Its oldest
cards are listed as `card:<id>` keys up to the row and byte limits. `n` includes every eligible card, `more` accounts
for cards omitted from `keys`, and excluded cards have no `held` entries. A manager that computes the count sends
`n` and its total even at zero. Earlier builds omit the field. The Live Activity uses its own standing-card rule
(D4).

### Later ids

`inbox_unread` and `inbox_action` come after their decision in the plan's section 6 (D7), each with its fixture and
its line here. `surfaces.json` lists their rules until then. Until the Inbox has a
core of its own, its count comes into the view as one more input of `Fleet.View`: the number package assistant works
out today (the Inbox items' `status()` fold), never a record made for it, as the to-dos' did (`todos_needs_you`). Once
the view's schema carries an id, its row in `surfaces.json` names its `producer`, and the guard fails until it does. The composer's Needs you is not a count id: it stays the `assistant_needs` payload of
`docs/design/proposals/todos-redesign.md`.

## Changing a count

- **A decided refinement keeps its id** (D18). This doc records it below with the manager build that applies it. Skew
  while builds roll out is accepted: the built-in manager updates with the hub, and diagnostics read an external
  manager's build from the view's `build` and `as_of`.
- **A change of unit is a new id**, such as unread items against open action items.
- **A new id is an optional field** of `counts` and `totals` in the schema, regenerated for every client. An older
  client ignores it, and a client draws it only once it names it.

| Id | Refinement | Decision | Applied by |
| --- | --- | --- | --- |
| `agents_needs_you` | A session whose only cards are held leaves the count; a card its task's supervisor holds, a routed terminal question included, is in no row | D11 (2026-11-22, routed terminal questions confirmed 2026-11-23) | `fleetcount` (#15250); in the view from the first manager build that tells it (step 7a) |

## Totals

`totals` repeats each count's `n` by id (D12). The manager fills it from the same rows as `counts`; the hub copies it
as it is into pushes and widget wakes, so it never decodes `counts`. A number outside the running app is never a plain
`aps.badge`, and Android sets no notification number; how pushes carry `totals` to devices that ask for it is step 12
of the plan.

## Until every client draws the view

Each client keeps today's rule in one frozen fallback, used only while a manager in a surface's scope is absent (an old
hub, a manager without the capability, or one that never sent a view this client kept), so one number never mixes two
rules. The fallbacks are deleted at step 13 on conditions, not a date (D14):

- **The floor** is the first stable release with steps 7a and 7b, recorded here when it ships (not yet).
  `proto.Protocol` is not bumped.
- Step 13 waits until the floor has been stable for 90 days; the client has drawn views in a released build for 30
  days; `count_skew` is 0 and `counts_shadow` clean for 30 days on opt-in devices the step-13 issue names, at least two
  per client; and `count_fallback` is 0 for 14 days for the reasons step 13 removes (an old hub, an old manager
  online). Managers that are offline and never sent a view are reported apart.
- After step 13, iOS and Android tell a hub without `counts_view` by a compatibility notice of its own, with its own
  dismiss key and words (for example "Update the hub to see counts"), never `hubTooOld`, whose notice is dismissed for
  good (`docs/operations/hub-update.md`).
- A manager absent from a surface's scope leaves that surface without a number, and the switcher marks the manager as
  needing an update or offline: never a sum that silently leaves it out.
- `count_skew` stays for good; `counts_shadow` and `count_fallback` go with the fallbacks.
