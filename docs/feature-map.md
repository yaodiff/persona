This map locates Persona's major maintained capabilities and their evidence. It is a navigation and maintenance index, not an acceptance dashboard or a second automation system. It does not inventory every setting or minor variant. Tracked issue: [#12208](https://github.com/nwverse/persona/issues/12208).

## Status contract

| Field | Allowed states | Required meaning |
| --- | --- | --- |
| Implementation | `merged` | The cited implementation exists at the reviewed `main` baseline. It does not imply test execution, release or deployment. |
| Test evidence | `PASS`, `FAIL`, `NOT_RUN` | `PASS` and `FAIL` require an actual command, environment, date and result in the change report. `NOT_RUN` means the cited test exists but was not run for this map; it is not a passing result. |
| Deployment | `deployed`, `NOT_RUN`, `N/A` | `deployed` requires a named environment, deployed revision, date and read-only verification. `NOT_RUN` means no current environment was inspected. `N/A` is only for a component with no independent deployed runtime, such as a pure contract or library. |

A local unit test, simulator, synthetic hub, browser fixture or historical CI result is not production verification. A merge, release tag or deployment script is not evidence that a deployment happened.

## Maintenance protocol

1. **Read before delegation.** Before assigning an Agent, read the relevant subsystem row and its cited implementation, test and module-guide lines. Put the current capability, known gap and next step in the handoff. Inspect the source again when the baseline has moved; do not copy a stale line number.
2. **Update with the work.** When a task changes a mapped capability, update its row in the same PR: public entry, implementation `file:line`, test `file:line`, actual execution evidence, known gap and next step. Add a row only after the implementation and its test entry have been read. Remove a row when its capability is removed.
3. **Keep evidence lanes separate.** Record a test command and its result without changing deployment state. Change deployment to `deployed` only after the named environment and revision have been verified. Record missing device, live-service or release evidence as `NOT_RUN`, with the boundary in the gap.
4. **Use one maintenance owner.** The designated `feature-map-maintainer` Agent owns on-demand review. A review is triggered by a merged change to mapped code/tests/docs, new deployment evidence, or an explicit maintainer request. There is no periodic cron, empty poll or run without a triggering diff or evidence. This role uses the ordinary issue/PR workflow; it is not another AOCI.
5. **Review only the trigger.** The maintenance Agent checks the affected rows against the new `main`, repairs stale references and evidence, and updates the review record. It does not rewrite unrelated rows or invent gaps to make a run useful.
6. **Validate every update.** Run `python3 -B scripts/test/test_feature_map.py` and the existing documentation checks listed below. The validator checks the table contract, allowed states, referenced files and line bounds. A valid line number does not prove that the prose is correct; the reviewer must still read the cited symbol.
